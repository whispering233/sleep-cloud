# 开发遗留项（Backlog）

本文件收集**已决定推迟**的事项。每项必须写清：为什么延后、什么时候该回头做。已确定不做的方案（而不是推迟）不记在这里。

## 一、产品功能类

| 项 | 为什么延后 | 何时该做 |
| :--- | :--- | :--- |
| **聊天历史持久化** | 无需求；客户端本地保留最近 N 条足够显示。服务端存历史会带来存储成本与隐私负担 | 出现「睡醒后想看看昨晚别人说了什么」的真实反馈时。届时需同时定：存哪、保存多久、谁能读 |
| **共处时长展示**（Nylu 式「一起睡了 6h10m」） | 第 1 阶段不做 UI。**但数据已经白送**：睡痕本身就是「躺下时间 + 起床时间」，也就是一条 sleep session，现在就在存 | 第 1 阶段跑通后即可加，零改表 |
| **跨厅串门 / 换厅 / 追着夜晚走** | 引入厅间移动会打乱「宿舍室友」的稳定关系，且需要厅间协调 | 出现「厅里人太少想去别的厅」的真实反馈时 |
| **满员自动扩厅** | 自动化运维，YAGNI。第 1 阶段「开新厅」= 手动加一条厅配置 | 单厅真的长期接近满员时（配置化的厅列表已为此预留） |
| **装饰自己的床位 / 床头留言 / 关灯** | 属于「玩法」，不在第 1 阶段范围 | 第 2 阶段；注意这会引入 UGC 审核负担 |
| **表情轮盘** | 可要可不要，Wheat 有 `obj_emoteRoulette` 可参考 | 第 1 阶段跑通后按余量决定 |
| **音频 / 白噪音 / 环境音** | 无音频则无音量设置，因此「设置」界面在第 1 阶段整体不存在 | 第 2 阶段；会同时带出设置界面与移动端自动播放限制问题 |
| **地图编辑器**（对标 `WheatBox/CloudSleepEngine`） | 第 1 阶段手写场景 JSON 即可，工具链是明确的过度设计 | 需要频繁换地图或开放用户自定义场景时 |

## 二、架构类

| 项 | 为什么延后 | 何时该做 |
| :--- | :--- | :--- |
| **D1 全局用户表** | 3 个厅 × 256 床的规模下，「用户属于哪个厅」放签名 cookie 就够，厅 DO 是唯一权威。引入 D1 只增加一个需要同步的真相源 | 出现跨厅迁移、用户资料页、全局数据看板、跨厅统计需求时 |
| **目录 DO / KV** | 同上 | 同上 |
| **反作弊加固**（点击频率限制之外的寻路滥用防护） | 第 1 阶段只有 5 条/秒上行限流。服务端寻路本身能挡住大部分伪造目标点 | 出现刷寻路/脚本走动等滥用迹象时 |

## 三、风控与治理类（Phase 2）

第 1 阶段只做：**内容过滤**（昵称 + 聊天敏感词，打码不拦截）、**上行限流**（5 条/秒）、**错误码体系预留风控码位**。

| 项 | 参数/形态参考（来自 WheatCloudSleep 源码） |
| :--- | :--- |
| **举报** | `CmdReport` → 记录到独立日志 |
| **渐进惩罚封禁** | `block_period_m` 10 分钟起 → 上限 `max_block_period_m` 1440 分钟；观察期 `watch_period_m = 2 × block_period_m` |
| **违规检测维度累计** | Wheat 按 IP 维度累计（`ViolationDetector` 观察者） |
| **投票踢人** | 判定 `agree >= 2 * refuse && agree > 2`（至少 3 票同意且同意数 ≥ 反对数 2 倍）；Wheat 还有发起冷却 `vote_kick_ratetime_s` |
| **封禁维度** | 设备 id（cookie 内）+ IP |
| **年龄分区**（成人区 / 未成年区） | 第 1 阶段只存「18 岁自述」这一个字段，不做分区 |
| **静音/安静区与聊天区分厅** | 调研结论：安静陪伴与热闹聊天互斥（Nylu 与 SleepInLate 都做了隔离），最终大概率需要分厅 |
| **聊天历史举报取证** | 与「聊天历史持久化」绑定：不存历史则事后取证只能靠实时记录 |

**已知且未解决的风险**：匿名 deviceId 存在 cookie 里，清掉即可换身份，因此封禁只能延缓不能阻止。若要真实保障必须上账号（见「身份与年龄」决策）。

## 四、性能与验证类

| 项 | 说明 |
| :--- | :--- |
| **单厅容量压测** | 官方只给「单 DO 软上限 1,000 requests/s、单线程」，未给每 DO 的 WebSocket 连接数上限。第 1 阶段的目标（256 床 / 并发在线 100）是拍的，必须实测校准 |
| **PixiJS 低端手机帧率** | 500+ sprite（256 床 + 小人 + 装饰）在低端机上的表现未实测。若每个睡着的人都有逐帧呼吸动画会明显吃 CPU，第 1 阶段建议用整体 alpha 微变代替逐帧动画 |
| **睡痕集中清理负载** | 若睡痕按「次日本地时间」集中过期，会出现同一时刻大量 alarm 负载，需要错峰窗口设计 |
