# 开发遗留项（Backlog）

本文件收集**已决定推迟**的事项。每项必须写清：为什么延后、什么时候该回头做。已确定不做的方案（而不是推迟）不记在这里。

> 已落地、不再属于遗留项的事：复用 `WheatCloudSleep` 美术素材（已定稿并写进 `../ui/DESIGN.md`）、满员自动扩厅（已由级表取代）、跨厅串门（已不存在多厅）、用户侧缩放（已取消）。

## 一、产品功能类

| 项 | 为什么延后 | 何时该做 |
| :--- | :--- | :--- |
| **聊天历史持久化** | 无需求；客户端本地保留最近 N 条足够显示。服务端存历史会带来存储成本与隐私负担 | 出现「睡醒后想看看昨晚别人说了什么」的真实反馈时。届时需同时定：存哪、保存多久、谁能读 |
| **共处时长展示**（Nylu 式「一起睡了 6h10m」） | 第 1 阶段不做 UI。**但数据已经白送**：睡痕本身就是「躺下时间 + 起床时间」，也就是一条 sleep session，现在就在存 | 第 1 阶段跑通后即可加，零改表 |
| **换床**（主动释放旧床 + 认领新床） | 现在是一人一床不可换（`3007`）。需求真伪不明：床号 + 我床标记已经能让人回自己那张；而允许换床会让「我的床位」变成可抛弃的东西 | 出现「想换到朋友旁边 / 想换个位置」的真实反馈时。实现 = 一个意图里先释放旧归属再认领新归属（同一事务） |
| **表情贴图** | 素材里没有表情图（原实现的 `gArrSleeperEmoteSprites` 来自云端场景包，仓库里没有）。现在世界内用**文字短标签气泡**呈现 | 有人把 5 个表情画出来时（一个贴图替换一个文字气泡，零改协议） |
| **睁眼躺姿补画** | 躺姿素材只有闭眼那一张。现在 `lying`（清醒躺着）靠代码在脸部位置叠两个点 | 在 SAI 2 里改 `bedBoy.sai2` / `bedGirl.sai2` 导出两张 PNG 即可；**替换是零成本的**（贴图换 overlay） |
| **装饰自己的床位 / 床头留言** | 属于「玩法」，不在第 1 阶段范围 | 第 2 阶段；注意这会引入 UGC 审核负担 |
| **音频 / 白噪音 / 环境音** | 无音频则无音量设置，因此「设置」界面在第 1 阶段整体不存在 | 第 2 阶段；会同时带出设置界面与移动端自动播放限制问题 |
| **多厅 / 串门 / 追着夜晚走** | 单厅 + 自动伸缩已经把「厅会满」这件事消掉；多厅会立刻带出「选哪个厅 / 能不能串门 / 厅间社交割裂」三个问题 | 单个厅的并发或活跃度真的逼近平台上限时（级表已经到最后一档且仍然不够） |
| **地板质感贴图** | 现在地板是纯色（走动反馈靠床滑过屏幕）。零美术即可接受 | 真机上看「走动没有速度感」或「大暗底太空」时。**不动几何**，只换 `TileSprite` 的贴图 |
| **安静区 / 热闹区的分区** | 调研结论：安静陪伴与热闹聊天互斥（Nylu 与 SleepInLate 都做了隔离）。但分区在第 1 阶段会引入「选哪个区」的入口 | 出现「想安静躺一会儿但聊天太吵」的真实反馈时（那时也得先解决多厅，见上） |

## 二、架构类

| 项 | 为什么延后 | 何时该做 |
| :--- | :--- | :--- |
| **多套布局主题**（换布局公式 / 换级表） | 第 1 阶段只需要一种几何。布局是纯函数，换主题 = 换函数 + **递增布局版本号** | 出现「想要不同形态的厅」的真实需求时 |
| **老 bundle 的平滑迁移** | 布局版本不一致现在直接 `2003` + 断开（要求刷新页面）。第 1 阶段只有自家前端，刷新是可接受的 | 出现「用户停在旧页面上很久」导致频繁被踢的迹象时 |
| **D1 / 全局用户表** | 单厅 + 匿名 cookie 的规模下「用户属于哪」不是一个问题（没有第二处）。引入 D1 只增加一个需要同步的真相源 | 出现跨厅迁移、用户资料页、全局数据看板时 |
| **目录服务 / KV** | 同上 | 同上 |
| **反作弊加固**（寻路滥用之外的防护） | 第 1 阶段只有 5 条/秒上行限流 + 目标点必须在街网上。服务端寻路本身能挡住大部分伪造目标点 | 出现脚本刷走动、刷聊天等滥用迹象时 |
| **睡痕过期与归属过期的「提前通知」** | 两者都是读取时推导，客户端自己算。代价：**大厅里最后一个在线的人**看不到别人睡痕到期（他不在场）——这不是问题 | 不需要回头做，除非出现「睡痕到期没消失」的实测证据 |

## 三、风控与治理类（Phase 2）

第 1 阶段只做：**内容过滤**（昵称 + 聊天敏感词，打码不拦截）、**上行限流**（5 条/秒）、**错误码体系预留风控码位**。

| 项 | 参数/形态参考（来自 WheatCloudSleep 源码） |
| :--- | :--- |
| **举报** | `CmdReport` → 记录到独立日志 |
| **渐进惩罚封禁** | `block_period_m` 10 分钟起 → 上限 `max_block_period_m` 1440 分钟；观察期 `watch_period_m = 2 × block_period_m` |
| **违规检测维度累计** | Wheat 按 IP 维度累计（`ViolationDetector` 观察者） |
| **投票踢人** | 判定 `agree >= 2 * refuse && agree > 2`（至少 3 票同意且同意数 ≥ 反对数 2 倍）；Wheat 还有发起冷却 `vote_kick_ratetime_s` |
| **封禁维度** | 设备 id（cookie 内）+ IP |
| **年龄分区**（成人区 / 未成年区） | 第 1 阶段只存「18 岁自述」这一个字段，不做分区 |
| **聊天历史举报取证** | 与「聊天历史持久化」绑定：不存历史则事后取证只能靠实时记录 |

**已知且未解决的风险**：匿名 deviceId 存在 cookie 里，清掉即可换身份，因此封禁只能延缓不能阻止。若要真实保障必须上账号。

## 四、性能与验证类

| 项 | 说明 | 何时该做 |
| :--- | :--- | :--- |
| **单厅容量压测** | 官方只给「单对象软上限 1,000 requests/s、单线程」，未给每对象 WebSocket 连接数上限。第 1 阶段的目标（114 床起步 / 并发 100）是拍的，必须实测校准 | 卡 3 落地后 |
| **Phaser 世界层帧率**（低端机） | 可视窗口 + 对象池的理论同屏对象数约 60（床 + 床号 + 小人），但**没量过**。若低端机不够，最小改法是减少床号文字对象（只在视野内取整行编号）或把床号换成位图字体 | 卡 1 落地后 |
| **空芯（可躺）通道的可辨性** | 「无主空床 = 空芯（白填充映射为透明）」靠 `paper` 与底色的 1.53:1 面积差。**为什么延后**：这是手感与口味，得真机低亮度下扫一眼。 | 卡 4 之后；若判「看不出来」，补救顺序是 ① 加大 `paper` 与底色的差；② 在无主空床床角加 `claimed` 色小标记（**不动几何**） |
| **困倦度幅度** | 地板底色的深浅幅度（`primary` ⇄ `primary-dim`）现在取的是「几乎察觉不到」。真机上可能完全看不出，也可能刚好 | 卡 7 之后；改色值即可 |
| **级表步长与升降级频率** | 级表步长约 ×1.37。若升/降级比预期频繁（滚动条式跳档），说明步长太小 | 有真实数据后调级表（**改级表必须递增布局版本号**） |
| **「最小空缺床号」查询的成本** | 出生点依赖它。缓存命中为零成本，驱逐后退化为一次表扫描（几百行） | 入场量显著变大时 |
| **节拍实际抖动** | 云端计时不精确。需实测两次节拍的实际间隔分布，确认「按实际时间差推进」的修正是否足够 | 卡 3 之后 |
| **`setAlarm()` 实际调用次数** | 每个对象每天应是个位数到几十次量级。若显著更高，说明调度器的「先比对再设置」没生效 | 卡 3 之后看平台用量面板 |
| **内存循环是否真的在无人走动时被清除** | 这是最容易泄漏活跃时长的地方。验证方式：无人走动的时段，活跃时长应停止增长 | 卡 3 之后看平台用量面板 |
| **睡痕 TTL 12 小时的体感** | 它是拍的（覆盖一整夜睡眠）。早晨不再保证「干净的厅」 | 真实使用后再定 8h / 14h / 24h |
| **点击手感：点床 vs 点地面** | 无缩放之后床是 61×100 的大目标，但床与床之间只有 4px 的缝、床边就是走道 | 卡 6 之后真机补测；不可接受就调「床的命中矩形」（**不动几何**） |
| **格模型残留（过渡期）** | 位置只在下行改成像素，服务端权威格仍是格号：①「就地点自己脚下那一格」若发生在两格之间，会按格心回正一次（≤32px）；②对象被驱逐后重建把「本格已走进度」归零（≤32px）。两者都属过渡期现象 | **不单独修**：卡 3 把权威位置换成像素后自然消失 |
| **渲染时钟平滑**（把“节拍晚点补上的位移”均摊到后续几帧） | 快照改成固定节拍发送后，单帧台阶的来源只剩一个：服务端节拍偶尔晚点（100ms 的拍拖到 260ms），客户端会在那一帧一次补上 ~20px。**为什么延后**：逐帧模拟显示 1× 滞后在这组场景里不劣于 1.5×，而“平滑”是新机制（会动客户端时间轴），得先有真实数据 | 先量两件事：服务端 tick 的**实际间隔分布**（最小/中位/最大/超过 150ms 的次数）与真机观感。两者都说明“晚点确实常见且看得见”时再做 |
| **互动意图重复上行** | **已复验：一次轻点 = 1 条上行，一次 DOM 点击 = 1 条**（之前的“双发”是验收方分触摸/鼠标两轮各一次）。**无需去重，已关闭** | — |
| **双击必然发 2 条 `walk`** | 双击 = 两次轻点，代码本就是逐 tap 分派；5 条/秒限流内无坏结果。若用户心里把双击当“一次动作”，就在客户端做双击去抖 | 出现真实抱怨时 |
| **提示条自清只挂在 `animationend`** | 动画被外力取消/禁用（截图管线、未来的 `prefers-reduced-motion` 分支）时提示条会常驻；产品默认路径下不复现 | 改提示条生命周期时一并改 |
| **提示条遮住顶部两行床号** | 提示条出现时盖住 y≈41~77 的床号约 3 秒（`pointer-events:none`，不影响点击） | 卡 5（HUD 精简）时一并看窄屏可读性 |
