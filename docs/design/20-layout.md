# 子模块设计：厅的空间模型与布局

一个厅的**全部几何都是程序化生成的纯函数**（`src/shared/layout.ts`）：床号 ↔ 位置、走道、区域、可走性。前端与房间服务引用**同一份**（`architecture.md` §2.5），所以不会出现「服务端认为不可走、客户端却画得出」的分歧，也**没有场景文件**。

**本文是尺寸、规格、级表与布局契约的唯一来源。** `config.md` 只放运行时可调的配置与限额；`../ui/DESIGN.md` 放视觉（贴图变体、色阶）；`10-hall-runtime.md` 放升降级与出生点的**运行时行为**。

## 1. 一间一格的空间模型

```text
应用（= 一个厅 = 一个房间服务实例 + 一份私有 SQLite）
  └─ 间（每间一张床 + 一块留给装饰物的预留位；一间占一格，一格自带一条竖走道）
       └─ 床位（容量由级表给出：117 → 150 → … → 9558，按需要自动伸缩）
            └─ 用户（匿名身份，持久认领一张床）
```

| 项 | 定义 |
| :--- | :--- |
| **格** | `CELL_W × CELL_H` 的矩形 = **一条竖走道**（左）+ **一间房**（右）。**行距就是 `CELL_H`** |
| **房** | **床** + **预留位** 并排（宽度 61 + 56 = 117） |
| **预留位** | 每间房留给装饰物的那块空地（`RESERVE_W = 56`）。它在可走性上**不可走** → 将来往里面放装饰物**永远不可能堵住街网**，也就不需要「阻挡集」这套东西 |
| **床脚前的横走道带** | 每格底部一条 56px 高的横走道，与竖走道交叉成街网（`isWalkable` 见 §4） |
| **行奇偶错位** | 床在房内**左右错位**：偶行靠本条竖走道那侧、奇行靠另一侧，错位量 = `RESERVE_W`。于是相邻两行看起来是交错排布，而不是队列 |
| **房间内部** | 床与预留位都**不是街**（不可走），步行只在走道上发生 |

**编号**：床号是**建成的先后**（第 1 级整片行优先编完，此后每一级只给新增外圈继续编），因此它**编码「年龄」，不编码方位**；级与级之间必然有一处空间跳变（改进办法见 `backlog.md` 的「外圈改蛇形编号」）。**显示值 = 内部编号 + 1**（`displayBedNoOf`），内部编号一律 0 起——协议、归属位图、数据库、命中判定全都用内部值。

**密度取舍**：一格一床意味着 iPhone 16 竖屏一屏约 2.3 格 × 4.6 行 ≈ **10 床**。比「每格塞多张床」的排法疏一倍多，这是「不压抑 + 每间有一块空地」的代价，也是「每间房有块空地」的前提。

## 2. 床位与格子规格

**世界单位就是 CSS 像素**（1 世界像素 = 1 CSS 像素）；位置允许出现半像素，**格子的常量一律取整**。

| 常量 | 值 | 为什么是这个值 |
| :--- | :--- | :--- |
| `ART_SCALE` | 0.5 | 素材像素 → 世界像素的固定比。**没有缩放**：1 世界像素 = 1 CSS 像素 |
| `BED_W` / `BED_H` | 61 / 100 | 素材墨迹 122×201 × 0.5（100.5 取整，丢 0.5px 不可见） |
| `AISLE` | 56 | 走道宽度 = 人高（113 × 0.5 ≈ 56.5）→ 走道里站得下一个人，也不会压到床 |
| `RESERVE_W` | 56 | 预留位宽度（= 一条走道宽）。它是「无边界个人房间」的那块空地，且**不可走**（§4） |
| `CELL_W` | 173 | 格宽 = `AISLE + BED_W + RESERVE_W` = 56 + 61 + 56：**一格 = 一条竖走道 + 一间房** |
| `CELL_H` | 156 | 格高 = `BED_H + AISLE` = 100 + 56：床 + 床脚前那条横走道（同时是行距） |
| `WALL_BODY` | 26 | 可走区从墙矩形四边**再向内缩 26px**。取值依据：**两张站立贴图里最宽的那张**（`girl_stand` 墨迹 97×113 → 世界 48.5 宽、**半宽 24.25**）+ 1.75 余量 → 小人不会压在墙上（贴墙走道有效宽 `56 − 26 = 30`，仍容得下一个人）。**上限也是硬的**：贴墙那条街列的节点在 `x = −28`、可走左界 = 墙矩形左沿 + `WALL_BODY` → 28 会让节点零余量。**将来出现更宽的贴图（披风、道具）必须重推这个值** |
| `WALL_WIDTH` | 3 | 墙带厚度（世界像素）。1.5px 的细线在手机上几乎看不见，这是「走到边缘看不见墙」的一半原因 |
| `OUTSIDE_MARGIN` | 56 | **墙外那一圈**：相机可以滚到墙外一条走道，于是手机上推到边缘也能看见墙外的底与那条墙带（否则墙永远贴着屏幕最外圈，看起来只是一条细线）。它**不属于厅**：不铺地板、不可走 |

**贴图规格不在本文**：空床 / 有主 / 男 / 女 / 睡痕各是哪张、两色渐变映射规则、素材许可，见 `../ui/DESIGN.md`「构建期要产出的变体」与 `../../public/sprites/LICENSE-wheatcloudsleep.txt`。几何这边只需要两条：**床的绘制锚点 = 床的左上角**（`positionOf`），**小人贴图的锚点 = 脚底中心**。

## 3. 级表与厅的边界

床位数不是一个固定配置，而是一个**随需要跳档的级**。一档的几何由**格**决定：一格 = 一条竖走道 + 一间房，行距 = 床高 + 床脚前横走道。

### 3.1 级表（唯一需要人工维护的配置）

| 级 | 行数 `R` | 每行床数 `C` | 容量 `C×R` | 床位区 `W×H` | `y:x` | 步长 |
| ---: | ---: | ---: | ---: | :--- | ---: | ---: |
| 1 | 9 | 13 | **117** | 2249 × 1404 | 0.624 | — |
| 2 | 10 | 15 | 150 | 2595 × 1560 | 0.601 | 1.28 |
| 3 | 12 | 18 | 216 | 3114 × 1872 | 0.601 | 1.44 |
| 4 | 14 | 21 | 294 | 3633 × 2184 | 0.601 | 1.36 |
| 5 | 17 | 25 | 425 | 4325 × 2652 | 0.613 | 1.45 |
| 6 | 20 | 29 | 580 | 5017 × 3120 | 0.622 | 1.36 |
| 7 | 23 | 34 | 782 | 5882 × 3588 | 0.610 | 1.35 |
| 8 | 27 | 39 | 1053 | 6747 × 4212 | 0.624 | 1.35 |
| 9 | 32 | 46 | 1472 | 7958 × 4992 | 0.627 | 1.40 |
| 10 | 37 | 54 | 1998 | 9342 × 5772 | 0.618 | 1.36 |
| 11 | 43 | 63 | 2709 | 10899 × 6708 | 0.615 | 1.36 |
| 12 | 51 | 74 | 3774 | 12802 × 7956 | 0.621 | 1.39 |
| 13 | 59 | 86 | 5074 | 14878 × 9204 | 0.619 | 1.34 |
| 14 | 69 | 101 | 6969 | 17473 × 10764 | 0.616 | 1.37 |
| 15 | 81 | 118 | **9558** | 20414 × 12636 | 0.619 | 1.37 |

尺寸公式（`CELL_W` / `CELL_H` 见 §2）：

```text
W(C) = 173·C      // 格宽 = 竖走道 56 + 床 61 + 预留位 56
H(R) = 156·R      // 格高 = 床高 100 + 床脚前横走道 56
```

三条不变量（单测逐条覆盖）：

1. **`R` 与 `C` 都单调不减** → 后一级的区域完全包含前一级 → 外圈生长不移动任何既有床；
2. **`y:x` 落在 0.60 ~ 0.63**（目标 0.618）→ 厅始终保持「宽大于高」的大厅形态；
3. **容量步长落在 1.25 ~ 1.52**（均值约 1.37）→ 类似 `ArrayList` 的扩容手感，既不频繁跳档也不浪费空间。

**第一级为什么是 117 而不是 99**：格宽 173 与格高 156 定死之后，`y:x = 0.618` 要求 `C/R ≈ 1.46`。整数行列里最接近 99 的解是 `9 × 13 = 117`（0.624）；`8 × 15 = 120`（0.481）与 `10 × 12 = 120`（0.751）都离大厅形态太远。

**上限为什么是 9558 而不是 9999**：再往上一档要么越过 9999（保持步长 ≥ 1.25 需要 ≥ 11948），要么只剩 `82 × 119 = 9758` 这种 **1.02 倍**的档——白发一档，等于把「扩容」退化成「每次加一点」。

**运行时**：`meta.bed_count` 必须**正好是级表里的一档**（读时归一后写回），升降级的判据与时机见 `10-hall-runtime.md` §8。

### 3.2 厅的边界：床位区 ⊂ 地板区 ⊂ 取景范围

三个矩形必须分清（混用会让墙看不见、或让相机永远贴死在屏幕最外圈）：

| 范围 | 定义 | 谁吃它 |
| :--- | :--- | :--- |
| **床位区**（格网） | 左上角锚在**世界原点**：`0 … W(C) × H(R)` | 床号 ↔ 位置。**它本身不是可走范围，也不是取景范围** |
| **地板区**（厅范围，`wallRegionOf`） | 床位区 + 四侧各一条走道 = `{ x: −56, y: −56, width: W + 112, height: H + 112 }` | **可走范围就是它**（再向内缩 `WALL_BODY`）；**墙画在它的边界上** |
| **取景范围**（`scrollRegionOf`） | 地板区 + 墙带 + **墙外一圈**（`OUTSIDE_MARGIN = 56`） | **相机可滚到的范围**。墙外那一圈不铺地板、不可走（用厅外底色）→ 推到边缘时看见的是「墙 + 墙外的一圈底」，而不是一条贴着屏幕最外圈的细线 |

| 项 | 值 |
| :--- | :--- |
| 四侧余量 | **各 56px（对称）**：左 / 上留在负坐标一侧，右 / 下在外侧 |
| 第 1 级 | 床位区 2249×1404 → 墙矩形 `[−56, 2305] × [−56, 1460]` = 2361 × 1516 |
| 最后一档（9558） | 床位区 20414×12636 → 墙矩形 `[−56, 20470] × [−56, 12692]` = 20526 × 12748 |
| 可走区内缩 | 再向内缩 `WALL_BODY = 26px`：小人不压到墙上（贴墙那条走道有效宽 30px，仍容得下一个人） |
| 墙的画法 | `WALL_WIDTH = 3px` 的墙带，沿**地板区的边界**画、且画在边界**之外**（不侵入地板） |

**为什么四侧都要余量、而且四侧相等**：床位区的四侧原本贴边（最上一排床的头、最左一列床的侧边直接抵着墙）。四侧各留一条走道之后，每张床四周都有可走的地板，**贴墙那一圈本身就是一条环形走道**。而原先的「右/下 = 下一级与本级之差」在每一档都不一样（第 1 级 316 / 156，末档 2277 / 1404）：厅看起来是歪的，相机还能拖进一大片没有床的空地板。现在**墙到最外圈床的距离在每一档都相同**。

**为什么左/上那条留在负坐标一侧**：床位区锚在原点不动，才能保证「**任何一次升级/降级都不移动既有床**」；把左 / 上余量放到 `x < 0` / `y < 0`，就不必平移整块床位，也不必改任何床号。

## 4. 布局契约（`src/shared/layout.ts`）

布局是**纯函数**，前端与厅服务引用同一份（没有场景文件，见 `architecture.md` §2.5）。对外契约：

| 函数 / 常量 | 输入 → 输出 | 说明 |
| :--- | :--- | :--- |
| `levelOf(index)` / `bedCountOf(index)` / `regionOf(index)` | 级号 → 几何 / 容量 / 床位区 | 床位区左上角锚在世界原点。索引越界夹到两端 |
| `displayBedNoOf(bedNo)` | 内部床号 → **显示床号**（`bedNo + 1`） | **唯一的显示换算点**：内部编号一律 0 起（协议、归属位图、数据库、`bedNoAt` 的入参与返回值、`cellOf` 全都不动），只有画在床角的数字与 HUD 那条「床号 N」吃它（`../ui/DESIGN.md` 的 `bed-number`） |
| `cellOf(bedNo)` | 床号 → `{ row, col }` | **建成顺序编号**（只吃行列数，**不吃像素**）：第 1 级整片行优先，此后每一级只给「新增外圈」按行优先继续编 |
| `positionOf(bedNo)` | 床号 → `{ x, y }`（世界像素） | 床的**绘制锚点**（左上角）。床在房内按**行奇偶左右错位**：偶行靠本条竖走道那侧、奇行靠另一侧，错位量 = `RESERVE_W` |
| `frontPointOf(bedNo)` | 床号 → `{ x, y }` | 床脚前那条横走道带的**中心点**；出生点与「走到床边再躺下」都用它 |
| `roomOf(bedNo)` / `reserveOf(bedNo)` | 床号 → 矩形 | 房间矩形（床 + 预留位）与**预留位**矩形。房间地面与预留位按两者绘制（固定色两档，见 `../ui/DESIGN.md`「地面梯次」）；将来的装饰物也吃 `reserveOf` |
| `bedNoAt(x, y, bedCount?)` | 世界像素 → 床号或空 | 命中判定（含行奇偶错位）。**不传 `bedCount` 按整张表（最高档）判定**；传当前床位数时，越过它的床不算床（降级后旧外圈不该再被点到） |
| `isWalkable(x, y, bedCount?)` | 世界像素 → boolean | 街网 = **街列**（每格一条竖走道）∪ **街行**（每格一条床脚前横走道带）∪ **贴墙那一圈环形走道**，再减去「墙矩形向内缩 `WALL_BODY`」以外的部分。**房间内部（床 + 预留位）不可走** |
| `wallRegionOf(index)` | 级号 → `{ x, y, width, height }` | **地板区（厅范围）** = 本级格网 + 四侧各一条走道（对称）。地板铺满它、墙带沿它的边界画、可走性以它（再内缩 `WALL_BODY`）为界 |
| `scrollRegionOf(index)` | 级号 → `{ x, y, width, height }` | **取景范围**（相机可滚到的矩形）= 地板区 + 墙带 + 墙外一圈 `OUTSIDE_MARGIN`。**它比厅大**：多出来的那一圈是墙外的底，用来让「墙」读成一个实体边界 |
| `nearestStreetPoint(point, bedCount)` | 点 → 点或空 | 离给定点最近的街网点：**客户端**点地面时吸附到街网（服务端只校验、不吸附）；服务端在降级后把落在区域外的位置拉回街网（那是恢复，不是对意图的吸附） |
| `STREET_BELT` / `streetPointAt` / `streetBandAt` / `streetBlockAt` / `streetBandCount` / `streetBlockCount` | 街网编号与坐标 | 街行（横走道带）× 街列（竖走道）的编号、节点坐标、某个点落在哪条街上、一个档里有几条。**几何只在这里定义**：寻路只按这套编号拼图（闭式解，见 `architecture.md` §2.6） |

**可走性与房间**：房间内部（床 + 预留位）**不是街**。于是「将来往预留位里放装饰物」**不可能堵住街网**，也就不需要阻挡集。

**升降级的几何语义**：铺满一级 = 床位区 + 四侧走道；**升一级只在外圈加床**（老床位的位置与床号都不变），**降一级 = 床位区收回到上一档**（挖掉的正是最大的那些床号），**地板与墙跟着一起收**。所以不需要「拆床」逻辑：**区域即真相**；被挖掉的那一圈落在**墙外**，要把人拉回街网的那条路径见 `10-hall-runtime.md` §8。

**必须成立的不变量**（单测逐条覆盖）：

1. `bedNo` 的位置与当前 `bedCount` **无关**：升级 / 降级都不改变任何既有床的位置；
2. 任意级的 `bedNo < capacity` 的床，位置在该级与更高一级完全相同；
3. **每张床左右各有 56px**（一侧是竖走道、一侧是预留位），**床脚前有 56px** 横走道带；
4. **墙四侧各距格网 56px，且四侧互相相等**；贴墙那一圈是**连通的环形走道**；**可走范围 = 地板区**（取景范围多出来的那圈墙外不可走、不铺地板）；
5. 街网连通：任两张床的前方走道之间都存在一条只走街网的路径；且街网是**完备网格**（任意街行 × 任意街列都是节点、每条街行横贯整厅、每条街列纵贯整厅）；
6. **房间内部（床 + 预留位）不可走**；
7. 编号在每一级内连续、全局连续（`0 … capacity−1`），降级砍掉的正是最大那些编号。
