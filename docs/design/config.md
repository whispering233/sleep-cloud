# 配置说明

## 1. 只有一个厅

| 项 | 值 | 说明 |
| :--- | :--- | :--- |
| 厅标识 | `main-1` | 房间服务实例名（`idFromName`）。**没有厅注册表、没有大区、没有多厅** |
| 布局版本 | `LAYOUT_VERSION`（如 `dorm-1`） | **几何是程序化生成的**，所以一致性校验的对象从「场景文件」变成「布局版本号」。客户端建连时必须在 `hello` 里带上它，不一致返回 `2003`（防止旧 bundle 连上新几何） |
| 床位数 | **运行时事实**，不是配置 | 由级表（§2）与 `meta.bed_count` 决定：114 ~ 9790 之间自动伸缩 |

**为什么没有厅注册表**：一个厅时，「厅在哪」不再是配置问题；真正需要人工维护的只剩级表（§2）。将来若真的要多厅，那时才需要注册表（见 `backlog.md`）。

## 2. 级表（唯一需要人工维护的配置）

| 级 | 行数 `R` | 每行床数 `C` | 容量 `C×R` | 像素尺寸 `W×H` | `y:x` | 步长 |
| ---: | ---: | ---: | ---: | :--- | ---: | ---: |
| 1 | 6 | 19 | **114** | 1455 × 936 | 0.643 | — |
| 2 | 7 | 23 | 161 | 1771 × 1092 | 0.617 | 1.41 |
| 3 | 8 | 26 | 208 | 2022 × 1248 | 0.617 | 1.29 |
| 4 | 9 | 29 | 261 | 2273 × 1404 | 0.618 | 1.26 |
| 5 | 11 | 36 | 396 | 2840 × 1716 | 0.604 | 1.52 |
| 6 | 13 | 42 | 546 | 3286 × 2028 | 0.617 | 1.38 |
| 7 | 15 | 49 | 735 | 3853 × 2340 | 0.607 | 1.35 |
| 8 | 18 | 58 | 1044 | 4550 × 2808 | 0.617 | 1.42 |
| 9 | 21 | 68 | 1428 | 5368 × 3276 | 0.610 | 1.37 |
| 10 | 25 | 81 | 2025 | 6381 × 3900 | 0.611 | 1.42 |
| 11 | 29 | 94 | 2726 | 7394 × 4524 | 0.612 | 1.35 |
| 12 | 34 | 110 | 3740 | 8658 × 5304 | 0.613 | 1.37 |
| 13 | 40 | 129 | 5160 | 10173 × 6240 | 0.613 | 1.38 |
| 14 | 47 | 152 | 7144 | 12004 × 7332 | 0.611 | 1.38 |
| 15 | 55 | 178 | **9790** | 14030 × 8580 | 0.612 | 1.37 |

尺寸公式（`⌊⌋` 为向下取整）：

```text
W(C) = 61·C + 4·(C−1) + 56·⌊C/4⌋      // 床宽 + 床间距 + 每 4 床一条竖走道
H(R) = 156·R                          // 床高 100 + 床脚前走道 56
```

三条不变量（由 §4 的几何常量与上表的单调性共同保证）：

1. **`R` 与 `C` 都单调不减** → 后一级的区域完全包含前一级 → 外圈生长不移动任何既有床；
2. **`y:x` 落在 0.604 ~ 0.643**（目标 0.618）→ 厅始终保持「宽大于高」的大厅形态；
3. **容量步长落在 1.26 ~ 1.52**（均值约 1.37）→ 类似 `ArrayList` 的扩容手感，既不频繁跳档也不浪费空间。

**第一级为什么是 114 而不是 99**：`y:x = 0.618:1` + 整数行列下 99 不可达（99 = 9×11 得 0.51:1，11×9 得 1.95:1，都离大厅形态太远）。114 = 6×19 是**最接近 99** 且比例正确的解（0.643）。

**上限为什么是 9790 而不是 9999**：下一级（64×207 = 13248）越过 9999，而整数行列凑不出 9999；9790 是 **≤ 9999 的最大级**。触顶后不再生长，躺床返回 `2002`。

## 3. 时间常量

| 常量 | 值 | 说明 |
| :--- | :--- | :--- |
| `GRACE_MS` | 60_000 | 断线宽限期。期内重连恢复原状态，超期按是否在床上分流 |
| `AUTO_SLEEP_MS` | 300_000 | 在床上无输入满 5 分钟自动转睡着（**显示态读取时推导**，由一个到期事件负责写库与广播） |
| `TICK_MS` | 100 | 位置推进与广播合并的**目标**周期。仅在有人走动时启用（内存循环，非持久唤醒） |
| `WALK_SPEED_PX_PER_S` | 130 | 走动速度（世界像素/秒）。**推进量按实际经过时间算**，节拍抖动只影响平滑度、不影响速度 |
| `TRACE_TTL_MS` | 43_200_000（12 小时） | **睡痕存活时长**，从「宽限到期时刻」起算。到期由**读取时推导**（服务端过滤 + 客户端按 `traceUntil` 自行淡出），不需要唤醒、不需要广播 |
| `DAILY_WAKE_UTC_HOUR` | 20 | 每日唤醒时刻（UTC 20:00 = 北京 04:00，低峰）。同时刻做两件事：**归属释放** + **缩级评估** |
| `BED_OWNERSHIP_TTL_MS` | 30 天 | 归属释放阈值（依据 `last_seen_at`）。**归属过期同样是可读取推导的**：判定「这张床能不能躺」时把过期归属当作无主 |
| `EMOTE_MS` | 2500 | 表情在世界内的显示时长。**只用于客户端推导过期**，服务端不记状态 |

**没有昼夜、没有厅时区**：`SLEEP_TRACE_CLEAR_HOUR`、厅 `timezone`、`owner_tz` 以及整套时区换算都已删除（见 `00-master-design.md`「在场与时间模型」）。

## 4. 几何常量

| 常量 | 值 | 为什么是这个值 |
| :--- | :--- | :--- |
| `ART_SCALE` | 0.5 | 素材像素 → 世界像素的固定比。**没有缩放**：线稿在 DPR 2~3 的手机上仍是下采样，比 1:1 更锐利 |
| `BED_W` / `BED_H` | 61 / 100 | 素材墨迹 122×201 × 0.5（100.5 取整，丢 0.5px 不可见） |
| `BED_GAP` | 4 | 视觉选择：床不贴在一起 |
| `AISLE` | 56 | 走道宽度 = 人高（113 × 0.5 ≈ 56.5）→ 走道里站得下一个人，也不会压到床 |
| `CORRIDOR_EVERY` | 4 | 每 4 床一条竖向走道（摊到每床 14px）。更密则厅碎、更疏则走动绕远 |
| `PITCH_X` / `PITCH_Y` | 65 / 156 | 列距 = 床宽 + 间距；行距 = 床高 + 床脚前走道 |
| `MAX_DPR` | 2 | 画布设备像素比上限。再高只是多花填充率，肉眼看不出 |

**世界单位就是 CSS 像素**（1 世界像素 = 1 CSS 像素）。位置允许出现半像素，渲染交给相机与 DPR 处理；**格子的常量一律取整**，避免图集与碰撞判定里出现小数。

## 5. 限制

| 项 | 值 | 说明 |
| :--- | :--- | :--- |
| `UPSTREAM_RATE_PER_SEC` | 5 | 每连接上行限流（条/秒），超出丢弃 |
| `NICKNAME_MAX_LEN` | 16 | 昵称长度上限（按字符计） |
| `CHAT_MAX_LEN` | 200 | 全局聊天消息长度上限（按字符计） |
| `CHAT_LOG_MAX` | 50 | 客户端本地保留的最近消息条数（只用于显示；服务端不存历史） |
| `POOL_SIZE` | 64 | 世界渲染的对象池大小。可见范围约 5 床 × 3.5 行（≈ 18 床）+ 邻接缓冲，64 足够覆盖两屏抖动 |

## 6. 密钥

| 名称 | 用途 | 存放 |
| :--- | :--- | :--- |
| `SESSION_SECRET` | 会话 cookie 的 HMAC 签名 | 平台密钥存储（`wrangler secret`），**不写入仓库** |

本地开发把它放进 `.dev.vars`（`cp .dev.vars.example .dev.vars`，该文件不进仓库）；**任何环境缺少该密钥都直接报错**，绝不静默使用可猜的密钥。

**这是对称密钥（HMAC），不是公私钥对**：同一把密钥既签名又验签，所以它只有一个要求——不外泄。谁拿到它就能伪造任意用户身份的会话 cookie。

**轮换的真实代价**：密钥一换，现有 cookie 全部验签失败 → 每个人都变成**新身份**，而他们原来的床仍绑在旧用户标识上，要等 30 天归属释放才回到可认领池。也就是说轮换 = 所有人（临时）丢床。因此第一版不做轮换。

## 7. 布局契约（`src/shared/layout.ts`）

布局是**纯函数**，前端与厅服务引用同一份（不再有场景 JSON，见 `architecture.md`）。对外契约：

| 函数 | 输入 → 输出 | 说明 |
| :--- | :--- | :--- |
| `levelOf(index)` | 级号 → `{ R, C, capacity }` | 超出上限时返回最后一档 |
| `bedCountOf(index)` | 级号 → 床位数 | 即 `capacity` |
| `regionOf(index)` | 级号 → `{ rows, cols }` | 该级的区域（左上角锚定，行列各自递增） |
| `cellOf(bedNo)` | 床号 → `{ row, col }` | **建成顺序编号**：第 1 级整片按行优先，此后每一级只给「新增外圈」按行优先编号 |
| `positionOf(bedNo)` | 床号 → `{ x, y }`（世界像素） | 床的绘制锚点 |
| `bedNoAt(x, y)` | 世界像素 → 床号或空 | 命中判定：该处不是床格时返回空 |
| `isWalkable(x, y)` | 世界像素 → boolean | 街网：横向走道带 ∪ 竖向走道带，且不在任何床的占用矩形内 |

**必须成立的不变量**（单测逐条覆盖）：

1. `bedNo` 的位置与当前 `bedCount` **无关**：升级/降级都不改变任何既有床的位置；
2. 任意级的 `bedNo < capacity` 的床，位置在该级与更高一级完全相同；
3. 街网连通：任两张床的前方走道之间都存在一条只走街网的路径；
4. 编号在每一级内连续、全局连续（`0 … capacity−1`），降级砍掉的正是最大那些编号。

## 8. 内容过滤数据

| 文件 | 内容 |
| :--- | :--- |
| 敏感词表 | 一行一词，随应用打包 |
| 干扰字符表 | `·（）【】！？《》￥` 等，匹配前剥离 |

**空白、零宽字符与大小写同样不影响匹配**（`傻 逼`、`傻`+零宽字符、`FUCK` 都会被命中）。剥离只作用于判定，不改写发出去的内容（打码除外）。

打码替换为**等长**的 `*`，因此聊天消息的长度与其余部分不受影响。第一版随包发布，不做热更新。

## 9. 前端可见配置

| 项 | 来源 |
| :--- | :--- |
| 当前床位数 `bedCount` | **厅下发**（快照与 `resize` 消息）——它是运行时事实，不是静态元信息 |
| 在线人数 `online` | **只在 WebSocket 里下发**（快照的 `hall.online`，以及 `join` / `leave` / `state`） |
| 布局版本 | 会话/元信息接口与快照各一份，供客户端自检 |
| 全部时间常量与几何常量 | **不下发**：前端引用同一份 `src/shared/` 常量，编译期内联 |
| 困倦度（明暗氛围）、睡痕过期 | **客户端本地推导**（前者由在厅人物的显示态算，后者由快照里的 `traceUntil` 算） |

## 10. 环境差异

| 环境 | 差异 |
| :--- | :--- |
| 本地开发 | 同一个厅，同样从第 1 级（114 床）开始；用本地密钥。需要造「厅满/升级/缩级」场景时，用脚本直接写 `meta.bed_count` 或批量认领床位 |
