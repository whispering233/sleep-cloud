# 后台管理面板（admin console）

**一句话**：运维面的**一个静态页 + 五个视图**——台账 / 黑名单 / 审计 / 举报 / 反馈，顶部四张统计卡。它不是产品界面，不套前台视觉令牌，也不引入前端框架。

**接口形态、鉴权与字段**见 `../api/30-api-admin.md`；本文只管**信息架构、版面、刷新时机与取舍**。

## 1. 定位与边界

| | |
| :--- | :--- |
| **是** | 同一个 Worker 子路由 `/admin` 下的静态页；只经 `/api/admin/*` 读写；单操作者 `admin` |
| **不是** | 前台 React 应用的一部分（不加载 Phaser、不连 WebSocket、不读前台令牌）；不是公开产品页；不是第二个部署 |
| **模板** | **不引入**后台模板（Tabler / AdminLTE / CoreUI / Pico 等）：它们要么带 Bootstrap（几十 KB + 自己的主题体系），要么引入新的构建链与许可约束。本页需要的只是「侧栏 + 表格 + 表单 + 抽屉」，用现有手写 CSS 就够；Tabler 的**信息架构**（侧栏分组、统计卡、空态、抽屉）作为参考，**不引入其代码与依赖** |
| **为什么可以手写** | 全站后台只有一个使用者、五个列表、四个统计数字；引入框架的长期维护成本大于它省下的样式 |

## 2. 信息架构

### 2.1 五个视图

| hash | 视图 | 数据来源 | 说明 |
| :--- | :--- | :--- | :--- |
| `#identities` | 访客台账 | `GET /identities` | **默认视图**。按最近出现倒序；可按 IP 精确反查、按昵称子串搜、**按 `userId` 精确查**；**点「身份」列**打开只读抽屉 |
| `#blocks` | 黑名单 | `GET /blocks` | 不分页；**封禁的唯一入口**（`POST /blocks`）与解封（`DELETE`）都在这里。`user` 行的「值」显示 `昵称 · userId`（读时现补），`ip` 行保持字面量 |
| `#audit` | 审计 | `GET /audit` | `id` 倒序分页；`user` 行同上述「值」列口径 |
| `#reports` | 举报 | `GET /reports` + `GET /reports/targets` | 上半张「谁被最多人举报」，下半张明细；两处都只读。当事人一律渲染成 `昵称 · userId`，可点开抽屉 |
| `#feedback` | 反馈 | `GET /feedback` | 用户主动提交的「反馈与建议」；只读，**不分已处理**（见 `130-feedback.md` §7）。「提交者」= `昵称 · userId`，可点开抽屉 |

**同一条展示规则**：只要一行的主语是「一个人」，就把**昵称与 `userId` 印在一起**，并可点开抽屉。理由很实在——昵称不唯一、可改、且 90 天后会被清空；`userId` 唯一、永不改，但它是运维认不出的随机串。只给一个，四种视图之间就对不上账。

**封禁只在 `#blocks` 一处**：台账抽屉、举报行、反馈行都**不放封禁按钮**。原因不是省事——封禁会关闭在线连接、写审计、可能误伤一片网络，这个动作只应发生在**看得见完整参数（kind / value / 时长 / 理由）**的那张表单里。台账与举报只负责「告诉你去封谁」，不负责执行。

### 2.2 路由

- 只用 **hash**（`#identities` 等），不用 History API、不做路径深链：页面是静态文件，`/admin/identities` 这类路径在生产会被平台资产处理掉，在 Vite 下会落进 SPA 回退。
- 初始无 hash → 落到 `#identities`；未知 hash → 替换成 `#identities` 并给一句 toast。
- `hashchange` 渲染对应视图；浏览器后退 / 前进天然可用。
- **不记住上次视图**：刷新回到默认台账。后台没有「恢复现场」的需求，多存一个键就多一个会过期的状态。

## 3. 统计卡

四张卡常驻在所有视图之上（滚动时随顶栏吸顶**只在宽屏**；窄屏留在页面顶部，不吸顶）。

| 卡 | 口径 | 为什么是这个口径 |
| :--- | :--- | :--- |
| **在线** | 厅对象内存里的**活连接数** | 与 `join` / `leave` / `state` 广播里的 `online` 同源；不去数台账的 `online` 列（那是逐行推导，贵且会与广播不一致） |
| **有主床** | `bed.owner_user_id` 非空**且归属未过期**（`last_seen_at` 在 `BED_OWNERSHIP_TTL_MS` 内） | 「实际有主的床」。过期但尚未被每日唤醒释放的行仍留在表里，直接 `COUNT(*)` 会把它们算进去，与「厅里还有多少空床」对不上 |
| **生效封禁** | `block.until_at` 为空（永久）**或** `until_at > now` | 与入场判定同一谓词（读取时推导），不数历史封禁 |
| **近 24 小时举报** | `report.last_at >= now − REPORT_DEDUP_MS` 的**行数** | 一行 = 一对 `(举报人, 被举报人)`；重复举报只加 `count`。行数答「昨晚有多少对人在起冲突」，`SUM(count)` 答「报了多少次」——卡片取前者，后者在举报视图里看 |

```json
{ "online": 37, "ownedBeds": 214, "blocks": 3, "reports24h": 5 }
```

**接口**：`GET /api/admin/stats`。一次请求，三条聚合查询 + 一次内存读数（`online` 不发 SQL）。**没有逐行读**，所以它比台账翻一页还便宜。

**刷新时机只有两处**：

1. **进入任一视图**（含首次登录后）——一次 `stats` + 该视图自己的第一页；
2. **封禁 / 解封成功之后**——重新拉 `stats` 与当前视图，让「生效封禁」当场变化。

**不做轮询、不做 SSE**：后台没有「实时盯着」的需求，而任何常驻循环都会让页面在没人看时继续计费。代价是「在线」在页面停留期间会变旧——顶栏标注「口径：进入视图时」，不假装实时。

## 4. 版面

### 4.1 宽屏（≥ 1024px）

```text
┌──────────┬──────────────────────────────────────────┐
│ 品牌     │ 顶栏：视图名 · 口径提示 · 刷新 · 登出      │
│          ├──────────────────────────────────────────┤
│ 台账     │ 统计卡 ×4                                 │
│ 黑名单   ├──────────────────────────────────────────┤
│ 审计     │                                          │
│ 举报     │  当前视图（表格 / 表单 / 两张表）          │
│ 反馈     │                                          │
└──────────┴──────────────────────────────────────────┘
```

- 侧栏固定宽 200px、`position: sticky`；当前项用底色 + 左侧 3px 竖条标记（不只靠颜色）。
- 正文最大宽 1200px，表格自己横向滚动（`overflow-x: auto`），**不为窄屏压缩列宽**。
- 顶栏与统计卡吸顶；视图内容不被吸顶层遮住（用 `scroll-margin-top` 或占位，不写死像素高度之外的值）。

### 4.2 窄屏（< 1024px）

侧栏折叠成**顶部横向标签条**（五颗胶囊，可横向滚动，当前项同样有可见标记），统计卡两列两行。后台允许「手机上凑合能用」：台账与审计主要看，封禁表单在手机上仍可完成（输入框与按钮 ≥ 44px）。

### 4.3 空态与反馈

- 每个列表都有**空态**（「还没有记录」/「没有匹配」），不是一张空表头。
- 写操作（封禁 / 解封）成功给一条 **toast**（3 秒，`aria-live="polite"`），失败给 `role="alert"` 的常驻条，直到下一次成功或手动关闭。
- 加载中：表格保留旧内容并降不透明度，**不清空**——清空会让页面在每次刷新时闪一下。

## 5. 台账详情抽屉

**只读**。从一个身份进入，回答「这个人在哪、最近从哪来、和谁同网络、被封过几次」。

| 区块 | 内容 |
| :--- | :--- |
| 概要 | `userId` / 昵称 / 首见 / 最近出现 / 最近 IP / 国家 / UA 哈希 / 当前床号 / 在线 |
| 当前封禁 | 命中时给 `kind` / 到期 / 理由；否则「未命中」 |
| 同一网络的其他身份 | `ipHistory`（最多 20 条），每条可继续打开详情 |
| 封禁 / 解封记录 | 针对该身份的审计（最多 20 条） |

- 用原生 `<dialog>` + `showModal()`（Chromium 100 支持；不依赖 Popover）。
- 出口：右上角「关闭」、`Esc`、点遮罩。**点遮罩要自己接一条 `click` 判断 `event.target === dialog` 才关**——`showModal()` 只给 `Esc`（close request），点遮罩**不会**自动关（Chromium 实测，所谓「`<dialog>` 已经给了」是错的）。
- 抽屉里**没有封禁按钮**：要封就带着 userId / IP 去 `#blocks` 填表单（见 §2.1）。
- 404（身份不存在）→ 抽屉内一行「查不到这个身份」，不关抽屉。其它非 200 仍显示「台账详情读取失败（状态码）」。

## 6. 文件与加载

| 项 | 决定 | 理由 |
| :--- | :--- | :--- |
| 文件 | `public/admin.html`（壳）+ `public/admin.css` + `public/admin.js` | 单文件 700+ 行内联脚本已经不可维护；拆开后样式与行为各自可读。**不建子目录**、不加构建步骤 |
| 脚本形态 | 经典 `<script defer>`（**不用 ES module**） | 少一次模块图解析、少一类 MIME/路径问题；后台不需要 tree-shaking |
| 依赖 | **零**：不引 CDN、不引字体、图标用内联 SVG | 后台被墙外 CDN 拖慢的代价比省下的代码大；字体用系统栈 |
| 语法检查 | 构建期对 `admin.js` 跑一次 `node --check` | 静态文件没有打包器，语法错误否则只能在浏览器里发现 |
| 缓存 | **沿用默认**（`max-age=0` + `must-revalidate` + ETag），**不加 `immutable`** | 后台是运维面，改动要立刻生效；`public/_headers` 只给 `/audio/*`、`/fun/*` 加长缓存 |
| 页面壳 | 仍然**不含任何数据**；登录前只显示登录表单 | 与 `30-api-admin.md` §1 的隔离前提一致 |

**不引入构建链**：没有 Tailwind、没有 bundler、没有 `npm run admin`。后台的样式量级（一张 CSS 文件）用不上这些。

## 7. 成本

| 动作 | 增量 |
| :--- | :--- |
| 打开 `/admin` | 1 次静态 HTML + 1 次 CSS + 1 次 JS（可缓存，默认协商） |
| 登录 | 1 次 `POST /login` + 1 次 `GET /stats` + 1 次当前视图第一页 |
| 切视图 | 1 次该视图请求 + 1 次 `stats`（举报视图多一次折叠表，共 3 次）；后台人工频率，可忽略 |
| 封禁 / 解封 | 1 次写 + 1 次 `stats` + 1 次当前视图 |
| 台账翻页 | 1 次列表 + 50 次床单行读 + 50~100 次封禁主键命中（见 `30-api-admin.md` §5.1） |
| 详情抽屉 | 1 次身份详情（含 ≤20 条网络关联 + ≤20 条审计） |

后台是人工频率，**不值得为它做缓存或去重**；真正的成本约束在厅对象（`architecture.md` §5）。

## 8. 已知代价

- **统计卡会变旧**：只在该视图进入与写操作后刷新，没有轮询。
- **不能从台账 / 举报直接封禁**：多一步「复制 userId 去黑名单」，换来封禁参数永远完整可见。
- **hash 不能指向某一条记录**：没有 `#reports/123`，分享链接只能到视图。
- **无权限分级**：单令牌、单操作者；第二个人出现时才需要账号与角色（`backlog.md`）。
- **无自动化回归**：后台没有 e2e（前台 e2e 已随 `main` 删除），判据只能手工 + `ui-verifier` 走（见 §9）。

## 9. 验收判据

| # | 判据 |
| :--- | :--- |
| 1 | 未登录访问 `/admin` 只见登录表单；登录失败给可见错误；登录成功进入 `#identities` |
| 2 | 五个 hash 都能直达；刷新保持当前 hash；未知 hash 落回台账并提示 |
| 3 | 窄屏（393×852）下五颗标签可点、表格可横向滚动、封禁表单可完成 |
| 4 | 封禁成功后 toast、统计卡「生效封禁」+1、黑名单出现新行；解封后反之 |
| 5 | 台账点「身份」打开抽屉，`Esc` / 遮罩 / 关闭都能退出；抽屉里没有封禁按钮；黑名单 / 审计 / 反馈的 `user` 行同样可点开 |
| 6 | 空列表显示空态；接口失败显示可重试的错误条，不清空已有内容 |
| 7 | `node --check public/admin.js` 通过；页面不加载任何第三方资源 |

## 10. 不做 / 推迟

| 项 | 原因 |
| :--- | :--- |
| 引入 Tabler / AdminLTE / CoreUI | 带框架与主题体系，收益（样式）小于长期维护成本；信息架构已借鉴 |
| 图表库 / 趋势图 | 四个数字够用；画趋势要保留时序，后台没有这个数据源 |
| 深色模式切换 | `color-scheme: light dark` 跟随系统；单独开关没有需求方 |
| 实时刷新（SSE / 轮询） | 会引入常驻连接或定时器；后台不需要盯屏 |
| 批量封禁 / 导出 CSV | 没有需求方；一次封一个，参数必须逐个看 |
| 在后台看聊天全文 | 服务端不存聊天；证据只在举报行里（`70-privacy-risk.md` §3） |
| 第二个操作者 / 角色 | 单令牌够用；出现第二个人再设计（`backlog.md`） |
