# 架构设计

## 1. 技术栈选型

| 层 | 选型 | 理由 |
| :--- | :--- | :--- |
| 部署形态 | **单个 Worker + 静态资源托管（同源）** | 同源 → 会话 cookie 自动随 WebSocket 握手发送 → 不需要令牌交换、不需要跨域配置。也不需要单独的静态站点项目 |
| 后端入口 | **Hono** | 路由/中间件/分组够用；**自带签名 cookie（HMAC SHA-256）**，正好是匿名会话所需，不用自己实现 HMAC；体积小；官方文档与模板广泛使用 |
| 房间服务 | 平台原生的**有状态对象**（Durable Object），类名 `Hall`，每个厅一个实例，`idFromName(hallId)` | 厅 = 强一致容器 = 一份私有 SQLite；单线程串行处理天然免疫并发分配冲突（256 张床不会重复分配） |
| 房间内持久化 | 对象自带的 **SQLite** | 嵌入式、单文件、事务型，与「一个对象一份私有库」完全匹配 |
| 前端 | **React + TypeScript + Vite + Tailwind**（**移动端优先**） | UI 小但会长（聊天、留言、装饰）；也贴合项目既定的 Tailwind 与细粒度组件要求。手机是主场景，竖屏窄幅下先定稿 |
| 世界渲染 | **PixiJS**（独立 canvas） | 图集、深度排序、批量渲染正是它的主业；这些我们全都要 |
| 本地开发 | 平台的本地运行时（`wrangler dev`） | 本地即可跑完整的对象 + SQLite + WebSocket |
| 不引入 | D1 / KV / R2 / 全栈同构框架 | 见 §5 与 `backlog.md` |

## 2. 架构理念

### 2.1 意图与事实分离

```
客户端：只发意图（我要去哪、我要躺哪张床、我说了什么）
服务端：定义事实（你在哪、哪张床属于谁、谁在说话）
```

这是整个架构的主轴。它同时解决三件事：反作弊无从下手的问题消失、视觉分歧无处产生、基于位置的规则（走到床边才能躺下）成立。

### 2.2 厅的边界就是数据库的边界

一个厅 = 一个对象 = 一份私有 SQLite。所有权威状态在同址，读写是本地操作，天然强一致、天然免锁。跨厅不存在事务需求（第一版没有任何真正跨厅的状态）。

### 2.3 渲染层是一个纯函数

```
状态快照（谁在哪、谁躺着、谁在说话） → 画出来
```

这条边界换来两个好处：

1. 渲染循环不触发前端框架重渲染（性能边界）
2. **渲染库可替换**：将来若真需要游戏引擎，只需重写这个纯函数，不动服务端、协议、数据模型

### 2.4 状态是时间戳的函数，而不是定时器的堆积

「睡痕」= 在床上 + 离线超过宽限期，可以由时间戳推导出来，不需要为每个用户挂一个定时器。**需要高频循环的只有位置推进**；需要“未来某刻唤醒”的只有几个到期事件。两者与平台约束的对应关系见 `10-hall-runtime.md` §4。

## 3. 分层与分包

| 层 | 职责 | 不允许做的事 |
| :--- | :--- | :--- |
| **前端世界层** | 渲染场景、小人、插值、点击命中 | 不计算权威位置；不写业务规则 |
| **前端 UI 层** | 入场、HUD、聊天、错误提示（DOM） | 不直接操作渲染层内部状态 |
| **Worker 入口层** | 路由、签名 cookie 签发与验签、静态资源回退、WebSocket 升级前的鉴权 | 不放业务状态；不直接读写 SQLite |
| **房间服务层** | 状态机、床位归属与占用、寻路、节拍推进、广播合并、到期事件调度、清理任务、内容过滤、限流 | 不做前端渲染；不做跨厅协调 |
| **共享层** | 协议消息类型、错误码、常量、场景数据类型 | **不依赖上面任何一层**（前端与后端都要引用它） |

包依赖链（单向，无环）：

```
共享层  ←  Worker 入口层  →  房间服务层
   ↑
前端（世界层 + UI 层）
```

## 4. 数据流

### 4.1 入场

```
浏览器 → Worker：读取会话 cookie（无则签发新的匿名会话）
       → Worker：返回 本人身份 + 所属大区 + 厅元信息（时区、场景标识、容量）
       → 浏览器：建立 WebSocket，握手时自动带上同源 cookie
       → 房间服务：验签 cookie → 比对场景标识 → 下发全量快照（含在线人数）→ 加入广播
```

### 4.2 一次走动

```
浏览器：点地面 → 发一条「我要去这一格」的意图
房间服务：校验目标格 → 服务端寻路 → 记录路径（存在连接上，不落库）
房间服务：按节拍推进 → 每 100 ms 把本周期所有位置变化合并成一条广播
浏览器：按收到的权威位置做插值渲染
```

### 4.3 一次躺下

```
浏览器：点空床 → 发「我要躺这张床」
房间服务：校验（床号合法 / 自己没在床上 / 床未被占用 / 该床属于自己或尚未被认领）
        → 认领归属（若尚未认领）→ 置为 在床上+清醒 → 写 SQLite → 广播
```

### 4.4 断线与睡痕

```
连接关闭 → 进入宽限期（60 秒，状态留在内存）
宽限内重连 → 恢复原状态（床、位置、对话都还在）
宽限超时 → 在床上：标记为睡痕（写 SQLite）；不在床上：离开（广播消失）
次日 → 清理任务把睡痕床位清空（保留归属）
30 天未出现 → 释放归属，床位回到可认领池
```

## 5. 平台约束与配额（官方文档核实）

### 5.1 免费计划配额

| 维度 | 免费额度 | 每日重置 |
| :--- | :--- | :--- |
| 房间服务请求 | 100,000 / 天（含 WebSocket 消息、持久唤醒触发） | UTC 00:00 |
| 房间服务活跃时长 | 13,000 GB-s / 天 | UTC 00:00 |
| SQLite 行读取 | 5,000,000 / 天 | UTC 00:00 |
| SQLite 行写入 | 100,000 / 天 | UTC 00:00 |
| SQLite 存储 | 5 GB（总量） | — |
| 外层 Worker 请求 | 100,000 / 天 | UTC 00:00 |
| **静态资源请求** | **免费且不限量** | — |
| Worker CPU | 10 ms / 次调用 | — |

**免费计划任一维度超额，该类操作直接失败**（不是降级）。Paid 计划最低 $5/月。

### 5.2 关键计费规则

| 计费与生命周期规则 | 影响 |
| :--- | :--- |
| **存在未完成的内存定时器时对象无法休眠**；未完成操作（含定时器）会阻止驱逐，阻止期间持续计费 | 高频循环只能在「正在工作」期间存在，用完必须立即清除；不能有常驻保底循环 |
| **内存定时器不持久**，对象驱逐后回调不再执行 | 「必须在未来某时刻发生」的动作只能用持久唤醒 |
| **云端计时不精确**（计时随 I/O 推进） | 位置推进量按实际经过时间计算，不假设固定帧间隔 |
| 每个对象只有**一个**持久唤醒槽位 | 多个到期时刻需自建调度器桥接 |
| **出站 WebSocket 消息不计费** | 我们的广播策略（只发变化 + 批量合并）在计费上正好最省 |
| 入站 WebSocket 消息按 **20:1** 折算成请求 | 上行意图几乎不消耗请求额度 |
| 协议层 ping/pong 与自动响应**不计费、不唤醒** | 心跳白拿 |
| 空闲且**可休眠**的对象不产生活跃时长 | 休眠是必需项，不是优化 |
| 活跃时长按**固定 128 MB** 分配量计费，与真实使用无关 | 节拍频率必须克制，不能常驻 |
| 每个 `setAlarm()` 计 1 行写入；删除也计行写入 | 调度器必须先比对再设置，避免重复写入同一时刻 |

### 5.3 容量换算

```
13,000 GB-s/天 ÷ 0.128 GB = 101,562 活跃秒/天 ≈ 28.2「对象活跃小时」/天
```

| 场景 | 消耗 | 占比 |
| :--- | :--- | :--- |
| 3 个厅 × 每晚活跃 8 小时 = 24 活跃小时 | 11,059 GB-s/天 | 85%（可行但吃紧） |
| 3 个厅 × 24 小时常驻活跃 | 33,178 GB-s/天 | 255%（会失败） |

**因此禁止**：常驻固定频率节拍、无人在线时仍保持对象活跃、唤醒时全表加载。

### 5.4 四条由此而来的硬约束

1. 必须使用平台的 **WebSocket 休眠机制**（把「活跃时长」从「连接生命周期」降到「代码实际执行时间」）
2. **位置节拍只在有人走动时存在，最后一个移动者停下就立即清除**；无人在线时不设任何持久唤醒 → 对象休眠 → 零成本
3. **唤醒时按需读行，绝不整表加载**（行读取是最容易被放大到超额的维度）
4. 心跳用平台的自动响应能力，不自建

## 6. 安全边界

| 边界 | 做法 |
| :--- | :--- |
| 会话 | 服务端签发的 HMAC 签名 cookie（HttpOnly）。**不接受客户端自报身份** |
| 连接 | WebSocket 升级前先验签；首条消息必须携带场景标识并与厅配置一致，否则断开且不转发任何房间消息 |
| 状态 | 位置、床位、清醒度全部由服务端计算。客户端上报的坐标一律不作为事实 |
| 内容 | 昵称与聊天走敏感词过滤（打码而非拦截）；上行限流 5 条/秒 |
| 传输 | 全程 HTTPS/WSS（平台默认），不同于参考项目裸 TCP 无加密的做法 |
| 昵称与性别 | 昵称做长度上限与控制字符剥离；**不信任客户端声明的任何属性** |

## 7. 第一版的已知取舍

| 取舍 | 代价 | 何时回头处理 |
| :--- | :--- | :--- |
| 匿名身份存在 cookie 里 | 清 cookie 即换身份，封禁只能延缓 | 需要真实保障时必须上登录，届时做身份升级与床位迁移 |
| 18 岁仅自述 | 不是核验 | 面向真实规模上线时 |
| 满员开新厅割裂社交 | 老用户见不到新人 | 有人真的住满时 |
| 不存聊天历史 | 无法事后取证、无法「看昨晚聊了什么」 | 出现真实需求时（见 backlog） |
