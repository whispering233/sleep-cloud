# 架构设计

## 1. 技术栈选型

| 层 | 选型 | 理由 |
| :--- | :--- | :--- |
| 部署形态 | **单个 Worker + 静态资源托管（同源）** | 同源 → 会话 cookie 自动随 WebSocket 握手发送 → 不需要令牌交换、不需要跨域配置。也不需要单独的静态站点项目 |
| 后端入口 | **Hono** | 路由/中间件/分组够用；**自带签名 cookie（HMAC SHA-256）**，正好是匿名会话所需；体积小 |
| 房间服务 | 平台原生的**有状态对象**（类名 `Hall`）。**整个应用只有一个实例**（`idFromName(HALL_ID)`） | 厅 = 强一致容器 = 一份私有 SQLite；单线程串行处理天然免疫并发分配冲突 |
| 房间内持久化 | 对象自带的 **SQLite** | 嵌入式、单文件、事务型，与「一个对象一份私有库」完全匹配 |
| 前端 | **React + TypeScript + Vite + Tailwind**（**移动端优先**；兼容基线 Chromium 100，见下方） | UI 小但会长（聊天、留言、装饰）；也贴合既定的 Tailwind 与细粒度组件要求。手机是主场景，竖屏窄幅下先定稿 |
| 世界渲染 | **Phaser 4.2.1**（独立 canvas，`Scale.NONE`，相机可拉远到 `0.175`、**上限 1× 不放大**；画布按 DPR ≤3 放大，**世界里的文字按同一个 DPR 栅格化**） | 图集与批量渲染、相机（缩放/跟随/死区/边界）、输入、tween 一站齐备；比自绘少写一套相机与输入 |
| **布局** | **共享纯函数**（`src/shared/layout.ts`） | 床号 ↔ 位置、区域、走道全部由**与床位数无关**的纯函数给出 → 自动伸缩不移动任何床；同一份函数被前端与房间服务引用 → 不存在「服务端认为不可走而客户端画得出」 |
| 本地开发 | 平台的本地运行时（`wrangler dev`，由 `npm run dev` 包一层并自动选端口） | 本地即可跑完整的对象 + SQLite + WebSocket |
| 不引入 | D1 / KV / R2 / 全栈同构框架 / 渲染用 Tilemap / 物理引擎（Arcade / Matter）/**寻路库**（phaser-navmesh / easystarjs / grid-engine） | 见 §2.5、§5 与 `backlog.md` |

**浏览器兼容基线 = Chromium 100。** 依据不是「尽量兼容老浏览器」，而是真实内核：夸克 / UC 这类定制内核把安卓端停在 Chromium 100（实测最新夸克 APK 的 `libwebviewuc.so` 内版本串 `100.0.4896.58`；同一库里 `showModal` 有、`showPopover`/`popover` 零命中，`toSorted` 没有而 `findLast`/`structuredClone` 有，与 ~100 完全吻合）。由此有三条硬约束：

- `build.target` 固定为 `chrome100`（Vite 默认是 `chrome111`；不钉死就可能在构建期引入 Chromium 100 解析不了的语法）。
- Chromium 114+ 才有的 API（Popover、`:popover-open`、`@starting-style`、anchor positioning 等）必须带降级路径，不允许裸调；CSS 新特性只能用「`@supports` 包住后仍可用」或纯装饰的写法。
- 降级路径的能力判断只允许出现在 `src/client/popover.ts` 一处，组件里不各写一份。

**Phaser 使用边界**（细节见 `20-layout.md` §2 与 `../ui/DESIGN.md`）：

| 用 | 不用 |
| :--- | :--- |
| `Scene` + `Camera`（`setBounds` + 自实现的死区与跟随：**按 dt 匀速靠近**，见 `../ui/DESIGN.md`「世界相机」） | 物理引擎（位置是服务端权威 + 客户端插值；**碰撞不做**，见 §7）；**Phaser 逐帧固定比例的 `startFollow`/`setLerp` 也不用**（首帧会按距离比例跳 20~33px，且帧率一变速度就变） |
| 地板用一块 `Graphics` 矩形（**明暗不在画布内做**，由整屏一层减光处理，见 `../ui/DESIGN.md`「三档色调」）；房间地面与预留位是每间房两块贴片 | `Tilemap` / `TilemapGPULayer`（地图是程序生成的，没有 Tiled 数据、没有地形类型；**碰撞不做**，见 §7） |
| 床/编号/我的床标记：**可视窗口 + 对象池**（普通 sprite 不裁剪，必须自己控制对象数） | `SpriteGPULayer`（单纹理且「填充一次后不再改」——床位的占用状态会变，不适合） |
| 命中判定：屏幕 → 世界 → 槽位的**纯函数**（可单测） | 每个对象 `setInteractive`（几十个对象手写命中反而更可控、可回放） |
| 世界里的文字（床号 / 名字 / 气泡）用 `Text` 对象，**贴图按画布 DPR 栅格化**（`Text.setResolution`）——文字是「离屏 canvas 贴图 + 相机 zoom 放大」，停在 1× 就会被放大采样而糊 | `BitmapText`（聊天内容是任意中文，得预烘整套字形或运行时造图集）；把气泡改成 DOM 叠加（世界走画布、界面走 DOM） |

## 2. 架构理念

### 2.1 意图与事实分离

```text
客户端：只发意图（我要去哪、我要躺哪张床、我说了什么）
服务端：定义事实（你在哪、哪张床属于谁、谁在说话）
```

这是整个架构的主轴。它同时解决三件事：反作弊无从下手的问题消失、视觉分歧无处产生、基于位置的规则（走到床边才能躺下）成立。

### 2.2 一份库就是整个世界

一个应用 = 一个厅 = 一个对象 = 一份私有 SQLite。所有权威状态在同址，读写是本地操作，天然强一致、天然免锁。**没有跨厅事务需求，因为只有一个厅**；将来若真要多厅（见 `backlog.md`），`bed` 表加一列厅标识或每厅一个对象实例即可。

### 2.3 渲染层是一个纯函数

```text
状态快照（谁在哪、谁躺着、谁在说话） + 布局函数 → 画出来
```

这条边界换来两个好处：

1. 渲染循环不触发前端框架重渲染（性能边界）
2. **渲染库可替换**：这条边界在本项目里已经兑现过一次（PixiJS → Phaser），服务端、协议、数据模型一行未动

### 2.4 状态是时间戳的函数，而不是定时器的堆积

「睡着」「睡痕」「归属过期」都可以由时间戳推导出来（见 `10-hall-runtime.md` §4.3），因此**不需要为每个用户挂定时器**。需要高频循环的只有位置推进；需要「未来某刻唤醒」的只剩三个到期事件；**需要用持久唤醒保证在某个时刻发生的事只有每日一次**（归属释放 + 缩级）。

这条理念在计费上有直接回报：睡着的人零下行流量、大厅无人走动时对象休眠、空厅零成本。

### 2.5 布局是纯函数

```text
bedNo → { row, col } → { x, y }        （与当前床位数无关；床位区锚在原点）
级号 → { rows, cols } → 床位区与容量
级号 → 地板区（wallRegionOf）       （本级格网 + 四侧各一条走道；地板铺满它、墙画在它的边界之外、可走性以它为准）
级号 → 取景范围（scrollRegionOf）   （地板区 + 墙带 + 墙外一圈；相机可滚范围）
世界像素 → 是否在地板区内的走道上
```

三件事都由共享纯函数给出，而不是由美术画的地图数据给出。带来三个结果：

1. **自动伸缩成立**：床位从 117 涨到 9558 都只是在**外圈**增加床位，既有床的位置不动（`20-layout.md` §3.1、§4 的不变量）
2. **两端一致**：服务端与客户端引用同一份函数，不会出现两边对「哪一格能走」的理解分歧
3. **没有场景文件**：不需要地图编辑器、不需要构建期读 JSON、不需要「一份数据两个读者」的同步机制

### 2.6 寻路是「算出来」的，不是「搜」出来的

```text
街网是完备网格：每条街行横贯整厅、每条街列纵贯整厅，任意「街行 × 街列」都是节点
→ 最短路 = 坐标曼哈顿距离（闭式），无搜索、无优先队列，代价与节点总数无关
```

`findPath` 在**共享层**（`src/shared/pathfinding.ts`），**房间服务与前端都引用它**（前端用它做自身外推，见 `30-movement-sync.md` §2.3）；两端各留 ≤2 条候选街，总共 ≤16 组算术；实测最坏偏差 52px（≈0.4s 步程），而出生点与「走到床边再躺下」这类**中线端点偏差为 0**。完备性假设由一条「护城河」测试守着（折线按 ≤8px 采样必须全程在街网）。

**因此不用任何寻路库**（Phaser 生态的 phaser-navmesh、grid-engine，或框架无关的 easystarjs）。三个理由：

1. **位置不对**：这些库是浏览器/画布语义（`Tilemap`、`Scene`），而寻路只跑在房间服务里；要在服务端用只能选 headless 分支，还要把 `rxjs` / `heap` 之类的依赖拉进服务端。
2. **会欠第二份几何真相**：三个库都要求把世界喂成二维数组 / Tilemap / 网格，而几何的唯一真源是共享纯函数（硬纪律 4）。喂一份网格就是第二份可走性，涨级/缩级/改布局时两者必须同步。
3. **买到的能力我们一个都不缺**：单厅、没有阻挡地形（房间内部不可走 → 装饰永远堵不住街，所以不需要阻挡集）、已决定不做碰撞（所以不需要多角色避让）。

**什么时候才回头**：街网不再是完备网格（走道被阻断、或分区真正隔开），或出现「代价地形」与真正的避让/排队需求。真到那时也**先改闭式解**（把拐点从「两端最近的两条街」换成对凸代价求极值，几行、零依赖），不够再写 A*（仍应是纯函数、仍在 `layout.ts` 的契约内）。

## 3. 分层与分包

| 层 | 职责 | 不允许做的事 |
| :--- | :--- | :--- |
| **前端世界层** | 相机与渲染（Phaser）、可视窗口与对象池、别人的位置插值、**自己的自身外推**、命中判定（纯函数）、**天气 Scene**（屏幕空间的雨层） | 不计算权威位置；不写业务规则；不做碰撞（允许重叠与穿过，见 §7） |
| **前端 UI 层** | 入场、HUD、聊天、错误提示（DOM + Tailwind）、**整屏页壳**（说明面板 / 求签 / 游戏 / 反馈共用 `.entry-overlay` 那一套） | 不直接操作渲染层内部状态 |
| **前端游戏页层** | 游戏页的列表与出口、舞台（`base` 等比 `scale`）、各条观赏物自己的 canvas / rAF（`src/client/games/`，**逐条动态 import**，首屏不载任何游戏代码） | **不 import 世界层、store、协议**；不发上行、不读本地存储；不占大厅画布 |
| **前端偏好与音频层** | 本地偏好（`localStorage` 的唯一门面）、天气与雨声两个独立开关、**雨声**（`AudioContext` → 两个 source 交叉 → 循环） | 不碰协议、不碰世界渲染；不进逐帧路径 |
| **Worker 入口层** | 路由、签名 cookie 签发与验签、静态资源回退、WebSocket 升级前的鉴权 | 不放业务状态；不直接读写 SQLite |
| **房间服务层** | 状态机、床位归属与占用、布局推导、寻路与节拍推进、广播合并、到期事件调度、宽限与睡痕、级表升降级、出生点、内容过滤、限流 | 不做前端渲染；不做跨厅协调（不存在） |
| **共享层** | 协议消息类型、**布局函数**、**寻路与位置推进**（`pathfinding.ts` / `movement.ts`，两端都要用）、常量（几何/级表/时间）、错误码、内容过滤词表、布局版本号 | **不依赖上面任何一层**（前端与后端都要引用它） |

包依赖链（单向，无环）：

```text
共享层  ←  Worker 入口层  →  房间服务层
   ↑
前端（世界层 + UI 层）
```

目录对应：

```text
src/shared/   协议、布局、寻路与位置推进、常量、错误码、内容过滤、布局版本号
src/client/   世界层（world/）+ UI 层（components/、styles/）+ 游戏页层（games/，逐条动态 import）+ 客户端偏好、天气与音频（prefs.ts、weather.ts、audio.ts）
src/hall/     房间服务层
src/worker/   入口层
public/       静态资源（重着色后的图集、雨声 WAV、词表）
```

**雨声不走 Phaser 的 `this.sound`**：`SoundManager` 的价值在于「用 Loader 载素材 + 统一的播放 API」，而这里只有一个音频、懒加载（`fetch` → `decodeAudioData`），还要做「早播小循环 → 主循环」的双 source 交叉淡化。接进 Phaser 会把音频绑到世界层的生命周期上：世界层是懒加载块，而 `load.audio` 会让首帧等那次下载。所以它是 UI 层旁边的独立小模块：一个 `AudioContext`、两个 `AudioBufferSourceNode`、每路一个 `GainNode`（1 s 交叉淡化要两个），对外只有 `setRain(on)` 与 `unlock()`。

## 4. 数据流

### 4.1 入场

```text
浏览器 → Worker：读取会话 cookie（无则签发新的匿名会话）
       → Worker：返回 本人身份 + 昵称是否已设置 + 形象 + 18 岁自述位 + 布局版本号
       → 浏览器：建立 WebSocket，握手时自动带上同源 cookie
       → 房间服务：验签 cookie → 比对布局版本 → 【厅满则先升级一级】
       → 房间服务：算出生点 → 下发全量快照（含床位数、归属位图、在线人数）→ 加入广播
```

### 4.2 一次走动

```text
浏览器：点地面 → 发一条「我要去这个世界像素点」的意图
房间服务：判定目标在街网上（否则 3006）→ 街网寻路 → 记录路径（存在连接上，不落库）
房间服务：按节拍推进 → 每 100 ms 把本周期所有位置变化合并成一条广播
浏览器：按收到的权威位置做插值渲染；**自己那一份用外推**（同一份共享寻路 + 同一速度按时间推进，收到自己的 `pos` 就重锚且**只许向前**收敛，见 `30-movement-sync.md` §3.2）
```

### 4.3 一次躺下

```text
浏览器：点空床 → 发「我要躺这张床」
房间服务：校验（床号在床位数内 / 自己不在床上 / 床无占用 / 床无主或归属已过期）
        → 认领归属（若无行则 INSERT，否则覆盖）→ 置为 在床上+清醒 → 广播 bed 然后 state
```

### 4.4 断线与睡痕

```text
连接关闭 → 写 last_seen_at（唯一落地的东西）→ 床上的人排一次宽限到期；地上的人立刻广播 leave
宽限到期 → 在床上：标记为睡痕（写 SQLite，updated_at = 宽限到期时刻），广播 state
         不在床上：无事发生
重连（不论隔了多久）→ 从**床位行**还原状态：lying / asleep / trace 一律回到原状态
归属释放（30 天，每日唤醒）→ 行改成 empty，睡痕随之消失
```

**没有内存宽限记录**：曾经有一份（位置与路径），删了——对象空闲约 10 秒就休眠，被驱逐时连 `close` 事件都不给，于是它**几乎从不生效且无法预测**。睡痕本身也没有 TTL，它跟归属同寿（30 天）。

客户端那一侧（与上面四行互补，不是同一件事）：**它不等平台把 `close` 事件送到**——手机切屏后 socket 常常只是变成一条死连接。它按需探活（回到前台 / 网络恢复 / 发了意图 1.5 秒没有任何关于自己的下行）并在超时后自行重连（退避 1→2→4→8→15 秒），重连成功后一律以新的 `snapshot` 为准。详见 `../api/20-api-ws.md` §5.1。

### 4.5 床位伸缩

```text
入场前：已用床数 ≥ 本档容量的 75%（与出生点同一套谓词）且未触顶 → 升一级：写 meta、广播 resize（新床全是无主空床）
每日：最外一圈全部无主且无占用 且 已用率 < 50% → 降一级：写 meta、广播 resize
归属释放（每日，UTC 20:00）：一条 UPDATE 清掉 30 天未出现的归属 → 每张床一条 bed
读 meta：床位数不在级表里（级表被改过之后的残留）→ 归一后写回，否则地板按一档画、可躺的床按老数字算
```

## 5. 平台约束与配额（官方文档核实）

### 5.1 免费计划配额

| 维度 | 免费额度 | 每日重置 |
| :--- | :--- | :--- |
| 房间服务请求 | 100,000 / 天（含 WebSocket 消息、持久唤醒触发） | UTC 00:00 |
| 房间服务活跃时长 | 13,000 GB-s / 天 | UTC 00:00 |
| SQLite 行读取 | 5,000,000 / 天 | UTC 00:00 |
| SQLite 行写入 | 100,000 / 天 | UTC 00:00 |
| SQLite 存储 | 5 GB（总量） | — |
| 外层 Worker 请求 | 100,000 / 天 | UTC 00:00 |
| **静态资源请求** | **免费且不限量** | — |

**免费计划任一维度超额，该类操作直接失败**（不是降级）。Paid 计划最低 $5/月。

### 5.2 关键计费规则

| 计费与生命周期规则 | 影响 |
| :--- | :--- |
| **存在未完成的内存定时器时对象无法休眠**；未完成操作（含定时器）会阻止驱逐，阻止期间持续计费 | 高频循环只能在「正在工作」期间存在，用完必须立即清除；不能有常驻保底循环 |
| **内存定时器不持久**，对象驱逐后回调不再执行 | 「必须在未来某时刻发生」的动作只能用持久唤醒 |
| **云端计时不精确**（计时随 I/O 推进） | 位置推进量按实际经过时间计算，不假设固定帧间隔 |
| 每个对象只有**一个**持久唤醒槽位 | 多个到期时刻需自建调度器桥接 |
| **出站 WebSocket 消息不计费** | 广播策略（只发变化 + 批量合并）正好最省 |
| 入站 WebSocket 消息按 **20:1** 折算成请求 | 上行意图几乎不消耗请求额度 |
| 协议层 ping/pong 与自动响应**不计费、不唤醒** | 心跳白拿 |
| 空闲且**可休眠**的对象不产生活跃时长 | 休眠是必需项，不是优化 |
| 活跃时长按**固定 128 MB** 分配量计费，与真实使用无关 | 节拍频率必须克制，不能常驻 |
| 每个 `setAlarm()` 计 1 行写入；删除也计行写入 | 调度器必须先比对再设置，避免重复写入同一时刻 |

### 5.3 容量换算

```text
13,000 GB-s/天 ÷ 0.128 GB = 101,562 活跃秒/天 ≈ 28.2「对象活跃小时」/天
```

| 场景 | 消耗 | 占比 |
| :--- | :--- | :--- |
| 1 个厅 × 每晚活跃 8 小时 | 3,686 GB-s/天 | 28% |
| 1 个厅 × 24 小时常驻活跃 | 11,059 GB-s/天 | 85%（可行但吃紧） |
| 1 个厅 × 整月不休眠 | — | **会撞上限，因此必须避免常驻循环** |

**因此禁止**：常驻固定频率节拍、无人在线时仍保持对象活跃、唤醒时全表加载。

### 5.4 四条由此而来的硬约束

1. 必须使用平台的 **WebSocket 休眠机制**（把「活跃时长」从「连接生命周期」降到「代码实际执行时间」）
2. **位置节拍只在有人走动时存在，最后一个移动者停下就立即清除**；无人在线时不设任何持久唤醒 → 对象休眠 → 零成本
3. **唤醒时按需读行，绝不整表加载**（行读取是最容易被放大到超额的维度）
4. 心跳用平台的自动响应能力，**不自建常驻心跳**（100 人 × 20s 会让对象永远等不到 10 秒空闲 → 整夜不休眠）；只做「可疑时才发」的探活，见 `../api/20-api-ws.md` §5.1

**单次调用的 CPU 预算口径不一致**：平台文档在两处分别给出「每次调用的 CPU 时间 10 ms」与「处理器墙钟上限 30 秒 / 15 分钟」。**按保守值 10 ms 设计**，实测校准（见 `10-hall-runtime.md` §14）。

### 5.5 风控台账的成本增量

风控与反馈台账（`identity` / `block` / `admin_audit` / `report` / `feedback`）同一份厅库，增量全部落在**已有的那一批操作上**，不新开路径：

| 事件 | 增量 |
| :--- | :--- |
| 一次页面加载（`/api/me`） | **+2 行读**（封禁判定最多两个索引命中）。该调用本来就会唤醒厅对象（厅满判定），所以**没有新增唤醒** |
| 一次成功入场（`hello`） | **+1 行写**（`identity` UPSERT，与已有的 `last_seen_at` 写并列） |
| 一次反馈提交 | **+1 次索引计数 + 1 行写**。人工触发，但每人每日上限 5 条（`130-feedback.md` §5） |
| 后台一次读写 | 人工频率，可忽略 |
| 每日唤醒 | **+5 条清理语句**，不新开唤醒 |

**不引入新绑定**：没有 D1、没有 KV、没有第二个有状态对象。理由与代价见 `70-privacy-risk.md` §6。

## 6. 安全边界

| 边界 | 做法 |
| :--- | :--- |
| 会话 | 服务端签发的 HMAC 签名 cookie（HttpOnly）。**不接受客户端自报身份** |
| 连接 | WebSocket 升级前先验签；首条消息必须携带布局版本并与服务端一致，否则断开且不转发任何房间消息 |
| 状态 | 位置、床位、清醒度全部由服务端计算。客户端上报的坐标一律不作为事实；目标点不在街网上直接拒绝，**不做静默吸附** |
| 内容 | 昵称与聊天走敏感词过滤（打码而非拦截）；上行限流 5 条/秒 |
| **来源与封禁** | 来源（IP / 国家 / UA 哈希）由 **Worker 读平台头并写入内部头**，与身份头同一套信任模型（客户端伪造的值会被覆盖）；封禁入库与踢连接都在厅对象里完成；台账与黑名单**永不下发给任何客户端** |
| 传输 | 全程 HTTPS/WSS（平台默认） |
| 昵称与外观 | 昵称做长度上限与控制字符剥离；外观由 `user_id` 派生，**不信任客户端声明的任何属性** |

## 7. 第一版的已知取舍

| 取舍 | 代价 | 何时回头处理 |
| :--- | :--- | :--- |
| 匿名身份存在 cookie 里 | 清 cookie 即换身份，封禁**只能延缓**。IP 维度补上了一半，但共享 NAT 会误伤、切流量即绕过 | 需要真实保障时必须上用户持有型凭据（passkey / 登录），届时 L1 不变、只加凭据（见 `70-privacy-risk.md` §2、`backlog.md`） |
| 18 岁仅自述 | 不是核验 | 面向真实规模上线时 |
| 世界缩放只有拉远 | 拉到下限时同屏约 190 个床位（1× 时约 10 张），对象数与填充率都涨；大厅（第 7 档以上）拉到下限也看不全整厅 | ①真机实测帧率（环境见 `test.md`）②低端机不够就先抬 `ZOOM_MIN` 回 0.5，或拉远时先砍预留位那一片 |
| **渲染性能未实测** | 可视窗口 + 对象池的对象数约 **80**（每张床多了房间地面与预留位两块贴片；本地软件渲染下已量过，不代表真机）。画布按 DPR 3 渲染，**填充率是 DPR 2 的 2.25 倍** | 基准设备（iPhone 16）上实测帧率（环境见 `test.md`） |
| 床位数自动伸缩 | 升级会让大厅变大（区域矩形变化），**但不移动任何既有床** | 级表步长若明显不合适就改表（改表需递增布局版本号） |
| 睡痕跟归属活 30 天 | `hello` 那次全量快照里的睡痕条目最多 ≈ 近 30 天活跃人数（每条约 76 字节；2000 人约 150 KB） | 条目数过千时改「快照 + 增量广播」（`backlog.md`） |
| 不存聊天历史 | 无法事后取证、无法「看昨晚聊了什么」 | 出现真实需求时（见 `backlog.md`） |
| **不做碰撞** | 两个小人可以重叠、可以相向穿过（没有占用格、没有让路）；走道宽 56px、小人半宽 24.25px，真做碰撞就得配占用格 + 让路 + 死锁兜底，而每拍按人查邻接与「睡着的人零成本」直接冲突 | 出现「人一多，重叠看着难受」的真实反馈时（见 `backlog.md`）。**不要**用渲染层「同格错位」的折中：那会让画出来的位置 ≠ 权威位置 |
