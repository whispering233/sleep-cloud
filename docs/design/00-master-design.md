# 总体设计：云上睡眠大厅

## 1. 一句话

浏览器打开就是一个宿舍式睡眠大厅：**每个用户在大厅里有一张属于自己的床，躺下时小人睡在床上，睡不着的人可以在厅里走动、看见别人、和别人说话。**

## 2. 核心循环

```
打开网页 → 匿名入场（不需要注册）→ 看见厅里的床位和别人
        → 走到一张空床边躺下（该床从此属于我）→ 睡着 / 睡不着躺着
        → 睡不着时起身走动、看别人、聊天
        → 关掉网页 → 床上留下「睡痕」，第二天早上消失
```

第一版只验证这条循环。**任何不服务于这条循环的功能都不做**（见第 9 节）。

## 3. 空间模型

```
大区（= 一个厅 = 一个独立的房间服务 + 一份独立数据库）
  └─ 床位（固定槽位，容量 256）
       └─ 用户（匿名身份，持久认领一张床）
```

| 决定 | 内容 |
| :--- | :--- |
| 厅的形态 | **宿舍式单厅**：一张大房间里排满床位，彼此可见。不是「私人房间 + 公共大厅」 |
| 大区划分 | **3 个大区**，每个大区一个厅：亚洲、欧洲、美洲 |
| 容量 | 每厅 256 床 |
| 满员怎么办 | 开新厅（手动加配置），老用户不动 |
| 串门 | 第一版不做（见 backlog） |

**为什么是宿舍而不是单间**：产品要满足的是「睡不着时来看看别人」。单间模式下进来一个人也看不见，核心情绪当场消失。宿舍模式还带来一个副产品——**别人看到那张床会知道那是谁的位置**，「我的床位」成为情感资产。

**已知副作用**（记录，不解决）：满员开新厅后，新厅的人是全新的一批，老用户再见不到新人。这与「宿舍室友」的稳定性相反。解决办法是厅间迁移/串门，属于过度设计，第一版接受该副作用。

## 4. 身份与床位归属

| 决定 | 内容 |
| :--- | :--- |
| 身份 | **匿名 deviceId**：首次访问由服务端签发一个签名 cookie，内含用户标识 |
| 昵称来源 | **用户在入场层自己输入**（没有登录、没有第三方资料、没有默认名）；昵称随会话存在签名 cookie 里，**不是从数据库查出来的** |
| 改名时机 | 只在入场层、**建立连接之前**。因此协议不需要「名字变更」消息；代价是已连接的其他人要等自己下次进入才看到新名字 |
| 注册 | **不做**。深夜失眠的人不会注册，保留匿名是门槛设计 |
| 升级通路 | 将来要跨设备/永久昵称时，把匿名标识升级绑定登录方式，床位跟着迁移，数据模型不重做 |
| 年龄 | 入场时**「我已满 18 岁」自述 + 一次点击**。这是法律免责表述与后续分区字段，**不是核验** |
| 认领时机 | **第一次躺下时认领**（不是入场时分配）。点哪张空床就躺哪，天然实现了「在空床里挑」 |
| 归属 vs 占用 | **归属**持久绑定用户，30 天未出现才释放；**占用**表示此刻床上有人/有睡痕 |
| 别人能用我的床吗 | **不能，永远不能**。空床很多，这条不造成摩擦，但让「我的床位」成为真实私人物品 |
| 重名 | **允许**。显示时一律带床号（「12 号床 小明」），歧义由此消除，省掉重名检查 |

## 5. 在场与时间模型（半持久）

### 5.1 状态机

三个**正交维度**，服务端是唯一真源：

| 维度 | 取值 |
| :--- | :--- |
| 位置 | `ROAMING`（不在床上）/ `IN_BED` |
| 清醒度 | `AWAKE` / `ASLEEP`（仅在 `IN_BED` 时有意义） |
| 连接 | `ONLINE` / `GRACE`（断线宽限中）/ `OFFLINE` |

派生显示态：

| 位置 | 清醒度 | 连接 | 别人看到 | 占床 | 能聊天 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| ROAMING | — | ONLINE | 站着/走动的小人 | 否 | 是 |
| ROAMING | — | GRACE / OFFLINE | 不显示 | 否 | — |
| IN_BED | AWAKE | ONLINE | 睁眼躺着（失眠的人的真实状态） | 是 | 是 |
| IN_BED | ASLEEP | ONLINE | 闭眼睡着 | 是 | 否 |
| IN_BED | 任意 | OFFLINE | **睡痕**（更暗、更低饱和） | 是 | — |

**睡痕不是第四种姿势，而是「IN_BED + OFFLINE」这个组合的显示名。**

### 5.2 转移规则

| 触发 | 前置 | 结果 |
| :--- | :--- | :--- |
| 点地面 | IN_BED | **自动起身**（释放占用，保留归属）→ 走过去。一条命令完成，少点一次 |
| 点地面 | ROAMING | 走过去（新目标覆盖当前路径；目标为当前格则原地不动） |
| 躺下 | ROAMING，且该床属于自己或尚未被人认领 | **先走到该床旁，再躺下**（一条意图完成两段动作），同时认领归属（若尚未认领） |
| 无输入满 5 分钟，或手动睡着 | `IN_BED + AWAKE` | `IN_BED + ASLEEP` |
| 说话 / 表情 | `IN_BED + ASLEEP` | **自动醒**后处理，不报错 |
| 起床 | IN_BED | ROAMING（站在床边） |
| 断线 | 任意 | GRACE（宽限 60 秒） |
| 宽限超时 | IN_BED | `ASLEEP + OFFLINE`（睡痕），占床保持 |
| 宽限超时 | ROAMING | 离开，小人消失 |
| 宽限内重连 | 任意 | 恢复原状态 |

**为什么躺在床上断线一律转睡痕**（哪怕断线前睁着眼）：「躺下」这个动作本身就是「我要睡了」的声明。这样就不必为「躺着但清醒且离线」单独定义一个状态，状态机少一整个分支。

### 5.3 归属与占用的生命周期

| 事件 | 占用 | 归属 |
| :--- | :--- | :--- |
| 首次躺下 | 占用 | 认领 |
| 起身 | 释放 | 保留 |
| 断线超宽限（在床上） | 保持（睡痕） | 保留 |
| 次日睡痕清理 | 释放（床变空） | 保留 |
| 30 天未出现 | — | **释放**，床回到可认领池 |

**关键区分：睡痕清理 ≠ 释放归属。** 睡痕消失后床是空的，但仍是你的；30 天不出现才是真的失去它。

### 5.4 昼夜与时间

| 决定 | 内容 |
| :--- | :--- |
| 昼夜来源 | **跟随厅的固定时区**，不是用户本地时间。厅是共享空间，物理上只能有一片天空；「我们一起在同一片夜里」是产品的情绪核心 |
| 多时区怎么办 | 靠**多开分时区的厅**解决，而不是让每个人看见不同的天空 |
| 用户本地时区 | 只用于与个人有关的时间：睡痕清理时刻、晚安提示、睡眠记录归属哪一晚 |
| 服务端时间轴 | 永远使用 UTC 时间戳。**不为用户时区分裂出多套定时机制** |

## 6. 交互模型

| 决定 | 内容 |
| :--- | :--- |
| 走动方式 | **点击目标格，服务端推进**。客户端只发意图，服务端自己按格寻路、按节拍推进位置并广播权威值 |
| 目标设备 | **移动端优先**。手机是主场景（躺在床上、单手、竖屏、弱网、随时锁屏），桌面是次场景 |
| 输入方式 | 只有点击/点按。**不依赖 hover、不依赖右键、不依赖键盘**。键盘快捷键可以有，但不得成为完成任何动作的唯一方式 |
| 移动端特有约束 | 触摸目标尺寸、安全区（刘海/手势条）、软键盘遮挡输入框、页面进入后台后连接可能被挂起 |
| 为什么不用键盘实时控制 | 手机没有键盘；高频上报会撞上单房间服务的吞吐上限；而且客户端上报坐标会让服务端失去真相 |
| 客户端预测 | 允许——客户端可对自己那一个小人做乐观预测，与服务端权威值不符时平滑纠正。**预测值不是事实** |
| 第一版动作集合 | 走动（点地面）、躺下（点空床）、起床、睡着、全局聊天、私聊、表情 |

**意图 vs 事实**（这是架构级纪律）：

- **客户端发意图**：我想去 (x,y)、我要躺 3 号床
- **服务端定事实**：你在 (x,y)、3 号床被你占着

一旦让客户端上报坐标并当作事实，基于位置的规则全部失效（走到床边才能躺下、距离语义、治理取证），而且没有任何真值可以纠偏。

## 7. 视觉

| 项 | 决定 |
| :--- | :--- |
| 视角 | **正俯视带轻微俯角**（不做等距斜 45°）——后者需要 8 方向行走精灵与复杂遮挡排序，成本翻几倍 |
| 屏幕适配 | **移动优先的响应式**：先在竖屏窄幅下定稿，再向上适配桌面。不是「先做桌面然后适配手机」 |
| 风格 | **单色线稿 + 夜晚色调**。白天：浅底深线；夜晚：深蓝底白线。反白只需换配色，不重画资源 |
| 点睛色 | 只留 1–2 个暖色（床头灯的暖黄光晕、睡着时的呼吸起伏） |
| 为什么不用像素风 | 高饱和像素风会让一个失眠大厅变得吵闹；线稿与「失眠、克制、安静」的气质同步，且美术工作量可控 |
| 世界渲染 | Canvas/WebGL（**PixiJS**）——500+ 绘制对象下 DOM 会被 style recalc 与遮挡排序拖死 |
| UI 渲染 | **DOM**。聊天、HUD、入场、错误提示全部走 DOM，canvas 只负责世界 |
| 场景数据 | 手写 JSON（`beds` / `decorates` / `backgrounds` + `guid`），第一版不做编辑器 |
| 床位可见状态 | 由**归属**与**占用**两个正交维度派生，轮廓取梯次（亮线 > 暖灯 > 淡色 > 无）：床上有占用者 → 亮线；无占用且是自己的床 → 暖灯色；无占用且是别人的床 → 淡色；无主 → 不画。名字**只在床上有占用者时**才画（睡痕更暗） |

**关键性能边界**：位置插值跑在渲染循环里，**不触发前端框架重渲染**。这条边界破了，几百个小人会把框架拖死。

**界面最小集**：入场层（昵称 + 18 岁自述）、世界层、HUD（自己昵称/床号/大区/在线人数）、**常驻聊天层**（核心动作，不进二级菜单）、错误反馈层。没有「手机」隐喻、没有设置页——那些是为了在游戏画面里塞 UI 而发明的容器，网页不需要。

## 8. 状态同步

| 决定 | 内容 |
| :--- | :--- |
| 模型 | **纯事件增量**：仅在进入/重连时发一次全量快照，之后只发变化事件 |
| 为什么不做周期性全量纠偏 | WebSocket 跑在 TCP 上，消息可靠且有序，不会静默丢包——需要纠偏的问题根本不存在。而每 5 秒给 256 人发全量快照约 2.5 MB/s 持续下行，纯属为不存在的问题付费 |
| 广播节拍 | 位置推进按节拍进行；每 100 ms 把这一周期内所有位置变化**合并成一条**消息广播 → 下行消息数与人数的平方无关 |
| 静止的人 | 不产生任何下行流量。**睡着的人零成本**——这是「睡眠大厅」在计费上的天生优势 |
| 消息格式 | JSON。消息量小（10 条/秒量级），可读性价值远大于节省的字节 |
| 心跳 | 使用平台的 WebSocket 自动响应能力（协议层 ping/pong 不唤醒休眠、不产生计费） |
| 上行限流 | 每连接 5 条/秒，超出丢弃。第一版唯一的治理措施 |

## 9. 第一版范围

**做**：走动、躺下、起床、睡着、睡痕、全局聊天、私聊、表情、HUD、内容过滤、上行限流、睡痕每日清理、30 天归属释放。

**不做**（已记入 `backlog.md`）：聊天历史持久化、共处时长展示（数据已在存）、跨厅串门、自动扩厅、装饰床位、床头留言、关灯、音频/白噪音、设置页、手机隐喻、地图编辑器、举报与封禁（协议预留错误码）、D1。

## 10. 内容安全（第一版底线）

| 项 | 决定 |
| :--- | :--- |
| 昵称过滤 | 敏感词命中 → 拒绝并提示改名（不粗暴断线） |
| 聊天过滤 | **打码而非拦截**：命中词循环替换为 `*` 后照常转发。硬拦截会让发送者意识到被审查并试探绕过；打码让对话继续，攻击者拿不到反馈 |
| 干扰字符 | 匹配前剥离 `·（）【】！？《》￥` 这类插入字符，防止 `傻·逼` 绕过 |
| 词表 | 静态文件随应用打包（平台包大小限制 64 MiB，词表远小于此） |
| 限流 | 上行 5 条/秒 |
| 错误码 | 协议中**预留**风控码位（禁言/封禁/限流/昵称违规/内容违规），避免第二版改协议 |
| 18 岁自述 | 入场一次点击。**必须承认：这不是核验，只是「不是裸奔」** |

## 11. 平台约束（决定了很多设计）

来自 Cloudflare 官方文档，逐条约束了上面的设计：

| 约束 | 对设计的影响 |
| :--- | :--- |
| 一个房间服务 = 一个单线程对象，软上限约 1,000 请求/秒 | 一厅一对象；广播必须批量合并；不能高频全量广播 |
| 每个对象自带一份私有 SQLite | **厅的边界就是数据库的边界**，不需要跨厅事务 |
| 免费计划每天只有有限的「对象活跃时长」额度 | **休眠不是优化，是必需**；不能有固定频率的常驻节拍；只在有事发生时才唤醒 |
| 存在未完成的内存定时器时对象**无法休眠**，且阻止驱逐期间持续计费 | 高频循环必须在不需要时立即清除；不能有「保底心跳式」的常驻循环 |
| 内存定时器**不持久**（对象驱逐后回调不执行） | 凡「必须在未来某时刻发生」的动作必须用持久唤醒，不能用内存定时器 |
| 云端计时**不精确** | 位置推进量按实际经过时间计算，而不是按拍数；客户端按服务端时间戳插值 |
| 每次调用的 CPU 预算很小（免费计划保守按 10 ms 设计） | 服务端推进必须在少量移动者下工作，不能一次处理 256 人 |
| 出站 WebSocket 消息不计费；入站消息按 20:1 折算 | 我们的「只发变化」+「批量合并」结构在计费上正好是最省的 |
| 每个对象同一时刻只能有一个持久唤醒（alarm） | 所有「必须在未来某时刻执行」的事件**共用一个槽位**，由一个到期事件调度器桥接 |
| 静态资源请求免费且不限量 | 前端资源托管不占用每日请求额度 |
| 唤醒时全表读取会放大「行读取」计费 | **唤醒时按需读行，不全表加载** |
