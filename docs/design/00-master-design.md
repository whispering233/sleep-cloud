# 总体设计：云上睡眠大厅

## 1. 一句话

浏览器打开就是一个睡眠大厅：**每个用户在大厅里有一张属于自己的床**，躺下时小人睡在床上，睡不着的人可以在厅里走动、看见别人、和别人说话。

**只有一个大厅**，床位随人来人往自动变多变小（114 ~ 9790）。没有大区、没有昼夜、没有缩放。

## 2. 核心循环

```text
打开网页 → 匿名入场（昵称 + 18 岁自述）→ 看见一屏的床位与人
        → 走到某张空床边躺下（该床从此属于我）→ 睡着 / 睡不着躺着
        → 睡不着时起身走动、看别人、聊天
        → 关掉网页 → 床上留下「睡痕」（12 小时后自动消失）
```

第一版只验证这条循环。**任何不服务于这条循环的功能都不做**（见 §9）。

## 3. 空间模型

```text
应用（= 一个厅 = 一个房间服务实例 + 一份私有 SQLite）
  └─ 床位（容量由级表给出：114 → 161 → … → 9790，按需要自动伸缩）
       └─ 用户（匿名身份，持久认领一张床）
```

| 决定 | 内容 |
| :--- | :--- |
| 厅的形态 | **一个宽矩形大厅**（`宽:高 ≈ 1.618:1`，即 `y:x = 0.618:1`）：床阵 + 规则街网（每行床脚前一条横向走道 + 每 4 床一条竖向走道） |
| 床位密度 | 床 61×100.5 世界像素、床间距 4、行距 156 → **iPhone 16 竖屏一屏约 5 床 × 3.5 行 ≈ 17 床** |
| 床位伸缩 | 级表跳档（类似 `ArrayList` 扩容，步长约 ×1.37）：床不够才扩，**只在外圈加床，老床位一动不动**；外圈没人要了则缩 |
| 只有一个厅 | 没有大区、没有厅列表、没有切厅。入口只有「昵称 + 18 岁自述」两项 |
| 满员怎么办 | 触顶（9790 张全被认领）→ `2002`「厅满了」。这是理论边界，不是运维事件 |
| 为什么不做多厅 | 多厅会立刻带出「选哪个厅 / 能不能串门 / 厅间社交割裂」三个问题；单厅 + 自动伸缩一次性消掉它们 |

**已知副作用**：床位编号按「建成的先后」分配（先内圈后外圈），所以号大的床在厅的外围。用户看到的是「这个厅在往外长」——这是可接受的隐喻，也是「老用户的床永远不动」这条硬要求的必然结果。

## 4. 身份与床位归属

| 决定 | 内容 |
| :--- | :--- |
| 身份 | **匿名 deviceId**：首次访问由服务端签发一个签名 cookie，内含用户标识 |
| 昵称来源 | **用户在入场层自己输入**（没有登录、没有第三方资料、没有默认名）；昵称随会话存在签名 cookie 里，**不是从数据库查出来的** |
| 改名时机 | 只在入场层、**建立连接之前**。因此协议不需要「名字变更」消息；代价是已连接的其他人要等自己下次进入才看到新名字 |
| 外观 | **由 `user_id` 派生**（`boy` / `girl`），不提供选择入口，同一个用户永远同一个外观 |
| 注册 | **不做**。深夜失眠的人不会注册，保留匿名是门槛设计 |
| 升级通路 | 将来要跨设备/永久昵称时，把匿名标识升级绑定登录方式，床位跟着迁移，数据模型不重做 |
| 年龄 | 入场时**「我已满 18 岁」自述 + 一次点击**。这是法律免责表述，**不是核验** |
| 认领时机 | **第一次躺下时认领**（不是入场时分配）。点哪张空床就躺哪，天然实现了「在空床里挑」 |
| **一人一床** | 一旦认领，**不能再认领第二张**（服务端返回 `3007`，客户端给可见提示）。想换床 = 先等 30 天归属释放（「换床」已记入 `backlog.md`）。重访时靠**床号 + 我床暖标记**回到自己那张 |
| 出生点 | **编号最小的「无主空床」前方走道**：新人落在已有住户中间（30 天释放留下的坑会被新人补上），而不是被丢在没有住户的尾部 |
| 归属 vs 占用 | **归属**持久绑定用户，30 天未出现才释放；**占用**表示此刻床上有人/有睡痕 |
| 别人能用我的床吗 | **不能，永远不能**。空床很多，这条不造成摩擦，但让「我的床位」成为真实私人物品 |
| 重名 | **允许**。显示时一律带床号（「12 号床 小明」），歧义由此消除，省掉重名检查 |

## 5. 在场与时间模型

### 5.1 状态机

三个**正交维度**，服务端是唯一真源：

| 维度 | 取值 |
| :--- | :--- |
| 位置 | `ROAMING`（不在床上）/ `IN_BED` |
| 清醒度 | `AWAKE` / `ASLEEP`（仅在 `IN_BED` 时有意义） |
| 连接 | `ONLINE` / `GRACE`（断线宽限中）/ `OFFLINE` |

派生显示态：

| 位置 | 清醒度 | 连接 | 别人看到 | 占床 | 能聊天 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| ROAMING | — | ONLINE | 站着/走动的小人 | 否 | 是 |
| ROAMING | — | GRACE / OFFLINE | 不显示 | 否 | — |
| IN_BED | AWAKE | ONLINE | 睁眼躺着（失眠的人的真实状态） | 是 | 是 |
| IN_BED | ASLEEP | ONLINE | 闭眼睡着 | 是 | 否 |
| IN_BED | 任意 | OFFLINE（未过 TTL） | **睡痕**（更暗、更低饱和） | 是 | — |

**睡痕不是第四种姿势，而是「IN_BED + OFFLINE」这个组合的显示名。**

### 5.2 转移规则

| 触发 | 前置 | 结果 |
| :--- | :--- | :--- |
| 点地面 | IN_BED | **自动起身**（释放占用，保留归属）→ 走过去。一条命令完成，少点一次 |
| 点地面 | ROAMING | 走过去（新目标覆盖当前路径；目标即当前点则原地不动） |
| 躺下 | ROAMING，且该床无主（或归属已过期）且无占用（或只剩过期睡痕） | **先走到该床旁，再躺下**（一条意图完成两段动作），同时认领归属（若可认领） |
| 无输入满 5 分钟，或手动睡着 | `IN_BED + AWAKE` | `IN_BED + ASLEEP` |
| 说话 / 表情 | `IN_BED + ASLEEP` | **自动醒**后处理，不报错 |
| 起床 | IN_BED | ROAMING（站在床边） |
| 断线 | 任意 | GRACE（宽限 60 秒） |
| 宽限超时 | IN_BED | `ASLEEP + OFFLINE`（睡痕），占床保持 |
| 宽限超时 | ROAMING | 离开，小人消失 |
| 宽限内重连 | 任意 | 恢复原状态 |
| **睡痕满 12 小时** | IN_BED + OFFLINE | 睡痕消失（**推导，不写库不广播**）：床回落为「有主空床」，别人可以躺 |

**为什么躺在床上断线一律转睡痕**（哪怕断线前睁着眼）：「躺下」这个动作本身就是「我要睡了」的声明。这样就不必为「躺着但清醒且离线」单独定义一个状态，状态机少一整个分支。

### 5.3 归属与占用的生命周期

| 事件 | 占用 | 归属 |
| :--- | :--- | :--- |
| 首次躺下 | 占用 | 认领 |
| 起身 | 释放 | 保留 |
| 断线超宽限（在床上） | 保持（睡痕） | 保留 |
| 睡痕满 12 小时 | 释放（床变空，**推导**） | 保留 |
| 30 天未出现 | — | **释放**，床回到可认领池（每日唤醒里批量清行） |

**关键区分：睡痕消失 ≠ 释放归属。** 睡痕过期后床是空的，但仍是你的；30 天不出现才是真的失去它。

**两个「过期」都是读取时推导**：判定「这张床能不能躺」时，过期的睡痕视为无占用、过期的归属视为无主（`../db/schema.md` §6）。写入只发生在别人真的躺上去、或每日唤醒清行的时候。

### 5.4 时间与光照

| 决定 | 内容 |
| :--- | :--- |
| **昼夜** | **取消**。用户白天起床之后没有任何场景可做，明暗切换反而会破坏「深夜陪伴」的产品语义 |
| **时区** | **整个概念删除**：服务端不存、不接收、不使用任何时区信息（没有厅时区、没有用户时区、没有按人区分的时间语义） |
| 三种时间机制 | 持久唤醒（宽限到期 / 自动睡着 / 每日唤醒）、内存循环（位置节拍）、**读取时推导**（睡着、睡痕、睡痕过期、归属过期）——职责不重叠，详见 `10-hall-runtime.md` §4 |
| 每日唤醒 | **UTC 20:00（北京 04:00，低峰）**：归属释放（30 天）+ 缩级评估。用户侧不可感知 |
| 服务端时间轴 | 一律 UTC 时间戳。**不为用户分裂出多套定时机制** |
| **光照** | 没有昼夜，但有氛围：**全厅困倦度**（睡着 + 睡痕 占在厅人数）驱动**地板底色**在 `primary` 与 `primary-dim` 之间缓动（约 1.5 秒）。床与小人的墨色不变——线稿可读性恒定，不会出现「暗到看不清人」 |

**为什么氛围由「困倦度」而不是时钟驱动**：一个随时间周期变化的明暗会被读成「昼夜替身」，正是要取消的东西；而「大家都睡下了，灯就慢慢暗下去」是**这个厅自己的事实**，语义上属于陪伴，不属于天空。

## 6. 交互模型

| 决定 | 内容 |
| :--- | :--- |
| 走动方式 | **点目标点，服务端在街网上寻路并推进**。客户端只发意图，服务端自己按节拍推进位置并广播权威值 |
| **缩放** | **取消**。世界固定比例（素材 ×0.5），单指拖拽平移，点自己 = 相机回中。理由：一般 2D RPG 也不缩放界面；缩放带来的拟合、夹取、旋屏重算等问题远多于收益 |
| **导航** | **床号常显在每一张床上**（没有缩放之后它是世界里唯一的导航线索）+ 我的床有暖色标记 + HUD 显示我的床号。玩家按编号自己走过去 |
| 目标设备 | **移动端优先**。手机是主场景（躺在床上、单手、竖屏、弱网、随时锁屏），桌面是次场景 |
| 输入方式 | 只有点击/点按与拖拽。**不依赖 hover、不依赖右键、不依赖键盘** |
| 名字显示 | 名字是身份信息，不是陪伴信息。床（位置稳定）上的名字**始终显示**；漫游者**默认不显示**，点中才弹出**唯一一个**名字气泡 |
| 选中态 | 点中小人或床上的人 → 成为**选中对象**：弹出名字气泡 + 作为私聊目标。一个概念服务两件事 |
| 客户端预测 | 允许——客户端可对自己那一个小人做乐观预测，与服务端权威值不符时平滑纠正。**预测值不是事实** |
| 第一版动作集合 | 走动、躺下、起床、睡着、全局聊天、私聊、表情 |

**意图 vs 事实**（架构级纪律）：

- **客户端发意图**：我想去这个世界像素点、我要躺 3 号床
- **服务端定事实**：你在 (x,y)、3 号床被你占着

一旦让客户端上报坐标并当作事实，基于位置的规则全部失效（走到床边才能躺下、距离语义、治理取证），而且没有任何真值可以纠偏。

## 7. 视觉

| 项 | 决定 |
| :--- | :--- |
| 视角 | **正俯视带轻微俯角**（不做等距斜 45°）——后者需要 8 方向行走精灵与复杂遮挡排序，成本翻几倍 |
| 屏幕适配 | **移动优先的响应式**：先在竖屏窄幅下定稿，再向上适配桌面。基准设备 iPhone 16（393×852 / DPR 3） |
| 风格 | **单色线稿 + 夜色调（只有一套配色）**。素材来自 `WheatCloudSleep`（MIT, © 2022 WheatBox）：空床、两人躺姿、两个站立小人共 5 张母图；**构建期做两色渐变映射**（黑线 → 墨色三档、白填充 → 纸色），生成 6~8 张变体 |
| 点睛色 | 只留**一个**暖色：**「这是我的床」的标记**；地板与墙是程序化的（没有装饰素材） |
| 为什么不用像素风 | 高饱和像素风会让一个失眠大厅变得吵闹；线稿与「失眠、克制、安静」的气质同步 |
| 世界渲染 | **Phaser 4.2.1**：地板用 `TileSprite`（1 个绘制调用铺满整厅），床/床号/标记用**可视窗口 + 对象池**（同屏约 60 个对象，与厅规模无关），**不用 Tilemap**（地图是生成的） |
| 墙 | **地板与墙都画在「下一级的矩形」上**（最外圈的床四周因此仍有走道；最高级用理论下一档 64×207），沿边界画**一条等宽线**（没有环带填充——程序化几何里不存在 `blocked` 环带）。无缩放之后左右墙是否在屏内取决于屏宽 |
| UI 渲染 | **DOM**。聊天、HUD、入场、错误提示全部走 DOM，canvas 只负责世界 |
| 场景数据 | **没有场景文件**：床号 ↔ 位置、区域、可走性全部由共享纯函数给出（`config.md` §7） |
| 床位可见状态 | 由**归属**与**占用**两个正交维度派生，两个维度各走一条通道：**占用用颜色**（有人 → `line` 12.0:1 / 睡痕 → `trace` 4.2:1 / 空床 → `claimed` 3.1:1）；**归属用线型**（无主虚线、有主实线）；**「是我的」用一个独立的暖灯色小标记**。**床号常显**；名字只在床上有占用者时画，且自己的名字不画 |
| 氛围光照 | 全厅困倦度 → 地板底色在 `primary` ⇄ `primary-dim` 之间缓动（§5.4） |

**关键性能边界**：位置插值跑在渲染循环里，**不触发前端框架重渲染**。这条边界破了，几百个小人会把框架拖死。

**界面最小集**：入场层（昵称 + 18 岁自述）、世界层、HUD（**我的床号 + 在线人数**）、**常驻聊天层**（核心动作，不进二级菜单）、错误反馈层。没有「手机」隐喻、没有设置页、没有厅列表——那些是为了在游戏画面里塞 UI 而发明的容器，网页不需要。

## 8. 状态同步

| 决定 | 内容 |
| :--- | :--- |
| 模型 | **纯事件增量**：仅在进入/重连时发一次全量快照，之后只发变化事件 |
| 为什么不做周期性全量纠偏 | WebSocket 跑在 TCP 上，消息可靠且有序，不会静默丢包——需要纠偏的问题根本不存在 |
| 广播节拍 | 位置推进按节拍进行；每 100 ms 把这一周期内所有位置变化**合并成一条**消息广播 → 下行消息数与人数的平方无关 |
| 静止的人 | 不产生任何下行流量。**睡着的人零成本**——这是「睡眠大厅」在计费上的天生优势 |
| 消息格式 | JSON。消息量小（10 条/秒量级），可读性价值远大于节省的字节 |
| 心跳 | 使用平台的 WebSocket 自动响应能力（协议层 ping/pong 不唤醒休眠、不产生计费） |
| 上行限流 | 每连接 5 条/秒，超出丢弃。第一版唯一的治理措施 |
| **本地推导** | 睡痕过期（按快照里的 `traceUntil`）、困倦度（由在厅人物显示态算）、位置插值（按 `pos.ts`）——三件都不需要服务端参与 |

## 9. 第一版范围

**做**：走动、躺下、起床、睡着、睡痕（12 小时 TTL）、全局聊天、私聊、表情、HUD（床号 / 在线人数）、内容过滤、上行限流、**床位自动伸缩（外圈生长 + 每日缩级）**。

**不做**（已记入 `backlog.md`）：聊天历史持久化、共处时长展示、装饰床位、床头留言、音频/白噪音、设置页、手机隐喻、地图编辑器、举报与封禁（协议预留错误码）、明暗氛围之外的任何光照系统、多厅/串门/换厅。

## 10. 内容安全（第一版底线）

| 项 | 决定 |
| :--- | :--- |
| 昵称过滤 | 敏感词命中 → 拒绝并提示改名（不粗暴断线） |
| 聊天过滤 | **打码而非拦截**：命中词循环替换为 `*` 后照常转发。硬拦截会让发送者意识到被审查并试探绕过；打码让对话继续，攻击者拿不到反馈 |
| 干扰字符 | 匹配前剥离 `·（）【】！？《》￥` 这类插入字符，防止 `傻·逼` 绕过 |
| 词表 | 静态文件随应用打包（平台包大小限制 64 MiB，词表远小于此） |
| 限流 | 上行 5 条/秒 |
| 错误码 | 协议中**预留**风控码位（禁言/封禁/限流/昵称违规/内容违规），避免第二版改协议 |
| 18 岁自述 | 入场一次点击。**必须承认：这不是核验，只是「不是裸奔」** |

## 11. 平台约束

完整清单与换算见 `architecture.md` §5。三条对设计影响最大的：

| 约束 | 对设计的影响 |
| :--- | :--- |
| 存在未完成的内存定时器时对象**无法休眠**，阻止期间持续计费 | 位置节拍只在有人走动时存在，最后一个移动者停下就清除；**没有常驻循环** |
| 内存定时器**不持久**、云端计时**不精确** | 「必须发生」的动作走持久唤醒；推进量按实际经过时间算，客户端按时间戳插值 |
| 出站 WebSocket 消息**不计费**，入站按 20:1 折算 | 「只发变化 + 批量合并」在计费上最省；睡着的人零成本 |
