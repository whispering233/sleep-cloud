# 端云位置同步（移动的时延、推断与验收）

> 一句话：**位置是可以算出来的量，不是必须观测的量**；每一端只需要知道「从哪一点、什么时刻、沿哪条折线、以什么速度」。
> 本文只定义**移动的同步规格**：谁承担时延、画面与真值的关系、重锚规则、别人的滞后、验收口径与已知代价。
> 几何见 `20-layout.md`，服务端运行时见 `10-hall-runtime.md`，协议字段见 `../api/20-api-ws.md` §4.7 / §6。

## 0. 术语（与本项目的其它「延迟」区分开）

| 用 | 不用 | 说明 |
| :--- | :--- | :--- |
| 单向时延（`oneWay`） | 延迟、latency、ping/2 | 单程传输时间 ≈ RTT/2。**分析量**：不进代码、不做常量、不做测量 |
| 真值（`truth`） | 权威坐标、真实位置 | 服务端在 `pos.ts` 时刻的位置/状态；与「画面」相对 |
| 画面（`render`） | 外推点、显示位置 | 实际画出来的那一点。**只有它进渲染**，真值不进渲染 |
| 领先量（`lead`） | 预测量、外推量 | 画面领先真值的时间量；名义值 = **快照那一刻的单向时延**（不是常量） |
| 倒退（`regress`） | 回弹、rubber band | 一次重锚让画面往回走的像素数。**定稿：恒为 0** |
| 漂移（`drift`） | 不同步、延迟差 | 同一个动作在两个人屏幕上显示时刻之差。**不设硬门槛** |

## 1. 问题定义

### 1.1 三个时刻（不可消除）

```text
t0              我按下（意图产生）
t0 + oneWay     世界知道（服务端受理、其余人可能开始看到）
t0 + RTT        我收到世界的第一条确认（关于自己的 pos）
```

`oneWay` 不可消除：包要走，光要走。所以「我的画面从哪一刻起步」只有三种解，区别只是**谁承担误差**：

| 选择 | 我的画面 | 代价落在 |
| :--- | :--- | :--- |
| 按 `t0` 起步（**本项目**） | 按下去立刻走 | 世界：别人看到我领先事实 `oneWay` |
| 按 `t0 + oneWay` | 按下去静止 `oneWay` 才动 | 我（手感坏） |
| 按 `t0 + RTT`（等回执） | 静止一个 RTT | 我（手感更坏） |

**定稿：世界承担。** 我的画面从 `t0` 起步、**永不倒退**；别人看到我领先半个 RTT。

### 1.2 考核哪几个量

四个量（分类取自 Savery & Graham, NetGames 2011 转述的「按交互上下文给要求」；`50ms` 只作量级参考，不当合同数字）：

| 量 | 定义 | 我们的门槛 |
| :--- | :--- | :--- |
| 本地反馈（interactivity lag） | 本地动作 → 本地显示 | **硬性**：0 额外帧 |
| 倒退（regress） | 画面往回走的像素 | **硬性**：0px |
| 漂移（local / global drift） | 我的动作 / 他的动作在两个人屏幕上的显示时刻差 | **软性**：恒定、单调、无台阶；上限 `oneWay + 一拍` |
| 顺序一致（ordering） | 同一批动作在不同客户端上的先后 | **不涉及**：本项目没有并发判定 |

为什么漂移不设硬门槛：**走动不产生任何判定**。床的归属由显式的 `lie` 意图 + 数据库裁决（不看位置），聊天可见性只看「是否在厅里」，睡着与睡痕全由时间戳推导，走动没有碰撞与卡位。所以「两个人对同一时刻的位置认知差半个 RTT」不改变任何结果——这是「上行是意图、下行是事实」这条纪律换来的成本节省。

### 1.3 数值基线（名义基线：RTT 500ms、`v = 220px/s`）

| 量 | 公式 | 值 |
| :--- | :--- | :--- |
| 单向时延 | RTT/2 | 250ms |
| 画面相对**服务端真值**的领先 | `oneWay × v` | **55px**（≈0.9 张床宽） |
| 画面相对**最新一条自己 `pos`** 的领先（= 改目标时被携带的那个 `lead`） | `(RTT + 一条 pos 的年龄) × v` | **≈110px**（≈1.8 张床） |
| 「真值陈旧度」（`serverNow − pos.ts`） | 一条 `pos` 的年龄 | **0~100ms**（**与 RTT 无关**：时钟偏移已经把单程吃掉了） |
| 新意图首个 `pos` 造成的倒退（旧实现） | `RTT × v` | 110px（≈1.8 张床） |
| 一拍位移 | `TICK_MS × v` | 22px |
| 别人看我的滞后 | `oneWay + clamp(窗口跨度,100,400)` | 350~650ms |
| 走到床边 → 躺下的站立等待 | `2 × oneWay` + 一拍 | ≈500ms（见 §3.9） |
| 单帧位移上限 | 60fps 下 `v/fps` | 3.7px（<10px 口径） |

> 上表第三、四行是两个**不同**的量，别混：携带的 `lead` 衡量「画面领先最新样本多远」，它随 RTT 增长（RTT 2s → 440px）；「真值陈旧度」衡量「最新样本本身多旧」，它只看链路有没有静默、与 RTT 无关（就一个 `posAge`）。

**模拟器压力基线是单向 500ms（RTT ≈ 1000），不是上表这个名义基线。** 上表留在 RTT 500 是因为它是**分析基线**（数字好算），压力基线只是把同一套公式代入两倍的 `oneWay`。注入方式与实测校准口径见 `test.md` §2。翻倍后的关键量：画面领先 **110px**、改目标时携带的 `lead` **≈240px**、走到床边→躺下站等 **≈1.1s**、别人看我的滞后 **600~900ms**。

## 2. 时间轴与两个坐标

### 2.1 `pos.ts` 的语义

**该批位置所对应的服务端时刻**（等于推进那一刻用掉的「现在」）。客户端一切插值、外推都按它算，**不得**按「两条消息的到达间隔」推进动画。

### 2.2 客户端的服务端时间轴

```text
clockOffsetMs = snapshot.serverTs − 本地收包时刻
serverNow     = 本地当前时刻 + clockOffsetMs
```

- 这个偏移**天然带 `−oneWay` 的偏差**（快照的 `serverTs` 是服务端发包时刻，收包时已经过去一个单程）。
- 它只在**收到快照时算一次**，之后冻结到下一条快照。所以 `lead` 的名义值 = **那一次快照时的单向时延**，不是常量。
- **不为它做测量、不做多点平滑、不引入 RTT 估计**：聊天回投与探活得到的 `rttMs` 只用于观测（§6.2），不进锚点。

### 2.3 两个坐标的职责

```text
truth = (P, pos.ts)                       最新一条关于自己的权威位置与时刻
lead                                   领先量（时间）
render(t) = 沿「从 P 起算的折线」按 (t − ts + lead) 推进
```

| 坐标 | 谁用 |
| :--- | :--- |
| `render` | 渲染、相机跟随、命中判定（点到我自己） |
| `truth` | 意图锚点（§3.3）、相机对准（`hop`）、任何「事实」类判断 |

**渲染只认 `render`，真值只用于重锚；两者之间只允许「向前」收敛**。

### 2.4 误差预算

| 来源 | 量级 |
| :--- | :--- |
| `lead` 的单向抖动（快照那一刻的单程 vs 当前单程） | ±几十 ms → ±10px |
| 寻路近似的候选剪枝（≤52px，见 `architecture.md` §2.6） | **新意图为 0**（两端同函数同输入 → 同一条折线）；「走路中途改目标」≤ `lead`（≈55px），由 §3.2 吸收 |
| 重锚后的位置残差 | **0**（不变量保证） |

## 3. 自己：不变量与重锚

### 3.1 三条硬不变量

1. 点击 → 画面起步：**0 额外帧**；
2. 画面**倒退量恒为 0**（起步、改目标、重锚、到达都算）。两处**有界**例外：§3.4 的传送级跳变，与 §3.7 的「陈旧外推被新意图接管时就地重同步」；
3. 走动过程的单帧位移 < 10px（**60fps 口径**：一帧的合法位移 = `WALK_SPEED_PX_PER_S × 帧时长`，60fps 是 3.7px、30fps 是 7.3px）。**唯一例外**是「权威点跑到我身前」时的**前向**纠错跳变（§3.2）：只许朝前、上限 `TELEPORT_SNAP_PX`（超过即作废外推、落回真值）。

### 3.2 重锚（唯一的重锚公式）

收到关于自己的 `pos`：

```text
锚点      = 权威点在折线上的**投影**（横向分量不进轨迹）
ahead     = 画面点的投影弧长 − 锚点的投影弧长（钳到 0）
anchorTs' = ts − ahead / v
剪枝      = 按**弧长**：剪掉**锚点**已经走过的拐点
```

- **权威在我身后**（`ahead > 0`）→ 锚点时刻前移 → **画面一动不动**，`lead` 保持；
- **权威在我身前**（投影落在画面之后，`ahead = 0`）→ 锚点时刻 = `ts` → 画面当场**前跳**到锚点，之后继续（前向，仍不倒退）；
- 两种情况都不产生倒退，所以保鲜期（§3.7）照常刷新，不会被误判成断线。

为什么锚点取**投影**而不取权威点本身：权威点与客户端折线可能横向分叉（「走路中途改目标」时必然有 `≤ lead` 的偏差），把横向分量带进锚点会让轨迹变成一条**穿过床的斜线**。横向分量不影响时间轴，丢掉它不会丢信息；传送判定（§3.4）仍按**原始**距离算。

为什么剪枝必须按**弧长**：用「拐点 → 下一个拐点」的方向点积判「这个拐点过没过」，在权威点横向偏离折线时会判错——实测一个 10px 的南向偏移就让画面还没走到的拐点被剪掉，画面被投到一条斜线上、**倒退 30px**。弧长口径只问「锚点在折线上走了多远」，与横向位置无关。

为什么剪枝看**锚点**、不看画面：`ahead`（≈`oneWay×v`）这一段里可能夹着一个拐点。按画面剪就把那个拐点抽掉，路径从「锚点 → 拐点 → 下一拐点」变成一条**弦**，画面沿弦前进 → 横向抄近路（实测 47.5px，等于斜穿床）。只需剪掉锚点身后的拐点，画面身后的那个拐点还要用来走。

### 3.3 发出意图时的锚点

- 锚点 = **真值点**（不是我画面上那一点）：站着 → 我的权威位置；在床上 → 床脚前那一点（服务端起身保留的就是它）。
- `lead = 画面点在「新折线上的投影弧长」/ v`（站着不动时为 0，于是「点击即起步」）。**不设人为上限**：`lead` 的定义就是「画面领先真值的量」，正常值 ≈ `oneWay`；给它封顶反而会在 RTT 大时把合法领先量咬掉、在用户点击那一刻把画面往后退。是否携带由 §3.7 的陈旧闸门决定。
  用弧长、不用直线距离：改目标时新折线可能与旧折线**垂直**（画面点偏在新路径的侧方），直线距离会把「侧向偏移」当成前进量，把画面凭空前推；弧长只要它在路径上的进度。
- 路径**只在这一次算**（与服务端同一份闭式寻路）；新意图**覆盖**旧路径。
- 取真值作锚点的理由：与服务端用**同一函数、同一输入**（同一点 + 同一目标）→ 同一条折线；取画面点会让折线整体前移 `lead`，凭空多一处误差。

### 3.4 外推作废的唯一条件

真值点在**同一时刻**距画面点超过 `TELEPORT_SNAP_PX`（传送级跳变：`hop`、布局恢复、服务端换了目标）→ 丢弃外推，渲染回到真值。**除此之外不作废**。

### 3.5 意图被拒

「这条意图一步也没走」的错误码（`3001`/`3002`/`3003`/`3004`/`3005`/`3006`/`3008`/`4002`）→ **当场丢弃外推**，画面回到真值。服务端不会为被拒的目标再发任何 `pos`，不丢就是永久错位。
不含聊天类错误（`4001`/`4003`）：清掉外推等于把一趟正当的走路打断。

### 3.6 不给 `walk` 加 ack

服务端拒绝一条走动类意图时**总是**伴着一条 `error`，客户端据此丢外推；`ack` 只是同一信息的第二条通道，而且它天生要在「立刻预测」与「等服务端」之间选一边。目标点还有一层客户端预吸附（点地面先取最近街网节点），`3006` 实际不可达。**不做。**

### 3.7 保鲜期与冻结

`PREDICTION_STALE_MS`（2000ms）内没有任何关于自己的 `pos` → **冻结在最后一个画面点，不回退**（倒退比停住更难受）。RTT 500ms 下这个值仍是 5 拍以上，不需要按 RTT 缩放。

**保鲜期从「最后一条关于自己的 `pos` 的时刻」起算，不从锚点时刻**——两者只在 `lead = 0` 时才相等。一旦 `lead` 被带入（「走路中途改目标」必带 `≈ oneWay`），拿锚点时刻当基准就会把「刚刚发过意图」误判成陈旧，把刚发起的行走当场冻死。锚点另外记着这个真值时刻（意图时 = 发起那一刻，重锚时 = `pos.ts`）。

已经冻结的外推再被新意图覆盖时，**不携带它的领先量**（那是幻影）：以真值重新起算，等于就地重同步。闸门取**严格**的「真值陈旧度 < 保鲜期的一半」，恰好等于也当陈旧：

| 真值陈旧度 | 行为 | 切换那一刻的画面 |
| :--- | :--- | :--- |
| < `PREDICTION_STALE_MS / 2`（正常操作：等于一条 `pos` 的年龄，0~100ms，**与 RTT 无关**） | 携带 `lead`（正常值 ≈ `RTT + 一条 pos 的年龄`，见 §1.3） | **不动**（0px） |
| ≥ 一半、< 保鲜期 | 不携带（就地重同步） | 落到真值点：**有界后退** ≤ `v × (陈旧度 + oneWay)` |
| ≥ 保鲜期 | 外推已冻结，按上一行同样重同步 | 同上 |

- 边界必须取严格：恰好 2000ms 也算陈旧，否则 2 秒的幻影（440px）会被当成领先量带进去。
- **不靠「给 `lead` 封顶」来做保护**：封顶会同时咬掉合法领先量（RTT 2s 时 `lead ≈ 1s` 是正常的），而且被咬的那一下正是用户点击的时刻——画面当场后退；收闸门只影响「链路已经静默半秒以上」这种已经降级的状态。
- 重同步之后若服务端的位置与我假设的不一致（它换了目标 / 早已停下），下一条 `pos` 按 §3.4 的距离判据直接落回真值。

### 3.8 断线、后台、恢复

| 情形 | 规格 |
| :--- | :--- |
| 断线 / 重连 | 以新 `snapshot` 为准：丢弃外推、清插值窗口、相机对准我（宽限恢复会把我放回原位，可能在厅的另一头） |
| 页面 hidden | 定时器被节流 → 画面冻在旧点；回前台由探活接手（不是心跳），重连后按上一条重置 |
| 重连恢复 | 服务端按**床位行**还原（`lying` / `asleep` 原样、`trace` 洗成 `asleep`），位置一律 `frontPointOf(bedNo)`；断线前那一点与那条路径**已经丢了**（连接销毁后附加数据就读不到，宽限不另存内存副本），所以这是权威位置的一次重置 |
| 降级（`resize`） | 落在旧外圈的权威位置被拉回街网（一次性 `pos`）；客户端按 §3.4 的传送判定落位 |
| 离线期间的上行 | **丢弃不补发**；离线时不登记外推（没有服务端在走，外推只会画错） |

### 3.9 到达与停留（已知代价）

画面因为 `lead` 先到终点，而「到了之后发生的事」是服务端事实：

| 情形 | 画面 | 结果 |
| :--- | :--- | :--- |
| 点地面走到终点 | 到点即停 | 服务端 `oneWay` 后才到；这段无人可见 |
| 点床 → 走到床边 → 躺下 | 到床脚前即停 | **站在床前等 `2 × oneWay`**（RTT 500 → ≈500ms + 一拍）才躺下 |
| 走 10 秒后床被别人抢走（到达动作失败） | 停在终点 | **原地停住 + 现有提示**；不倒退、不瞬移 |

**定稿：接受这段等待并记录**（RTT ≤ 300 时 ≈300ms，「走到床边停一下再躺下」语义上说得过去）。**在单向 500ms 的压力基线（`test.md` §2）下这段等待是 ≈1.1s。** 验收时必须先把这一条摆出来、再判「到床后站着不动」是不是缺陷——它一定会被当成新 bug 报上来。这不是给缺陷开脱：按 §1.3 的公式，这个量本来就随时延线性放大，压到 1.1s 是压力基线自己挑的，不是代码退步。**但压力基线不是「接受这段等待」时的那个链路**：若真机反馈「到床后站着不动」明显，仍按原定口径启用 `lead` 前向收敛（限速追平，见 `backlog.md`）——那会让走速短暂降约 20%。

### 3.10 一跳（`hop`）

不走路：服务端直接给位置、不进移动者集合。客户端**落位不插值**、**同时对准相机**、并**作废本地外推**（相邻床脚只差一格，重锚的跳变阈值盖不住）。

## 4. 别人：口径与已知滞后

### 4.1 口径

- 按 `pos.ts` **线性插值**；滞后 = `clamp(本窗口跨度, 100ms, 400ms)`（等长跨度时就是一个补丁间隔）。
- 单条位移 > `TELEPORT_SNAP_PX` → **直接落位**，不插值（否则跨厅瞬移会拉出一道横贯大厅的模糊线）。
- 不跨窗口插值：跨度超过滞后上限时取端点，不「快进一格」。

### 4.2 已知滞后

| 项 | 值 @RTT500 | 判定 |
| :--- | :--- | :--- |
| 别人看我的滞后 | 350~650ms | **软约束**：允许有、且必须是常量偏置；不允许台阶、不允许抖动 |
| 每拍台阶（节拍晚点时一次补上） | 罕见，p95 间隔 102ms | 已实测「现在不需要平滑」（`backlog.md`） |

### 4.3 禁止：给他人外推

别人的路径我不知道，外推等于给自己造第二个事实源。**别人的位置只来自下行采样。**

### 4.4 备选方案：广播「被验证的折线 + 起始时刻」

把下行从「位置采样」换成「服务端验证过的折线 + 服务端起始时刻」，各端用同一份纯函数推导位置（行业等价物：DIS dead reckoning、RTS 的 move order、框架里的 reckon 模式）。收益：别人的滞后降到 ≈`oneWay`，每拍台阶消失，出站从 10 条/秒降到每次走动 1 条。**代价：协议级改动**，且它**不修**本轮的手感问题。

**现在不做。** 触发判据（任一成立才回头做）：

1. 出现**按位置判定**的交互（距离可见性、谁能和谁说话、任何「谁先到」的规则）；
2. 真机/线上反馈明确抱怨「看别人像慢半拍」（要用户说出来的，不要推测）；
3. 唤醒次数或出站量被平台用量面板证明成为瓶颈。

**混合形态（采样兜底 + 折线为主）明确禁止**：同一个问题两个源，必须再发明优先级与冲突消解规则，是最差的形态。

## 5. 服务端：推进与广播

### 5.1 推进

- 移动者集合只在有人走动时存在；**按实际经过的时间**推进（`elapsed × v`），不按拍数。
- 内存循环 `TICK_MS = 100`：只在集合非空时存在，空了**立即清除**（有定时器存在，对象就无法休眠）。
- 每拍把**所有移动者此刻的精确位置**合并成**一条**广播（`pos`），只要有人在走就必发（不按「格号变没变」筛）。
- 走路开始与结束时各**立即补发一条**当前位置（让别人永远有新鲜的插值端点）。

### 5.2 新移动者不得「补走一拍」

节拍是全局的：一个在两次拍之间才开始走的移动者，若按「上一次拍到现在」整段推进，会在第一拍凭空前冲最多 `TICK_MS × v = 22px`。
规格：**推进量 = 现在 − max(上一拍时刻, 该移动者创建时刻)**。

### 5.3 成本（已知代价，记录用）

- 节拍**不读写 SQLite**（只推进内存与连接附加数据），所以不影响行读写额度；它只影响**房间服务活跃时长**（按固定 128MB 计费）。有人走动时循环几乎常开 → 百人厅里接近「24 小时活跃」那一档（`architecture.md` §额度）。
- 出站（仅量级参考，本项目额度表里没有这一维）：

```text
一条 pos = 42 + 30n 字节            （n = 本拍移动者数）
出站速率 = 10 × 连接数 × (42 + 30n) 字节/秒
100 人 / 5 人在走 → ≈192 KB/s → 走动 8 小时 ≈ 5.5 GB
```

- 不随厅的规模增长（末档 9558 张床同量级），只随在线人数增长；没有按视野裁剪（不在视野里的连接也收）。

## 6. 验收与观测

### 6.1 指标

| 类别 | 指标 | 门槛 |
| :--- | :--- | :--- |
| 硬 | 点击 → 画面起步 | 0 额外帧 |
| 硬 | 画面倒退量（起步 / 改目标 / 重锚 / 到达） | **0px**；例外：传送级跳变（§3.4）与陈旧外推接管时的有界重同步（§3.7） |
| 硬 | 单帧位移（走动过程） | ≤ `WALK_SPEED_PX_PER_S × 帧时长`（60fps 即 < 10px）；例外：前向纠错跳变只许朝前、上限 `TELEPORT_SNAP_PX` |
| 硬 | 冻结时不回退 | 单调 |
| 软 | 别人看我的滞后 | 恒定、无台阶、最终一致；上限 `oneWay + 一拍` |
| 不考 | ordering | — |

### 6.2 观测字段（客户端，`?debug=1`）

`leadMs` / `posAge` / `tickSpan` 在拿到 `pos` 时采（10s 一行）；其余各项由世界层**每帧**采（`world.update()` 末尾一次只读调用，**不参与任何判定**；`?debug=1` 才挂上，不调试时每帧只多一次判空）。

| 字段 | 含义 | 判据 |
| :--- | :--- | :--- |
| `leadMs` | 当前领先量 | ≈ 快照时的单向时延 |
| `posAge` | `serverNow − pos.ts` | p50 ≤ 200ms（`backlog.md`） |
| `tickSpan` | 相邻两条 `pos` 的 `ts` 差 | p95 ≤ 150ms（`backlog.md`） |
| `regressPx` | **倒退像素**：本帧把「上一帧画面点」与「本帧画面点」各投影到**同一条当前折线**上取弧长差，负的那部分累加 | **必须恒为 0**（§6.1 硬指标） |
| `reversals` | `regressPx` 的变号次数（单次幅度 > 0.5px 才算，滤掉浮点噪声） | **必须为 0** |
| `frameDelta` | 相邻两次 `update()` 的**墙钟**间隔（`performance.now()`）的 p50 / p95 / max | **p95 ≤ 25ms 且 p95/p50 ≤ 2** |
| `loopDelta` | 同一帧里 Phaser 的 `loop.delta` —— 小人动画与猫**真的**按它推进 | 与 `frameDelta` 应当 ≈ 相等（帧时直通，`60-interaction-shell.md` §5.2）。整屏页揭幕后若是 `loopDelta` 只有 `frameDelta` 的四成，就是帧时又被平滑了（猫会慢一半，持续 ~120 帧） |
| `selfStepPx` | 本帧画面点的位移**长度**（`hypot`，px） | **max ≤ `WALK_SPEED_PX_PER_S × 帧时长`**：60fps 是 3.7px、30fps 是 7.3px。§6.1 的「< 10px」是 **60fps 口径**，换成 30fps 直接套会让红线自己红 —— 判据要按帧时长归一化 |
| `camStepPx` | 本帧相机 scroll 增量；`opposed=k/n` = 与 `selfStepPx` **方向相反**（点积 < 0）的帧数 / 有样本的帧数 | **opposed / n ≤ 5%** |
| `isMovingFlips` | 本帧摆动闸门的翻转次数。闸门是 `isPictureMoving`（折线上还有路可走且外推没过保鲜期），**不是**服务端时间窗 `isMoving` —— 后者比画面晚关 `oneWay + MOTION_SLACK_MS`，会让小人站住后还在摆 | 一趟走动 **≤ 2** |
| `pathSwap` | 采样窗内折线被换掉的次数（换目标 / 重锚剪枝） | 只用于解释那几帧的投影，不设门槛 |
| `bigStep` | 采样窗内**超过 10px 的最大单帧位移**，带三个判别位：当时有没有外推（`pred`）、摆动闸门开没开（`moving`）、**这一帧多长**（`dt`） | 只在越界时出现。看 **`px / dt`**：≈ 220px/s 就只是「这一帧慢」，明显更快才是跳变（§6.1 的例外是前向纠错） |
| `bigRegress` | 采样窗内**最大的一次倒退**，带这一帧的时长（`dt`）与「折线是不是刚换过」（`pathChanged`） | §3.1 要求倒退恒为 0。读数要除以时长看：30fps 下 5px 只是一帧的合法位移量级；`pathChanged=1` 时先怀疑是弧长坐标在重锚处微动（折线换了、几何相同 ⇒ 同一世界点在新折线上的弧长会差一点点） |
| `suspendGap` | 采样窗内世界被**挂起**过的次数（整屏页揭幕那一帧） | 不算帧间隔也不算位移（否则会读出「190s 的一帧」与跨整屏的假位移）；只用来解释样本为何变少 |

**为什么 `regressPx` 不再比折线身份**：`anchorPrediction` 每拍都用 `dropPassed` 剪一次折线（`path.slice` 换新数组），于是「引用相同才比较」的旧判据让它**恒为 0** —— 那是仪器坏了，不是不变量成立。剪枝只砍掉已过的前缀、剩余几何完全相同，所以「两个世界点投影到同一条当前折线」既连续又可比；换折线的那一帧若把上一帧点被夹在折线起点，记一次 `pathSwap` 并跳过该帧。

这套判据是**先定后量**：采数之前先写死，免得看完数字再倒推结论。

### 6.3 回归测试（本地无需真实网络）

用**假时间轴**注入一条完整的端云端时序：`发出意图 @t0` → `服务端起步 @t0+oneWay` → `起步那条 pos @t0+oneWay` → `每拍 pos` → `到达 @t` → `state @t+oneWay`。矩阵：

| 维度 | 取值 |
| :--- | :--- |
| 单向时延 | 0 / 150 / 250 / 500ms |
| 场景 | 站定起步 / 走路中途改目标 / 在床上点地面 / 点床走躺 / 到达动作失败 |
| 断言 | `regressPx = 0`；画面时间单调；稳态 `leadMs ≈ oneWay`；冻结不回退 |

### 6.4 真机验收

响应式与触摸类验收默认在宿主 Android 模拟器里做（真实 Chrome / IME / 触摸分发）；哪类测试该用哪个环境、为什么桌面手机视口只是降级选项见 `test.md`。

**本轮实测记录**（宿主模拟器 `Medium_Phone_UX`（393×772 CSS）+ `tools/dev/latency-proxy.mjs` 单向 500ms；五趟走动，每窗 10s）：

| 环境 | `frameDelta` p95 | `selfStepPx` max | `regressPx` max | `camStepPx` opposed | 判定 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| 硬件 GPU（60fps） | 18.3ms | 4.2px | 0.7~1.5px | 2%（12/600） | 位置 / 帧时 / 相机都干净 |
| 软件渲染 `-gpu swiftshader_indirect`（~30fps） | 50~55ms | 12.1px，带 `dt=54.6ms` ⇒ **221.6px/s** | 0.9px，带 `pathChanged=1` | 1.8%（5/282） | 同上：12.1px 只是**慢帧**，不是跳变；0.9px 是重锚处的弧长微动 |

`loopDelta` 与 `frameDelta` 在同帧上同步（30fps 下 33.3 / 50.1 / 366.7 对 32.7 / 52.4 / 380.8）⇒ 退出整屏页后帧时直通，猫按真实帧时推进（`60-interaction-shell.md` §5.2）。

## 7. 明确不做

| 不做 | 理由 | 什么时候才做 |
| :--- | :--- | :--- |
| 回滚重放 / 命中回退（Overwatch 式） | 没有命中判定、没有战斗 | 出现需要「按谁看到的时刻裁决」的玩法时 |
| 给他人外推 | 造第二事实源 | 永不（改为 §4.4 的折线广播） |
| 抖动预算 1.5×、渲染时钟平滑 | 实测 `tickSpan` p95 = 102ms；额外预算本身会制造台阶 | `posAge` p50 > 200ms 且真机可见台阶 |
| `walk` ack | 拒绝已有 `error`；ack 要先在「预测/等」之间选边 | 永不 |
| `oneWay` 常数 / 时钟偏移测量 / 多点平滑 | 领先量就该等于当时的单向时延；写死常量会在抖动时凭空造偏差 | 出现长会话漂移的实测证据 |
| `lead` 前向收敛（限速追平） | 为 250ms 引入一整套纠错速率机制；且会破坏「按经过时间等速推进」 | 真机反馈「到床后站着不动」明显时（见 §3.9） |
| 混合形态（采样 + 折线双源） | 同一问题两个源 | 永不 |
| 广播折线（替代采样） | 无需求方，且不修本轮手感问题 | §4.4 的三条触发判据任一成立 |
