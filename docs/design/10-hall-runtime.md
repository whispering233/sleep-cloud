# 子模块设计：大厅运行时

对应架构中的「房间服务层」。一个厅一个实例，单线程串行处理所有请求、消息与到期事件。

## 1. 职责边界

**做**：状态机、床位归属与占用、寻路与位置推进、广播合并、到期事件调度、宽限与睡痕、清理任务、内容过滤、上行限流、场景校验。

**不做**：前端渲染、跨厅协调、用户登录、持久化用户历史（聊天历史不存，见 backlog）。

## 2. 状态存放位置

| 数据 | 存放位置 | 为什么 |
| :--- | :--- | :--- |
| 床位归属、床位状态、睡痕起始时间、用户昵称/外观/时区 | SQLite | 必须跨休眠、跨驱逐存活；且 30 天释放依赖时间戳 |
| 位置、移动路径、当前清醒度（在床上时）、连接标识 | 连接上的附加数据 | 高频变化，写库是纯浪费；**醒着的人一定有活着的连接** |
| 移动者集合、宽限中的连接、限流计数 | 内存 | 可重建、可丢失 |
| 到期事件表（持久唤醒用） | 内存最小堆 | 见 §4.4；丢失可接受（后果见 §4.3） |

**权威边界纪律**：**SQLite 是床位状态的唯一权威**，连接附加数据里只放可丢弃的临时量。若附加数据丢失（进程重启），兜底是**把这个人放回他的床边站着**——这是可接受的降级，不是数据丢失。

## 3. 唤醒与恢复

对象被休眠/驱逐后重新激活时，按以下顺序重建，**不做整表读取**：

1. 从连接集合取出所有仍然活着的连接，读取附加数据（连接标识、位置、路径与到达后动作、是否在床上）
2. 对这些连接对应的床位**按需读取单行**（只有在需要渲染/校验时才读）
3. **重建移动者集合**：附加数据中路径未走完的人，同时启动内存循环（无人则循环不启动）
4. **重建到期事件堆**（按 §4.3 从当前连接集合与床位状态推导出应有的到期事件），并与平台上已存在的持久唤醒槽位对账
5. **不可见人列表不从内存重建**：供快照使用的「可见的人」由三类来源合成——在线者来自连接（步 1），**床上离线者（含睡痕）来自床位行**（按需查询，见下）。后两类必须查库，因为他们已经没有连接了

   两张床位行各自对应一个阶段：`state` 为 `lying` / `asleep` 但人已离线 → 他还在宽限期内（占用不能凭空消失）；`state` 为 `trace` → 宽限已过（睡痕）。**判断的依据是 `last_seen_at` + 宽限期**，不是内存里的宽限记录——记录丢了也要能重建出来（见 §4.3）

**禁止**：唤醒时把 256 行床位一次性读出来。行读取是免费额度下最容易被放大到超额的维度（一次全表 = 512 行，若每次唤醒都做，一夜即可超限十倍）。

**睡痕查询的纪律**：必须走 `state` 索引取出 `trace` 行（几十行量级），而不是取全部床位再在内存里过滤。睡痕行数 ≈「昨晚在床上睡着且未主动起身的人」，这个数字同时也是快照体积的驱动因素，值得监控（详见 `../api/20-api-ws.md` §4.3）。

## 4. 时间驱动的三种机制（术语精确区分）

平台上存在三种互不相同的计时手段，**职责完全不重叠**。混用会直接导致「对象永不休眠」或「高频重写持久状态」两类故障。

### 4.1 平台事实（官方文档核实）

| 事实 | 出处 |
| :--- | :--- |
| DO 提供 `setTimeout` / `setInterval`，但它们**只在对象驻留内存时有效**，对象驱逐后回调不再执行 | 生命周期文档：`No setTimeout/setInterval scheduled callbacks are set, since there would be no way to recreate the callback after hibernating` |
| **存在未完成的定时器时，对象无法休眠**；未完成操作（含定时器）会阻止驱逐，**阻止期间持续产生活跃时长计费** | 生命周期文档「Pending operations prevent eviction」与「Hibernation can only occur if all of the conditions below are true」 |
| 每个对象同一时刻**只能有一个持久唤醒（alarm）**，重复设置会覆盖 | Alarms 文档 |
| 每次 `setAlarm()` 计 **1 行写入**；每次 alarm 触发计 **1 次请求** | 计费文档脚注 |
| 持久唤醒保证**至少一次执行**；失败以指数退避重试，起始 2 秒、**最多 6 次**；处理器墙钟上限 15 分钟 | Alarms 文档 |
| 云端的定时器**不保证精确**（计时只随 I/O 推进，实测存在偏差报告） | 运行时文档「timers / scheduler」与 workerd 已知问题 |

### 4.2 三种机制及其职责

| 机制 | 用途 | 原语 | 持久性 | 何时使用 |
| :--- | :--- | :--- | :--- | :--- |
| **持久唤醒（alarm）** | 必须在**未来某个确定时刻**执行的动作 | 单一的 alarm 槽位 | 跨驱逐存活 | 宽限到期、自动睡着到期、每日清理 |
| **内存循环（timer loop）** | **高频、可丢失**、只在对象已经醒着时才有意义的循环 | 循环调度的内存定时器 | 驱逐即丢（无害） | 位置节拍（100 ms） |
| **读取时推导（derive-on-read）** | 状态本身是时间的函数，**不需要任何定时器** | 无 | — | 睡痕判定、睡着判定 |

**核心分工规则**：

- **凡「必须在某个时刻发生」→ 持久唤醒**（定时器会在驱逐后丢失回调）
- **凡「只在工作中才需要」→ 内存循环**（用完立即清除，否则对象永不休眠）
- **凡「可以算出来」→ 读取时推导**（定时器只是为了让在线观者及时看到变化，不是正确性的来源）

### 4.3 推导是正确性来源，唤醒只是通知手段

睡痕与睡着都可以由时间戳算出，**不需要为任何人挂定时器**：

```
在床上睡着  = 位置为 IN_BED 且 清醒度为 AWAKE 且 现在 - 最后输入时间 > 自动睡着阈值
睡痕        = 位置为 IN_BED 且 连接为 OFFLINE 且 现在 - 最后在线时间 > 宽限期
```

这条性质带来两个结果：

1. **即使所有定时器都丢失，重建后状态依然是正确的**——只需在唤醒时重算一次
2. 持久唤醒的作用**不是正确性，而是及时性**：让「某个睡着的人变成了睡痕」这件事在还有人在看的时候被推出去

### 4.4 到期事件调度器（把多个到期时刻映射到唯一的 alarm 槽位）

平台只给一个 alarm 槽位，而我们需要多个到期时刻，因此需要一个调度器。

**数据结构**：一个按到期时间排序的**最小堆**（内存中），元素为 `(到期时刻, 事件类型, 关联主体)`。事件类型只有三种：宽限到期、自动睡着到期、每日清理。

**同一个主体同一类事件只保留一条**（新的覆盖旧的）：否则「躺在床上的人每说一句话」都会在堆里留下一条旧条目，每一条到点都会白醒一次对象——而唤醒预算是「个位数到几十次/天」。

**桥接规则**：

```
堆顶到期时刻 != 当前已设置的 alarm 时刻 时，才调用 setAlarm(堆顶时刻)
```

先比对再设置，是为了避免重复写入（每次 `setAlarm()` 都是一行写入）。

**`alarm()` 处理器流程**：

1. 弹出所有 `到期时刻 <= 现在` 的事件并执行
2. 若堆非空 → 把新的堆顶时刻写入 alarm 槽位；否则 → 调用删除槽位
3. 执行过程中**不得**留下未清除的内存定时器（否则阻塞休眠）

**事件表为什么可以不持久**：

- 丢失的后果只是「这次及时通知没发出」，而状态仍可由 §4.3 重算得到
- 对象重建时，会从当前连接集合与床位状态重新推导出需要调度的到期事件
- 唯一必须持久的是**每日清理**（对象可能整夜处于休眠），而它本来就是堆里最稳定的一个元素，每天只写一次槽位

**重建放在第一个事件里，不放构造函数**：对象被唤醒时构造函数**先于** `alarm()` 运行，那时写槽位会把平台刚排好的下一次唤醒盖掉。所以重建与槽位对账都在第一个事件入口上做（只真正执行一次）。重建时已经把过期的条目直接丢掉——到期事件只是通知手段，该做的事每个入口都会按推导扫一遍。

**调用频率估算**：每人每晚约 2 次宽限/睡着事件，256 人约 512 次，加上每日清理。相比 100,000 行写入/天的免费额度，占比不到 1%。

### 4.5 内存循环的使用纪律

位置节拍是唯一的内存循环，三条纪律：

| 纪律 | 原因 |
| :--- | :--- |
| **只在存在移动者时创建** | 有未完成定时器时对象无法休眠，常驻循环等于整夜计费 |
| **最后一个移动者停下时立即清除** | 同上。这是本设计里最容易泄漏成本的地方 |
| **不假设节拍精确** | 云端计时不精确。推进量按「自上次推进以来实际经过的时间」计算，而不是「每拍推进固定一步」 |
| **alarm 处理器内不留循环** | 否则一次唤醒变成永久驻留 |

最后一条的具体后果：**位置推进量是时间的函数，不是拍数的函数**。节拍抖动只影响平滑度，不影响移动速度。客户端侧同理：按服务端下发的时间戳插值，不假设固定帧间隔（见 `../api/20-api-ws.md`）。

## 5. 位置推进与广播合并

### 5.1 推进

- 服务端持有**可行走网格**（由场景 JSON 推导）
- 客户端只发目标格，服务端寻路得到**路径**（格序列），并附上**到达后动作**（见下）
- 路径携带「每格耗时」与「已消耗时间」。每次推进按**实际经过时间**消耗若干格（不是每拍固定一格，因为云端计时不保证精确，见 §4.1）
- 路径耗尽时执行到达后动作（若有），再把自己从移动者集合移除

**复合意图**：一条上行的意图可能包含两个动作，由路径携带「到达后动作」实现：

| 上行意图 | 展开为 |
| :--- | :--- |
| 在床上点地面 | 起身（释放占用，保留归属）→ 走到目标格 |
| 不在床上点某张床 | 走到该床旁 → 躺下（兼完成认领，若尚未认领） |
| 原地不动地点地面 | 路径为空 → 不是移动者；若这是最后一个移动者，循环立即结束 |

这样「一次点击 = 一个完整动作」在客户端和服务端都只有一条意图，而移动者集合只需关心一件事：**路径是否走完**。

**移动者集合的定义**：当前有未走完路径的参与者。它就是内存循环的**工作集**（working set）。

| 项 | 说明 |
| :--- | :--- |
| 元素 | 参与者标识 + 路径 + 到达后动作 + 已消耗时间（实际上就是连接附加数据里的那一份） |
| 存放位置 | **只在内存，不落库**（理由见 §5.3 的不变量） |
| 为何不每拍扫描全部连接 | 进镇就为了用 O(移动者) 代替 O(全部连接)。最大厅也只有几百人，但没必要白浪费 CPU（每次调用只有很小的预算） |

### 5.2 广播合并（关键）

```
每个节拍：
  收集本周期内所有位置发生变化的参与者
  合并成一条批量位置消息
  一次性广播给厅内所有在线连接
```

**效果**：下行消息数与「同一周期内变化的人数」无关，只与节拍频率有关——**每 100 ms 最多一条**。静止的人（尤其睡着的人）不产生任何下行流量。

**为什么这是必须的**：若每个移动者每周期各发一条、再逐连接扇出，消息数会随人数平方增长，直接撞上单对象的请求/CPU 上限。

### 5.3 移动者集合的生命周期与循环的启停

**一个白拿的不变量**：

```
存在移动者  ⇔  存在内存循环  ⇒  对象无法休眠/驱逐  ⇒  集合不会因驱逐而丢失
```

左右两个方向都成立：

- 有移动者 → 必须跑内存循环 → 未完成的定时器阻止驱逐 → 集合一直在内存里
- 集合为空 → 循环被清除 → 对象允许休眠，但此时已经没有东西可丢

**结论**：移动者集合只需存在内存，不需要持久化，也不需要在休眠时保存。对象真正被驱逐后重建时，从活着的连接附加数据里重建即可（§3）。

**「停下」的三个来源**（都不是超时，而是确定事件）：

| 来源 | 处理 |
| :--- | :--- |
| 路径走完 | 每拍推进后检查剩余路径为空 → 执行到达后动作 → 移除 |
| 断线 | 连接关闭事件里同步移除（同时把位置与路径搬进宽限会话，见 §6） |
| 被新意图取代 | 新的意图覆盖当前路径（可能从「不在移动者中」变成「在」或反之）；原地目标 → 路径为空 → 直接移除 |

三者统一为「从集合移除」，移除后若集合为空 → **立即清除循环定时器**。

**没有常驻定时循环。** 大厅在无人走动时自然静止并允许休眠。这条纪律的代价是真实的：一个忘记清除的循环会让对象整夜不休眠、整夜计费（见 §4.5）。

## 6. 宽限与睡痕

| 阶段 | 存放 | 行为 |
| :--- | :--- | :--- |
| 连接关闭瞬间（**在床上**） | 内存 | **把位置、移动目标与到达后动作从连接附加数据搬进内存的宽限会话记录**（连接一旦销毁，它的附加数据就不可读了）；进入宽限（60 秒）；**不广播离开**；床位保持占用；同时从移动者集合移除 |
| 连接关闭瞬间（**在地上**） | — | **立刻广播离开**（小人消失）+ 移出移动者集合；同样留一份宽限记录，但它只买「期内重连、位置还在」这条尽力而为的优化 |
| 宽限内重连 | — | 用宽限会话记录恢复原位置与原状态（对别人是「走了又回来」） |
| 宽限到期（在床上） | SQLite | 标记为睡痕，记录起床预估时刻（用于共处时长）；广播状态变化 |
| 宽限到期（在地上） | — | 无事发生（离开早就广播过了）；顺手丢弃宽限记录 |

**为什么必须在关闭事件里同步搬运**：连接对象被销毁后，附加数据就读不到了。如果不搬，宽限期内重连的人会失去位置，只能退回到「站在原地」的降级——而宽限期的意义就是让网络抖动不可见。

**为什么地上的人不等宽限**：宽限能兑现的前提是「到期时还有个东西记得他」——床上的人有床位行（SQLite，权威），地上的人没有。宽限记录只在内存里，而对象空闲约 10 秒就会休眠（见下），所以「等 60 秒再广播离开」对地上的人根本兑现不了，只会留下一个在别人屏幕上停住的小人。代价：网络抖动时地上的人会闪一下（他的位置在休眠后本来也保不住）。

**宽限期的存在理由**：主要服务于**床上的人**——若没有宽限，每次网络抖动都会让人从床上消失（而在床上正是最需要一个稳定状态的地方）。对地上的人，它只覆盖「重连时位置还在」。

**宽限记录只放内存，丢了会怎样**：平台在对象空闲约 10 秒后即可休眠，而**待触发的持久唤醒不阻止休眠**（休眠条件里没有它）——所以 60 秒的宽限记录在生产上大概率在到期前就丢了。丢了的后果分两类：

| 人断开时的位置 | 记录丢了以后 |
| :--- | :--- |
| **在床上** | **不受影响**。宽限与睡痕都能由床位行推导（`state` 为 `lying` / `asleep` + `last_seen_at` + 无活连接），持久唤醒到点仍能把睡痕推给在线的人 |
| **在地上** | 只影响重连时的位置：他早就发过 `leave` 了（别人本来就看不到他），重连后退回到入口 |

## 7. 清理任务

每日在厅时区 08:00 触发一次（换算为 UTC 时间戳，作为到期事件参与 §4.4 的调度器）：

| 任务 | 行为 | 是否释放归属 |
| :--- | :--- | :--- |
| **睡痕清理** | 跨日的睡痕床位 → 状态置空 | **否**（床仍是你的） |
| **归属释放** | 最后出现时间超过 30 天的床位 → 清空归属 | **是**（床回到可认领池） |

**为什么睡痕清理不释放归属**：睡痕是「昨晚」的痕迹，早上消失是自然行为；而「失去我的床」需要更长的缺席时间，否则随便出差几天回来床就没了。

**为什么用「次日 08:00 统一清理」而不是「固定 N 小时」**：「睡眠」这个语义天然与日历日绑定。

**错峰考虑**：若未来厅数变多，各厅的清理时刻应加一个基于厅标识的偏移，避免所有厅在同一秒同时唤醒。第一版 3 个厅时区不同，天然错峰。

## 8. 内容过滤

| 环节 | 行为 |
| :--- | :--- |
| 昵称 | 长度上限 + 剥离控制字符 + 敏感词检测。命中 → 拒绝并返回「昵称违规」错误，**不粗暴断线** |
| 聊天 | **打码而非拦截**：命中词循环替换为 `*`，直到不再有命中，然后照常转发 |
| 干扰字符 | 匹配前剥离 `·（）【】！？《》￥` 类插入字符，并忽略空白、零宽字符与大小写 |
| 词表 | 静态文件随应用打包（平台单包上限 64 MiB，词表远小于此） |
| 为什么打码不拦截 | 深夜陪伴场景里硬拦截会让发送者意识到被审查并试探绕过；打码让对话继续，攻击者得不到反馈 |

## 9. 上行限流

| 项 | 值 |
| :--- | :--- |
| 限额 | 每连接 5 条/秒 |
| 超出 | 丢弃 + 返回「限流」错误（首次提示，后续静默丢弃，避免错误反馈本身变成放大器） |
| 实现位置 | 房间服务层（客户端不可绕过） |

第一版唯一的治理措施。举报、封禁、投票踢人见 backlog，但**错误码已预留**。

## 10. 场景校验

- 每个厅配置一个场景标识（`guid`），客户端首条消息必须携带
- 不匹配 → 返回「场景不匹配」错误并断开
- 未收到场景标识之前，**不向该连接转发任何房间消息**

这个形态来自参考项目 `WheatCloudSleep` 的场景包校验（源码中 `CmdPackGuid` 与 `Room::DeliverToAll` 里的 `m_receivedPackGuid` 判断）。区别是：参考项目用它做地图一致性校验，我们同时把它当作「连接必须先完成握手」的门槛。

## 11. 重连语义

| 情况 | 结果 |
| :--- | :--- |
| 宽限期内重连，cookie 有效 | 恢复原会话（床与在床上状态都保留；**位置**只在宽限记录还活着时能恢复，对象休眠过就退回到入口 / 床边） |
| 宽限期满后重连，cookie 有效 | 新会话。若床位仍是自己的且上一条连接已转睡痕 → 从睡痕状态恢复为「在床上清醒」；否则出现在入口 |
| cookie 无效/缺失 | 签发新匿名身份，从头开始 |

## 12. 未决与实测项

| 项 | 必须先测什么 |
| :--- | :--- |
| 单次调用的 CPU 预算到底是 10 ms 还是 30 秒 | 文档两处口径不一致（详见 `architecture.md` §5.4）。按保守值 10 ms 设计 |
| 单厅并发容量 | 官方未给「每对象 WebSocket 连接数上限」。第一版按 256 床 / 并发 100 设计，实测校准 |
| 睡痕集中清理的负载 | 若某厅一次性清理 200 个睡痕，需确认在单次调用预算内完成（可能需要分批） |
| 唤醒频率与行读取量的实际比值 | 决定是否需要更激进的缓存策略 |
| **内存循环是否真的在无人走动时被清除** | 这是最容易泄漏活跃时长的地方。验证方式：无人走动的时段，平台用量面板上的活跃时长应停止增长 |
| **节拍的实际抖动** | 云端计时不精确。需实测两次节拍的实际间隔分布，确认「按实际时间差推进」这一修正是否足够 |
| **`setAlarm()` 的实际调用次数** | 每个对象每天应是个位数到几十次量级。若显著更高，说明调度器的「先比对再设置」没生效 |
