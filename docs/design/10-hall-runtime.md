# 子模块设计：大厅运行时

对应架构中的「房间服务层」。**一个厅一个实例**（整个应用只有一个厅），单线程串行处理所有请求、消息与到期事件。

## 1. 职责边界

**做**：状态机、床位归属与占用、布局推导（床号 ↔ 位置）、寻路与位置推进、广播合并、到期事件调度、宽限与睡痕、级表升降级、出生点、内容过滤、上行限流、布局版本校验。

**不做**：前端渲染、跨厅协调、用户登录、持久化用户历史（聊天历史不存，见 `backlog.md`）。

## 2. 状态存放位置

| 数据 | 存放位置 | 为什么 |
| :--- | :--- | :--- |
| 床位归属、床位占用、睡痕起算时刻、名字快照 | SQLite | 必须跨休眠、跨驱逐存活；且 30 天释放依赖时间戳 |
| 厅的床位数与每日唤醒边界（`meta`） | SQLite（每 key 一行） | 升降级的判据；每次快照都要读，必须是一次单行读 |
| 位置、移动路径、当前清醒度（在床上时）、连接标识 | 连接上的附加数据 | 高频变化，写库是纯浪费；**醒着的人一定有活着的连接** |
| 移动者集合 | 内存 | 可重建、可丢失 |
| 到期事件表（持久唤醒用） | 内存最小堆 | 见 §4.4；丢失可接受（后果见 §4.3） |
| **上行限流窗口** | 连接上的附加数据 | 可丢失，但**放内存会被绕过**：对象一被驱逐计数就清零 |
| **床位坐标、区域、级表** | **不存任何地方** | 由共享纯函数现算（`20-layout.md` §4）——这是「自动伸缩」能成立的前提 |

**权威边界纪律**：**SQLite 是床位状态的唯一权威**，连接附加数据里只放可丢弃的临时量。若附加数据丢失（进程重启），兜底是**把这个人放回他的床边站着**——这是可接受的降级，不是数据丢失。

## 3. 唤醒与恢复

对象被休眠/驱逐后重新激活时，按以下顺序重建，**不做整表读取**：

1. 从连接集合取出所有仍然活着的连接，读取附加数据（连接标识、位置、路径与到达后动作、是否在床上）
2. 对这些连接对应的床位**按需读取单行**（只有在需要渲染/校验时才读）
3. **重建移动者集合**：附加数据中路径未走完的人，同时启动内存循环（无人则循环不启动）
4. **重建到期事件堆**（按 §4.3 从当前连接集合与床位状态推导出应有的到期事件），并与平台上已存在的持久唤醒槽位对账
5. 读 `meta`（床位数、每日唤醒边界）；**床位数缺失、或不在级表里**时按需归一并写回（规则见下），边界缺失视为「从未结算」
6. **不可见人列表不从内存重建**：供快照使用的「可见的人」由三类来源合成——在线者来自连接（步 1）；**床上离线者（含睡痕）来自床位行**（按需查询，见下）

   两张床位行各自对应一个阶段：`state` 为 `lying` / `asleep` 但人已离线 → 他还在宽限期内（占用不能凭空消失）；`state` 为 `trace` → 宽限已过（睡痕）。**判断的依据只有「`last_seen_at` + 宽限期」与「有没有活连接」**——没有第二份记录可以依赖（见 §6）。

**床位数的归一（读时修正 + 写回）**：`meta.bed_count` 必须**正好是级表里的一档**，否则归一后写回：

| 情况 | 处理 |
| :--- | :--- |
| 在级表里 | 原样用，不写库 |
| 不在级表里（**级表被改过之后的残留**） | 取「**能装下它的最小那一档**」；且不小于 `MAX(bed_no) + 1`（既有床不因级表变小而失去几何）。高于末档则夹到末档 |
| 缺失 | 由 `MAX(bed_no)` 反推能装下它的最小那一档；一行都没有就是第 1 级 |

**为什么需要这条**：级表一改，老库里的 `bed_count` 就是一个不在新表里的数字 —— 地板与墙按「能装下它的那一档」画，可躺的床却按老数字算，厅里于是看起来少几张床（实测：老库 `bed_count = 114`、新表第一档 117 → 最后一行 13 格只画 10 张）。而它**不会自愈**：缩级在表里找不到更小的档（`114` 没有前一档）、升级又要求「已用率 ≥ 75%」。高于末档时多出来的床位行会成为**不可见、不可用**的残留 —— pre-launch 的取舍，真要处理得走降级那条路径。

**禁止**：唤醒时把床位表一次性读出来（升到最高级时那是 9558 行）。行读取是免费额度下最容易被放大到超额的维度。

**睡痕查询的纪律**：走 `state` 索引取出 `trace` 行即可，**没有时间过滤**（睡痕没有 TTL，见 §6）。一条 `state = 'trace'` 且有主的行就是一条该画的睡痕。睡痕行数 ≈「近 30 天在床上睡着、没主动起身、此后也没回来过的人」，这个数字同时也是快照体积的驱动因素，值得监控（详见 `../api/20-api-ws.md` §4.3）。

## 4. 时间驱动的三种机制（术语精确区分）

平台上存在三种互不相同的计时手段，**职责完全不重叠**。混用会直接导致「对象永不休眠」或「高频重写持久状态」两类故障。

### 4.1 平台事实（官方文档核实）

| 事实 | 出处 |
| :--- | :--- |
| 房间服务提供 `setTimeout` / `setInterval`，但它们**只在对象驻留内存时有效**，对象驱逐后回调不再执行 | 生命周期文档：`No setTimeout/setInterval scheduled callbacks are set, since there would be no way to recreate the callback after hibernating` |
| **存在未完成的定时器时，对象无法休眠**；未完成操作（含定时器）会阻止驱逐，**阻止期间持续产生活跃时长计费** | 生命周期文档「Pending operations prevent eviction」与「Hibernation can only occur if all of the conditions below are true」 |
| 每个对象同一时刻**只能有一个持久唤醒（alarm）**，重复设置会覆盖 | Alarms 文档 |
| 每次 `setAlarm()` 计 **1 行写入**；每次 alarm 触发计 **1 次请求** | 计费文档脚注 |
| 持久唤醒保证**至少一次执行**；失败以指数退避重试，起始 2 秒、**最多 6 次**；处理器墙钟上限 15 分钟 | Alarms 文档 |
| 云端的定时器**不保证精确**（计时只随 I/O 推进，实测存在偏差报告） | 运行时文档「timers / scheduler」与运行时已知问题 |
| 空闲且**可休眠**的对象不产生活跃时长；活跃时长按**固定 128 MB** 计费，与真实使用无关 | 计费文档 |

### 4.2 三种机制及其职责

| 机制 | 用途 | 原语 | 持久性 | 何时使用 |
| :--- | :--- | :--- | :--- | :--- |
| **持久唤醒（alarm）** | 必须在**未来某个确定时刻**执行的动作 | 单一的 alarm 槽位 | 跨驱逐存活 | 宽限到期、自动睡着到期、每日唤醒 |
| **内存循环（timer loop）** | **高频、可丢失**、只在对象已经醒着时才有意义的循环 | 循环调度的内存定时器 | 驱逐即丢（无害） | 位置节拍（100 ms） |
| **读取时推导（derive-on-read）** | 状态本身是时间的函数，**不需要任何定时器** | 无 | — | 睡着判定、睡痕判定、**归属过期** |

**核心分工规则**：

- **凡「必须在某个时刻发生」→ 持久唤醒**（定时器会在驱逐后丢失回调）
- **凡「只在工作中才需要」→ 内存循环**（用完立即清除，否则对象永不休眠）
- **凡「可以算出来」→ 读取时推导**（定时器只是为了让在线观者及时看到变化，不是正确性的来源）

**本设计刻意让「读取时推导」承担尽可能多的事**：睡痕的出现、归属的过期、清醒度、色调档位（客户端按自己的显示态算）全都不需要任何定时器。定时器越多，越容易在某处留下一个未清除的循环，而那是本项目最容易付出真金白银的错误。

### 4.3 推导是正确性来源，唤醒只是通知手段

睡痕与睡着都可以由时间戳算出，**不需要为任何人挂定时器**：

```text
在床上睡着 = 位置为 IN_BED 且 清醒度为 AWAKE 且 现在 − 最后输入时间 > AUTO_SLEEP_MS
睡痕       = 位置为 IN_BED 且 连接为 OFFLINE 且 现在 − 最后在线时间 > GRACE_MS
归属过期   = 有主 且 现在 − 最后出现时间 > BED_OWNERSHIP_TTL_MS
```

这条性质带来三个结果：

1. **即使所有定时器都丢失，重建后状态依然是正确的**——只需在唤醒时重算一次
2. 持久唤醒的作用**不是正确性，而是及时性**：让「某个睡着的人变成了睡痕」这件事在还有人在看的时候被推出去
3. **睡痕没有到期这回事**（它跟归属同寿，§6），归属过期也只在每日唤醒真正清行时才广播。客户端也不需要任何时间量：`state === 'trace'` 就画暗，一直画到行被改写

### 4.4 到期事件调度器（把多个到期时刻映射到唯一的 alarm 槽位）

平台只给一个 alarm 槽位，我们需要多个到期时刻，因此需要一个调度器。

**数据结构**：一个按到期时间排序的**最小堆**（内存中），元素为 `(到期时刻, 事件类型, 关联主体)`。事件类型只有三种：

| 事件 | 触发时的动作 |
| :--- | :--- |
| `grace` | 判定并落地「转睡痕 / 什么也不做」（§6） |
| `autosleep` | 把躺着的人写成睡着并广播（§4.3 推导 + 一次写库） |
| `daily` | 归属释放 + 缩级评估（§7） |

**同一个主体同一类事件只保留一条**（新的覆盖旧的）：否则「躺在床上的人每说一句话」都会在堆里留下一条旧条目，每一条到点都会白醒一次对象——而唤醒预算是「个位数到几十次/天」。

**桥接规则**：

```text
堆顶到期时刻 != 当前已设置的 alarm 时刻 时，才调用 setAlarm(堆顶时刻)
```

先比对再设置，是为了避免重复写入（每次 `setAlarm()` 都是一行写入）。

**`alarm()` 处理器流程**：

1. 弹出所有 `到期时刻 <= 现在` 的事件并执行
2. 若堆非空 → 把新的堆顶时刻写入 alarm 槽位；否则 → 调用删除槽位
3. 执行过程中**不得**留下未清除的内存定时器（否则阻塞休眠）

**事件表为什么可以不持久**：

- 丢失的后果只是「这次及时通知没发出」，而状态仍可由 §4.3 重算得到
- 对象重建时，会从当前连接集合与床位状态重新推导出需要调度的到期事件
- 唯一必须由堆自己排出来的是**每日唤醒**（对象可能整夜休眠），而它每天只写一次槽位

**重建放在第一个事件里，不放构造函数**：对象被唤醒时构造函数**先于** `alarm()` 运行，那时写槽位会把平台刚排好的下一次唤醒盖掉。所以重建与槽位对账都在第一个事件入口上做（只真正执行一次）。重建时已经把过期的条目直接丢掉——到期事件只是通知手段，该做的事每个入口都会按推导扫一遍。

**调用频率估算**：每人每晚约 2 次宽限/睡着事件，几百人约几百次，加上每日一次。相比 100,000 行写入/天的免费额度，占比不到 2%。

### 4.5 内存循环的使用纪律

位置节拍是唯一的内存循环，四条纪律：

| 纪律 | 原因 |
| :--- | :--- |
| **只在存在移动者时创建** | 有未完成定时器时对象无法休眠，常驻循环等于整夜计费 |
| **最后一个移动者停下时立即清除** | 同上。这是本设计里最容易泄漏成本的地方 |
| **不假设节拍精确** | 云端计时不精确。推进量按「自上次推进以来实际经过的时间」计算 |
| **alarm 处理器内不留循环** | 否则一次唤醒变成永久驻留 |

最后一条的具体后果：**位置推进量是时间的函数，不是拍数的函数**。节拍抖动只影响平滑度，不影响移动速度。客户端侧同理：按服务端下发的时间戳插值，不假设固定帧间隔（见 `../api/20-api-ws.md` §4.7）。

## 5. 位置推进与广播合并

### 5.1 推进

- **可行走区域由布局函数给出**（`20-layout.md` §4 的 `isWalkable`）：**街列**（每格一条竖走道）∪ **街行**（每格一条床脚前横走道带）∪ **贴墙那一圈环形走道**，再减掉「墙矩形向内缩 `WALL_BODY`」以外的部分。**房间内部（床 + 预留位）不是街** —— 于是将来往预留位里放装饰物不可能堵住路，也不需要阻挡集。**没有场景文件、没有 blocked 数组**
- 客户端只发**目标世界像素点**（客户端已把点吸附到街网，`layout.nearestStreetPoint`）；服务端**只校验**，在街网上寻路得到路径（街网上的折线），并附上**到达后动作**（见下）
- 街网是**完备网格**：任意「街行 × 街列」都是节点，每条街行横贯整厅、每条街列纵贯整厅。于是**沿走道走的最短路 = 坐标曼哈顿距离**，寻路退化成**闭式**：总代价 = 起点→源节点 + 曼哈顿(源, 目标) + 目标节点→终点，只枚举两端各自的常数个候选（≤16 组算术，**无搜索、无优先队列**）。**不是按跳数**（按跳数会让「跨横走道带」的点对绕到边界去），也不保证最少拐弯。
- **行切换只能发生在竖走道上**（横走道带上，只有 x 落在竖走道里才连得上别的行）→ 同列相邻两行的正确走法必然是「横到最近竖走道 → 竖走 → 横回来」，朴素的 `|Δx| + |Δy|` 在这张网上**不可达**：实测同列相邻两行的 `路径长 / L1` = **1.75 ~ 2.64**。这是判「就近寻路」的口径，别再拿两点直线距离当基准。
- 端点不在走道中线上时，首／末段是**近轴斜线**（最多偏半条走道 ≈ 28px）：因为端点与节点同带或同块，整段仍落在街网内。**这是既有行为**（不是某次改动引入的），`nearestStreetPoint` 保留 x、只改 y 也是同一回事。
- 路径携带「已消耗时间」。每次推进按**实际经过时间** × `WALK_SPEED_PX_PER_S` 消耗（不是每拍固定一段，因为云端计时不保证精确，见 §4.1）
- **推进量从「上一拍」与「本人起步时刻」中较晚的那个起算**：节拍是全局的，而一个人可能在两拍之间才开始走——直接拿「上一拍到现在」会让新起步的人第一拍凭空前冲最多 `TICK_MS × 速度 = 22px`。同理，对象被驱逐后重建工作集按「此刻起步」算，不补停工那段（规格：`30-movement-sync.md` §5.2）
- 路径耗尽时执行到达后动作（若有），再把自己从移动者集合移除

**目标点不在街网上 → `3006`（静默）**：**不吸附到最近的合法点**。静默吸附会让「点床躺下」与「点地面走动」的判定出现意外（用户点在床上却走开了）。

**寻路规模**：节点 = 街行（每格的床脚前横走道 + 贴墙那一条）× 街列（每格的竖走道 + 贴墙那一条）。最高档 83 × 120 ≈ **1 万个节点**，但闭式的代价**与节点总数无关**：每个端点只保留常数个候选（最近的街列 ≤2 + 自身所在街列的最近街行 ≤2）→ 最高档仍 ≤ 0.1ms，**与厅的绝对尺寸无关**。
剪枝是**近似**：偏差上限约**一条走道（56px ≈ 0.43s 步程）**（拐点最优点一般落在两端之间，「各自最近的那条街」可能错过它，最多各差半条走道），实测最坏 **52px**（档 294、2 万组随机可走点对）；而**床脚前走道中心这类中线端点（出生点、躺下目标）偏差为 0**——常见路径都是后者。

「网格完备」这条前提有单测兜底（`src/hall/tests/pathfinding.test.ts` 的**护城河**测试：折线的每一段按 ≤8px 密集采样后必须全程在街网上）——某条横走道不再横贯整厅时，闭式照样会返回一条长度正确、但**穿过床**的折线，那条测试会红。

**复合意图**：一条上行的意图可能包含两个或三个动作，由路径携带「到达后动作」实现：

| 上行意图 | 展开为 |
| :--- | :--- |
| 在床上点地面 | 起身（释放占用，保留归属）→ 走到目标点 |
| 不在床上点某张床 | 走到该床旁 → 躺下（兼完成认领，若可认领；**我已有别的床则这是一次换床**：旧床当场释放，距上次认领不足 10 秒 → `3008`）。**服务端不看这步是不是换床意图**：换床模式的闸门在客户端，见 `../api/20-api-ws.md` §4.5 |
| 在床上点另一张可认领的床 | **起身**（释放占用、保留归属）→ 走到该床旁 → 躺下（兼换床）。只在换床模式内会发生（模式外那一下在客户端就被拦下） |
| 原地不动地点地面 | 路径为空 → 不是移动者；若这是最后一个移动者，循环立即结束 |

这样「一次点击 = 一个完整动作」在客户端和服务端都只有一条意图，而移动者集合只需关心一件事：**路径是否走完**。

**为什么在床上点别的床也自动起身**：与「在床上点地面」同一条原则。**判定不通过时不站起来**（不为了一个会失败的动作产生副作用）；反面唯一例外是「点自己正躺着的那张床」——那什么都不做（`3004`，静默）。

**「一跳」（`hop`）不走路**：它不寻路、不进移动者集合 —— 服务端直接把位置设为 `frontPointOf(bedNo)`（在床上则先起身：释放占用、保留归属），清空路径与到达后动作，并立即广播一条位置。为什么不是走过去：跨厅距离与走动速度不在一个量级（第 1 级厅宽 2361px ≈ 10.7s，末档 20526px ≈ 93s）。**不带床号 = 我自己那张**（没有归属就静默忽略；HUD 那一条在没有床时本来也不显示）；**带床号时只看床号，不看归属与占用**（跳到别人床脚站着是合法的），越界回 `3001`（静默）——客户端用 `bedCount` 先拦一道并给可见提示。客户端对这次跳变**直接落位不插值**，并且**相机同时对准那张床**（`focusBed`），不依赖 500px/s 的跟随（见 `../api/20-api-ws.md` §4.7）。

**移动者集合的定义**：当前有未走完路径的参与者。它就是内存循环的**工作集**（working set）。

| 项 | 说明 |
| :--- | :--- |
| 元素 | 参与者标识 + 路径 + 到达后动作 + 已消耗时间（实际上就是连接附加数据里的那一份） |
| 存放位置 | **只在内存，不落库**（理由见 §5.3 的不变量） |
| 为何不每拍扫描全部连接 | 用 O(移动者) 代替 O(全部连接)。单次调用的 CPU 预算很小，没必要白花 |

### 5.2 广播合并（关键）

```text
每个节拍：
  收集本周期内的**所有移动者**（不按「格号有没有变」筛；走路开始与结束各再补发一条当前位置）
  合并成一条批量位置消息
  一次性广播给厅内所有在线连接
```

**效果**：下行消息数与「同一周期内变化的人数」无关，只与节拍频率有关——**每 100 ms 最多一条**。静止的人（尤其睡着的人）不产生任何下行流量。

**为什么这是必须的**：若每个移动者每周期各发一条、再逐连接扇出，消息数会随人数平方增长，直接撞上单对象的请求/CPU 上限。

### 5.3 移动者集合的生命周期与循环的启停

**一个白拿的不变量**：

```text
存在移动者 ⇔ 存在内存循环 ⇒ 对象无法休眠/驱逐 ⇒ 集合不会因驱逐而丢失
```

左右两个方向都成立：有移动者 → 必须跑内存循环 → 未完成的定时器阻止驱逐 → 集合一直在内存里；集合为空 → 循环被清除 → 对象允许休眠，但此时已经没有东西可丢。

**结论**：移动者集合只需存在内存，不需要持久化。对象真正被驱逐后重建时，从活着的连接附加数据里重建即可（§3）。

**「停下」的三个来源**（都不是超时，而是确定事件）：

| 来源 | 处理 |
| :--- | :--- |
| 路径走完 | 每拍推进后检查剩余路径为空 → 执行到达后动作 → 移除 |
| 断线 | 连接关闭事件里同步移除（床上的人只写一行 `last_seen_at`，见 §6） |
| 被新意图取代 | 新的意图覆盖当前路径（可能从「不在移动者中」变成「在」或反之）；原地目标 → 路径为空 → 直接移除 |

三者统一为「从集合移除」，移除后若集合为空 → **立即清除循环定时器**。

**没有常驻定时循环。** 大厅在无人走动时自然静止并允许休眠。这条纪律的代价是真实的：一个忘记清除的循环会让对象整夜不休眠、整夜计费（见 §4.5）。

## 6. 宽限与睡痕

| 阶段 | 存放 | 行为 |
| :--- | :--- | :--- |
| 连接关闭瞬间（**在床上**） | SQLite | 写 `last_seen_at = now`（这是唯一要写的）；排一次宽限到期；**不广播离开**；床位保持占用；从移动者集合移除 |
| 连接关闭瞬间（**在地上**） | SQLite | **立刻广播离开**（小人消失）+ 移出移动者集合；除 `last_seen_at` 外不写任何东西 |
| 重连（**不论隔了多久**，床位行仍是我的且归属未过期） | SQLite | 从床位行恢复**行上的状态**（`lying` / `asleep` / `trace` 一律还原）；位置退回床边；行本来是 `trace`（别人看的是暗的）→ 广播「我醒了」 |
| 宽限到期（在床上） | SQLite | `state → 'trace'`，`updated_at` 写**宽限到期的时刻**（不是发现它的时刻），广播状态变化 |
| 宽限到期（在地上） | — | 无事发生（离开早就广播过了） |
| **归属释放（30 天，每日唤醒）** | SQLite | 睡痕跟着一起消失：`state → 'empty'`、`owner_*` 清空（§7） |

**为什么没有内存宽限记录**：曾经有一份——把位置与路径从连接附加数据抄进内存，供宽限期内重连恢复原位置。它被删掉了：对象空闲约 10 秒就会休眠，被驱逐时连 `close` 事件都不给（平台文档明写不提供关闭钩子），于是「内存比库更权威」的分支在线上**几乎从不生效，而且何时生效无法预测**。现在宽限只靠一根时间轴——床位行上的 `last_seen_at` 加「有没有活连接」，两者都能重建。代价是地上的人断网重连落在床边（或出生点），而不是原地——即硬纪律 10 的可接受降级。

**为什么地上的人不等宽限**：宽限能兑现的前提是「到期时还有个东西记得他」——床上的人有床位行（SQLite，权威），地上的人没有（没有行就等于没有记忆）。所以「等 60 秒再广播离开」对地上的人根本兑现不了，只会留下一个在别人屏幕上停住的小人。

**为什么 `updated_at` 仍写「宽限到期时刻」而不是「发现时刻」**：它已经不是任何判据了（睡痕没有 TTL），但让行表达「这件事本该何时发生」——对象重建后重跑 `expireGrace`，得到的仍是同一个值，行不会显得比自己更活跃。

**睡痕什么时候消失**：**跟归属同寿（30 天）**，没有独立的 TTL。它只会在三种情形下终结：① 主人回来（回到 `lying` / `asleep`）；② 归属释放后行被新人躺上（改写）；③ 每日唤醒释放归属（`state → 'empty'`）。所以客户端也不需要 `traceUntil` 去淡出——一张睡痕会一直画到它被上面三件事之一改写。

## 7. 每日唤醒（UTC 20:00）

每日固定时刻触发一次，做两件事：

| 任务 | 判定 | 行为 | 广播 |
| :--- | :--- | :--- | :--- |
| **归属释放** | 有归属且（`last_seen_at` 超过 30 天 **或为 NULL**） | 一条 `UPDATE` 清空 `owner_*`、`sleep_started_at`，`state → 'empty'` | 每张床一条 `bed`（`owned: false`） |
| **缩级评估** | 最外那一圈床**全部无主且无占用**（占用随时间消失只有一条路：归属 30 天释放）**且今天还没结算过** | 取下 `meta.bed_count` + 写 `daily_wake_at` | 一条 `resize` |

**为什么没有「清睡痕」这条任务**：睡痕跟归属同寿（§6），归属释放那一条 `UPDATE` 同时把它带走。不存在第二个时间轴，也就不需要第二个任务、第二个 TTL、第二次广播。

**为什么归属释放仍然需要一次批量任务，而不是纯推导**：判定「能不能躺」时确实按过期推导，但**行不会自己消失**——「最外圈是否全空」需要一个周期性结算点才能结算（睡痕自己不会到期，它只跟着归属一起走）。每日唤醒本来就要为缩级评估存在，顺手一条 `UPDATE` 即可。

**为什么时刻固定 UTC 20:00**：没有厅时区了，就选一个低峰时刻（UTC 20:00 = 北京 04:00）。归属释放与缩级在**用户侧不可感知**（释放的床本来是空床，缩级砍掉的是无人拥有的外圈），所以选哪个时刻只影响成本，不影响体验。

**排「下一个」20:00；越过一个就补跑一次，但补跑受 `meta.daily_wake_at` 约束——同一个 20:00 只结算一次**：平台保证持久唤醒至少执行一次（失败会退避重试），正常情况下不会漏；而对象被驱逐后重建时，堆是空的（§4.4），若此刻已经越过一个 20:00，就该把它补上——否则「夜间对象一直在重建」的忙厅会永远不结算归属释放。

**为什么必须有「只结算一次」这条约束**：`daily_wake_at` 缺失或过旧时，重建即补跑；若没有这个边界，缩级就会变成「每个对象生命周期一次」——忙厅里一夜能连降好几档（208 → 161 → 114），与 §8 的「一天最多降一级」直接冲突，还会与入场时的升级叠成 resize 抖动（刚长出来的一圈、住户还没躺进去就被收回去）。

**`last_seen_at` 为 NULL 的有主床也释放**：认领必然伴随一次写 `last_seen_at`，所以这种行只可能来自历史或异常数据；不释放等于这张床永远回不到池子里。

**广播形态为什么逐条**：协议里 `bed` 与 `resize` 都是单主体消息（`../api/20-api-ws.md` §4.5、§4.6），没有批量形态；被释放的床量级下（一夜几十张）逐条发仍远低于一次调用的出站预算。

## 8. 级表升降级

床位数不是一个固定配置，而是一个**随需要跳档的级**（`20-layout.md` §3.1）。整个机制只有三个动作：判据、写 `meta`、广播 `resize`；**不写任何床位行**（新增的床全是无主空床，不需要行）。

| 动作 | 时机 | 判据 | 是否动既有床 |
| :--- | :--- | :--- | :--- |
| **升级** | **入场前**（生成快照之前） | **已用率 ≥ 75%**（等价：可认领的床已不足本档容量的 25%，与出生点同一个查询：无主或归属已过期；无占用）且未到最后一档 | **否**：床号按「建成顺序」分配（先内后外），外圈新增的床号必然最大；**地板与墙随之外扩**（新的格网 + 四侧各一条走道） |
| **降级** | **每日唤醒**（且该次 20:00 尚未结算过） | 最外那一圈床全部无主且无占用（占用清空只有一条路：归属 30 天释放）**且 已用率 < 50%** | **否**：砍掉的正是那些无主无占用的床——它们落在**墙外**（墙矩形只按本级算），墙跟着收回。**广播 `resize` 之前先对全厅连接跑一次 `recoverPosition`**：站在旧外圈的漫游者由它拉回街网，**同时清掉他正在走的那条路径**（否则他会沿着旧路径走出墙外）；落地状态是「停在街网上」 |
| **触顶** | 已是最后一档（9558）且无空床 | `2002`（厅满），由入场前的 HTTP 判定拦下 | — |

**为什么升级触发在入场前**：厅满意味着「新进来的人没有床可躺」。入场是唯一必然产生新住户的时刻，在那一刻判定，既不会提前浪费空间，也不会让人进来后无处可去。

**为什么判据是「已用率 ≥ 75%」而不是「厅满了」**：像 `ArrayList` 一样**提前扩容**——厅永远留有余量，新人进来时看得见的是一片有空床的厅，而不是「刚刚才长出来」的尾巴。75% 与步长 1.37 是配好的：一次跳档后已用率降到 `0.75 / 1.37 ≈ 55%`（空闲 45%），既不会连跳两档，也不会刚扩完就又接近阈值。

**两个阈值必须成对（滞回），否则会自激**：「外圈全空」**不等于**「内圈有富余」——第 2 级 150 床、117 张有主时，外圈那 33 张全空，可空闲率只有 **22%**；此时若缩到 117 床，厅立刻坐满，下一拍又满足扩容条件 → 一天一档地来回跳。所以缩级多加一条「已用率 < 50%」，并让它与扩容阈值满足 `50% × 1.37 = 68.5% < 75%`：**扩完空闲 45%、缩完已用 68.5%**，两边都不越界。

**为什么降级只在每日评估**：降级需要「这一圈真的没人要了」的判断，实时判定会在人数波动时来回跳档。每日一次天然滞后，且跳档本身（区域矩形变化 + 一条广播）成本可忽略。

**为什么升降级都不会移动既有床**：`bedNo ↔ 位置` 是**与当前床位数无关**的纯函数（`20-layout.md` §4 的不变量 1、2）。这是「外圈生长」的全部意义：老用户的床永远在原地，躺着的人不会看到房间在自己身下重排。

**降级会不会砍掉有人的床**：不会。判据要求那一圈「全部无主且无占用」；只要有一张床有主——哪怕是 29 天没回来的住户——这一级就保留。

**升/降级的成本**：一次 `meta` 写（约 2 行）+ 一条广播。**不产生任何床位行**，所以它比「一次性预建 9558 行」便宜几个数量级。

## 9. 出生点

新用户进入时的站立位置：

| 步骤 | 规则 |
| :--- | :--- |
| 0 | 若我已有**未过期归属**的床 → 站在**那张床脚前的横走道中心**（`frontPointOf`），不看「最小可认领床」 |
| 1 | 否则取**编号最小的「无主空床」**（无行 = 无主空床；归属已过期也视为无主） |
| 2 | 站在那张床**前方的横向走道**上（世界像素） |
| 3 | 若整个厅没有可认领的床 → 先升级（§8），再取（新外圈的第一张床） |
| 4 | 触顶且无空床 → 不入场（`2002`） |

**为什么第 0 步先看自己的床**：跨厅走不动（第 1 级 10.7s、末档 93s），而我的床可能在大厅另一头——把人丢在最小的可认领床旁边，等于让他先走两分钟才能回到自己的位置。已有归属的人直接落在自己床边，与「回我的床」（§5.1）是同一件事的两个入口。

**为什么新人（还没有床）不适用这一条**：他还没有床，而「编号最小」同时是最好的近似——最小的空床通常在厅内偏内圈的位置，那里住户最密。

**为什么不丢在尾端**：这个产品的价值是「看见别人」。把新人丢在没有住户的尾部，等于一进厅就看不见人；填坑规则让新人落在已有住户中间（30 天释放留下的坑会被新人补上），大厅始终是紧凑的。

**为什么需要找「编号最小」**：它同时是最好的近似——最小的空床通常在厅内偏内圈的位置，那里住户最密。

**代价**：每次入场做一次「有没有可认领的床 / 最小空缺床号」的线性扫床号（床表只有「有主或有占用」的行，量级接近近 30 天活跃人数，从几百到几千行）。**不做缓存**：缓存要自己维护失效点（认领、释放、降级、驱逐重建），而收益只是省一次几百行的扫描——按 §3 的行读取纪律衡量，这个量级可接受。

## 10. 内容过滤

| 环节 | 行为 |
| :--- | :--- |
| 昵称 | 长度上限 + 剥离控制字符 + 敏感词检测。命中 → 拒绝并返回「昵称违规」错误，**不粗暴断线** |
| 聊天 | **打码而非拦截**：命中词循环替换为 `*`，直到不再有命中，然后照常转发 |
| 私聊 | **与聊天同一套规则**（打码、长度上限、空消息），区别只在投递：只给双方各一条，第三人零流量。目标不在厅 → `2005`，静默 |
| 干扰字符 | 匹配前剥离 `·（）【】！？《》￥` 类插入字符，并忽略空白、零宽字符与大小写 |
| 词表 | 静态文件随应用打包（平台单包上限 64 MiB，词表远小于此） |
| 为什么打码不拦截 | 深夜陪伴场景里硬拦截会让发送者意识到被审查并试探绕过；打码让对话继续，攻击者得不到反馈 |

## 11. 上行限流

| 项 | 值 |
| :--- | :--- |
| 限额 | 每连接 5 条/秒；**固定 1 秒窗口**，窗口锚点是该窗口内的第一条消息，满 1 秒开新窗口（不引令牌桶） |
| 超出 | 丢弃 + 返回 `4002`。服务端不记「是否已经提示过」——提示与否由客户端决定，而 `4002` 属静默类：不提示（避免错误反馈本身变成放大器） |
| 适用的意图 | 全部上行业务意图（含 `walk`），不只是聊天 |
| 实现位置 | 房间服务层（客户端不可绕过） |

## 12. 布局校验

- 布局版本号写死在共享层（`config.md` §1），客户端首条消息必须携带
- 不匹配 → 返回 `2003` 并断开（客户端应刷新页面）
- 未收到布局版本之前，**不向该连接转发任何房间消息**

这个形态来自参考项目 `WheatCloudSleep` 的场景包校验（源码中 `CmdPackGuid` 与转发前的 `m_receivedPackGuid` 判断）。区别是：参考项目校验的是「地图文件一致」，我们校验的是「几何版本一致」——因为几何是程序化生成的，没有文件可校验。

## 13. 重连语义

| 情况 | 结果 |
| :--- | :--- |
| 重连（**不论隔了多久**），cookie 有效，且床位行仍是我的、归属未过期 | 恢复**行上的状态**：`lying` / `asleep` / `trace` 一律还原（睡下就是睡下，不会退成「躺着」）；位置回床边，相机对准它；行本来是 `trace`（别人看到的是暗的）→ 广播「我醒了」 |
| 重连，cookie 有效，但归属已过期（30 天） | 那张床已经不是他的，可能已被别人躺上。**静默**按新人处理（出生点，§9）：不提示、不报错——要提示就得在 30 天之外再留一份「你曾经有张床」的记录（`70-privacy-risk.md` §5） |
| cookie 无效/缺失 | 签发新匿名身份，从头开始 |

**客户端侧（与上表互补）**：断线后客户端按 1→2→4→8→15 秒退避**自动重连**，并按需探活（三条触发点、`ping`/`pong`、提示条三态见 `../api/20-api-ws.md` §5.1）。两处必须对齐：

1. **客户端不在宽限期上做任何判断**——它只管重连，恢复成什么样由服务端按上表决定（床还在就还原床上的状态，30 天不回来就按新人处理）。
2. **探活的 `ping` 不算输入**：不刷新 `lastInputAt`。否则躺在床上的人切一次屏就把自己的自动睡着又推后 5 分钟（`AUTO_SLEEP_MS` 是「无输入」时长）。

## 14. 未决与实测项

| 项 | 必须先测什么 |
| :--- | :--- |
| 单次调用的 CPU 预算到底是 10 ms 还是 30 秒 | 文档两处口径不一致（详见 `architecture.md` §5）。按保守值 10 ms 设计 |
| 单厅并发容量 | 官方未给「每对象 WebSocket 连接数上限」。第一版按 117 床起步、并发 100 设计，实测校准 |
| 升/降级的真实频率 | 117 → 150 需要 117 张床全部有主（= 30 天内出现过 117 个不同的人）。若明显更频繁，说明级表步长太小 |
| **内存循环是否真的在无人走动时被清除** | 这是最容易泄漏活跃时长的地方。验证方式：无人走动的时段，平台用量面板上的活跃时长应停止增长 |
| **节拍的实际抖动** | 云端计时不精确。需实测两次节拍的实际间隔分布，确认「按实际时间差推进」这一修正是否足够 |
| **`setAlarm()` 的实际调用次数** | 每个对象每天应是个位数到几十次量级。若显著更高，说明调度器的「先比对再设置」没生效 |
| 睡痕条目数（近 30 天有主且离线的行） | 它现在是快照体积的主驱动因素。条目数过千时把 `hello` 的全量快照换成「快照 + 增量广播」（见 `backlog.md`） |
| 「最小空缺床号」查询的成本 | 缓存命中时为零；缓存被驱逐后退化为一次表扫描（几百行）。若入场量很大再优化 |
