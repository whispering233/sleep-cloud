# 反馈与建议（feedback）

**一句话**：齿轮浮层里的一行「反馈与建议」，打开一块表单，用户写一段话发出去；服务端只存下来给运维看，**不回复、不公开、不关联任何人**。它与举报是两件事：举报针对**某个人**、要证据；反馈针对**这个产品**、只要一段话。

协议字段与错误码见 `../api/20-api-ws.md` §3、§4.10 与 `../api/error-code.md`；后台列表见 `../api/30-api-admin.md` §5.9；本文定**产品语义、上限与取舍**。

## 1. 定位与边界

| | |
| :--- | :--- |
| **是** | 用户主动写的一段文字（bug、想要的功能、体验抱怨）+ 提交时刻 + 提交者身份；后台只读列表 |
| **不是** | 举报（没有对象、不要证据、不触发封禁语义）；客服工单（没有回复、没有状态、没有联系方式）；公开留言板（不展示给任何其他用户） |
| **入口** | 齿轮浮层 →「反馈与建议」。**不做常驻按钮**：它不是高频动作，常驻一颗按钮会与「睡不着留言板 / 求签 / 游戏」那三颗占位入口抢位置 |
| **落地** | 插槽面板的第四个内容态（`composer = 'feedback'`），几何与退场完全复用 `50-slot-panel.md`；**不是浮层、不是新页面、不加载新资源** |

**为什么不复用举报表单**：举报的 `toId` 是「当前选中的人」，事由框的语义是「他做了什么」；反馈没有对象，也不该被迫先点一个人。把两者塞进一个表单会让「举报」这个动作变得含糊，也会让反馈的文案无法独立。

## 2. 入口与面板

| 项 | 决定 |
| :--- | :--- |
| 入口位置 | 齿轮浮层菜单里，「关于失眠云」之上（先反馈、再看说明；说明面板是文档，反馈是动作） |
| 状态 | `composer = 'feedback'`（`60-interaction-shell.md` §2） |
| 进入 | 点菜单项 → 面板打开、组合贴顶、**焦点进事由框**（拉键盘）。这与 `typing` / `report` 是同一套几何 |
| 退场 | 「收起」胶囊 / 点面板空白 / 断线 / 提交成功（`5004` 回执） |
| 不降级 | `focusin` 落在事由框上时**保持 `feedback`**，不能像 `reading → typing` 那样降级——降级会当场卸载表单、丢掉已写的字（与 `report` 同一条规则） |
| 草稿 | **不留**：退场即丢弃，重开是空表单。理由见 §9 |

**入口文案**：菜单项叫「反馈与建议」；面板标题没有额外标题行，第一行就是说明文字 + 输入框（插槽面板的内容契约不允许自造标题栏）。

## 3. 表单

```text
┌─────────────────────────────┐
│ 哪里让你睡不着？想加点什么？   │ ← 说明行（弱化，13px）
│ ┌─────────────────────────┐ │
│ │                         │ │ ← textarea，自动聚焦，最多 500 字
│ │                         │ │
│ └─────────────────────────┘ │
│ 0/500                       │ ← 计数器（右下，仅在接近上限时变色）
│ 反馈会保存 90 天，只有运维能看到，不会公开，也不回复。  │
│                    [ 发送反馈 ] │ ← 44px 主按钮
└─────────────────────────────┘
```

| 项 | 规则 |
| :--- | :--- |
| 输入 | `<textarea>`，`maxLength = FEEDBACK_MAX_LEN`（500），`rows ≈ 5`；字号 ≥ 16px（移动端不触发缩放） |
| 空态 | trim 后为空 → 按钮 `disabled`；**不发上行**（不靠服务端 `4003`） |
| 计数器 | `已写/500`，纯文本；不阻止输入，超出由 `maxLength` 拦 |
| 说明行 | 弱化墨色，不写「我们会尽快处理」——没有这个承诺 |
| 隐私行 | 一句 + 「使用须知」链接（复用 `privacy-link` 的打开方式，**不写 `target="_blank"`**）。这句话就是告知，不另开勾选框 |
| 提交按钮 | 主按钮，`pointerdown` 里 `preventDefault()`（插槽红线，`50-slot-panel.md` §7） |
| 提交中 | 按钮禁用 + 文案「发送中…」；**不发第二条** |
| 失败 | `4004`（配额）在表单内显示一行可见错误、**保留已写内容**；`4001` / `4003` 同区域显示；网络失败（无回执）由连接层处理，面板不自己猜 |

**没有的字段**：联系方式、分类下拉、截图、评分、是否愿意被联系。每多一个字段就多一份隐私面与一次放弃率；首版只回答「你想说什么」。

## 4. 协议与服务端

### 4.1 上行

```json
{ "t": "feedback", "text": "希望夜里能有一个只看不说话的区" }
```

| 项 | 规则 |
| :--- | :--- |
| 身份 | 取**当前连接**的身份（`hello` 已认证），**客户端不能指定别人**；不校验 `identity` 行是否存在（`hello` 已 UPSERT） |
| 长度 | trim 后按字符计 1~`FEEDBACK_MAX_LEN`（500） |
| 过滤 | **不过内容过滤**：它不是广播内容，只有运维看得到（与举报事由同一条理由）。代价是用户可能写进个人信息——告知里说清「只保存给运维看」 |
| 限流 | 与业务意图共用 5 条/秒窗口；超限**静默丢弃**（不回 `4002`，同 `report`） |
| 配额 | 同一身份**滚动 24 小时内最多 5 条**（`FEEDBACK_DAILY_MAX`）。按 `created_at` 数行，**不按自然日**（没有时区概念） |
| 去重 | **没有**：同一段话再发一次仍是一条（直到配额）。反馈不是幂等动作，静默吞掉重复会让用户以为没发出去 |
| 落库 | 一行：`user_id` + `text` + `created_at`。**不存昵称快照、不存床号、不存来源信息**——后台读时现补昵称，与举报一致 |

### 4.2 判定的顺序

```text
已握手？ ──否──▶ 2004（断开）
  │是
trim 后为空？ ──是──▶ 4003（静默，客户端本就不该发）
  │否
超长？ ──是──▶ 4001（可见，客户端 maxLength 之外的兜底）
  │否
24 小时配额已满？ ──是──▶ 4004（可见）
  │否
写一行 → 回 5004（可见）
```

**空 / 超长不消耗配额**：否则一次误触的长粘贴会把当天的额度吃掉。

### 4.3 回执

- 成功：`{ "t": "error", "code": "5004" }`，**只回给发送者**。它与 `5003` 一样是「成功用 `error` 报文回」的例外：客户端需要一条带码的回执来退场并给确认。
- 客户端收到 `5004` → `exitComposer()` + 一句「已收到你的反馈」。
- **没有回执的其他路径**：被 5 条/秒静默丢弃时什么都不回；连接已断时上行被丢，面板随断线退场（`60-interaction-shell.md` §2）。

## 5. 配额与成本

| 动作 | 成本 |
| :--- | :--- |
| 一次提交 | 1 次 `COUNT(*)`（走 `(user_id, created_at)` 索引）+ 1 行写 + 1 条下行 |
| 一次被配额拒绝 | 1 次 `COUNT(*)`，不写 |
| 每日唤醒 | 1 条 `DELETE ... WHERE created_at < now − 90 天`（走 `created_at` 索引） |

| 上限 | 值 | 依据 |
| :--- | :--- | :--- |
| 单条长度 | 500 字 | 足够说清一件事；比举报事由（200）宽，因为反馈通常要描述场景 |
| 每人每日 | 5 条 | 正常用户一天不会写第 6 条；它挡住的是「按住发」而不是表达 |
| 全局 | **没有** | 见 §9：满员时 5 条/人/天仍是可观的写放大量，但当前没有全局闸门的需求方 |

## 6. 存储与留存

| 项 | 决定 |
| :--- | :--- |
| 表 | `feedback`：`id`（自增）/ `user_id` / `text` / `created_at` |
| 索引 | `(user_id, created_at)`（配额查询）、`created_at`（留存清理与后台排序） |
| 留存 | **90 天**，并入每日唤醒的批量删除；与来源信息、举报同批 |
| 删除 | 没有单条删除接口；到期自动删 |
| 证据 | **没有**：反馈不关联聊天，也不拷贝任何发言缓冲 |
| 公开 | 任何用户接口都不返回反馈内容；只有 `/api/admin/feedback` 返回 |

## 7. 后台

| 项 | 决定 |
| :--- | :--- |
| 视图 | `#feedback`（`110-admin-console.md` §2.1） |
| 列表字段 | `text` / `nickname`（读时现补，过期或从未有过 → `null`）/ `userId` / `createdAt` |
| 排序 | `id DESC`（最新在前） |
| 分页 | `?limit=50&before=<id>`，`{ items, next }`，与举报明细同一套游标 |
| 过滤 | **没有**：不按人、不按时间、不按关键词筛。量级是人工可翻的（见 §9） |
| 操作 | **只有读**：没有「已处理」标记、没有删除、没有回复、没有封禁按钮 |
| 成本 | 一页 50 行 = 1 次列表查询（`LEFT JOIN identity` 一次补齐昵称，不做逐行主键读） |

**为什么不做「已处理」**：它需要一个谁改的、什么时候改的、改了之后还能不能撤销的状态机，而后台只有一个操作者、也没有第二个消费者。真要跟踪，运维自己在别处记。

## 8. 隐私告知

必须与功能**同一版**上线，不能先开入口后补告知。需要改两处：

| 位置 | 加什么 |
| :--- | :--- |
| `70-privacy-risk.md` §3.1 数据清单 | 一行「反馈内容（用户主动提交的文字 + 时刻 + 身份），只给运维看，90 天」 |
| `public/privacy.html` 第 2 条（记录什么） | 「你主动提交的反馈内容」 |
| `public/privacy.html` 第 4 条（留多久） | 「反馈内容 90 天」 |

**不进日志**：反馈正文不得写进任何 `log.ev` 字段（`100-log.md` 的字段白名单本来就不含自由文本）；也**不新增日志事件**——提交量在后台列表里看得到，日志不记内容、只记事件名与短标量，多一条事件就多一份预算。

## 9. 已知代价

- **不会回复**：用户写完不知道有没有人看。这是明确的取舍——回复需要工单状态、通知渠道与「谁来回」的承诺，当前没有需求方。面板上那句「不回复」就是诚实的边界。
- **没有全局闸门**：满员 9558 人 × 5 条/天 = 每天最多约 4.8 万行写。这比聊天消息量小得多（聊天不落库），但仍是一个可被恶意放大的写路径；出现真实滥用时再加全局日上限（`backlog.md`）。
- **配额可被绕过**：清 cookie 换身份即重置，与封禁同一个天花板（匿名身份下无解，`70-privacy-risk.md` §9）。
- **正文可能含个人信息**：用户自己写的，服务端不过滤、不打码；只有运维看得到，90 天后删除。
- **草稿不保留**：退场即丢。保留草稿要新增本地存储键与「什么时候算草稿」的规则，当前没有需求方（`40-client-storage.md` 的准入判据也倾向于不存）。
- **没有截图 / 设备信息**：复现 bug 只能靠文字描述；自动附带 UA / 版本会变成一条隐式的指纹上报，先不做。

## 10. 验收判据

| # | 判据 |
| :--- | :--- |
| 1 | 齿轮 →「反馈与建议」→ 面板打开、焦点在输入框、世界被面板盖住（与非空闲态几何一致） |
| 2 | 空内容时「发送反馈」禁用；输入后可用；计数器随输入变化，到 500 字停止 |
| 3 | 提交成功 → 面板退场 + 一句「已收到你的反馈」；库里多一行，`user_id` 是当前身份 |
| 4 | 同一天第 6 条 → 表单内可见「今天已经提过很多次了」类提示，**已写内容还在**，不发第二条成功回执 |
| 5 | 点「收起」/ 点面板空白 → 退场；重开是空表单；表单内容不落本地存储 |
| 6 | 后台 `#feedback` 按 `id` 倒序显示，昵称读时补；90 天前的行被每日唤醒删掉 |
| 7 | `npm test` 覆盖：空 / 超长 / 配额边界 / 成功回执 / 清理条件（各一条，不穷举） |

## 11. 不做

| 项 | 原因 |
| :--- | :--- |
| 回复 / 工单状态 / 通知 | 没有需求方；需要一整套会话与投递 |
| 已处理标记 / 删除 | 单操作者、无第二消费者；删除会毁掉「用户说过什么」的唯一记录 |
| 分类下拉 / 评分 / 截图 | 每多一项就多一份隐私面与一次放弃率 |
| 联系方式字段 | 服务端不知道你是谁；收联系方式等于开始保管一条可联系到人的记录 |
| 公开的反馈墙 / 投票 | 会变成 UGC 审核面，且与「只有运维看得到」的告知冲突 |
| 自动建 issue / 转发到外部 | 引入第三方与凭据；当前只有一个人看 |
