# 数据结构 Schema 设计

## 1. 存储划分

| 存储 | 内容 | 权威性 |
| :--- | :--- | :--- |
| **厅的私有 SQLite**（每个厅一份） | 床位归属、床位状态、睡痕、用户档案快照 | **唯一权威** |
| 连接上的附加数据 | 位置、移动路径、在床上时的清醒度、连接标识 | 临时量，可丢弃 |
| 内存 | 移动者集合、宽限中的连接、限流计数 | 可重建 |
| cookie（客户端持有） | 用户标识 + 所属厅 + 该厅中的床位号 | 服务端签名的凭据，不含隐私数据 |

**厅的边界就是数据库的边界**：厅与厅的数据互不可见，第一版不存在跨厅事务需求。

## 2. 表：`bed`

一个厅一张表，行数恒定等于该厅容量（256 行，初始化后不再增删行，只改字段）。**一个用户最多只能认领一张床**由唯一索引保证。

| 字段 | 是否必选 | 数据类型 | 取值范围 | 备注 |
| :--- | :--- | :--- | :--- | :--- |
| `bed_no` | 是 | INTEGER | 0 ~ capacity-1 | 主键。厅内固定槽位号，与场景坐标的映射由场景数据提供 |
| `state` | 是 | TEXT | `empty` / `lying` / `asleep` / `trace` | **床位**占用状态。`trace` 即睡痕（在床上但已离线超宽限） |
| `owner_user_id` | 否 | TEXT | 用户标识 | 归属。为空表示该床尚未被人认领；**唯一索引，一个用户只能有一张床** |
| `owner_name` | 否 | TEXT | 1~16 字符 | 昵称快照。**服务于离线者**：睡痕没有连接，名字只能从这里读。允许重名 |
| `owner_appearance` | 否 | TEXT | 枚举值 | 小人外观（第一版为固定几种） |
| `owner_tz` | 否 | TEXT | IANA 时区名 | 用户本地时区。**当前不参与服务端任何判断**（含睡痕清理时刻，那是厅时区的 08:00）。保存它只为将来的「睡眠记录归属哪一晚」不需要补数据 |
| `claimed_at` | 否 | INTEGER | epoch 毫秒 | 认领时刻 |
| `last_seen_at` | 否 | INTEGER | epoch 毫秒 | 最后一次出现的时刻。归属释放的唯一依据（超过 30 天释放） |
| `sleep_started_at` | 否 | INTEGER | epoch 毫秒 | 本次睡眠（躺下）的起始时刻。为空表示当前未在床上 |
| `updated_at` | 是 | INTEGER | epoch 毫秒 | 最后一次状态变更时刻，用于调试与幂等判断 |

### 状态取值语义

| 值 | 含义 | 归属 | 占用 |
| :--- | :--- | :--- | :--- |
| `empty` | 床空 | 可能仍有归属（人不在） | 无 |
| `lying` | 有人睁眼躺着（在线） | 有 | 有 |
| `asleep` | 有人睡着（在线） | 有 | 有 |
| `trace` | 睡痕：床上的人已离线超过宽限期 | 有 | 有 |

**注意**：`empty` 不等于「无归属」。一张床可以是「你的，但现在空着」。**归属与占用是两个正交概念**，不要合并成一个字段。

**两个词表的区别（容易搞混）**：

| 词表 | 取值 | 主体 |
| :--- | :--- | :--- |
| 本表的 `state` | `empty` / `lying` / `asleep` / `trace` | **一张床** |
| 下行 `state` 消息的取值 | `roaming` / `lying` / `asleep` / `trace` | **一个人** |

差别只在第一个值上：人可以说「不在床上但活着」（`roaming`），而对应那张床的状态是 `empty`（没有占用者）。**不要把 `roaming` 写进这张表**。

### 索引

| 索引 | 目的 |
| :--- | :--- |
| 主键 `bed_no` | 按槽位直接寻址（绘制、渲染、点击命中） |
| 唯一索引 `owner_user_id` | 保证一个用户只能认领一张床 |
| 索引 `last_seen_at` | 归属释放扫描（30 天） |
| 索引 `state` | 睡痕清理扫描、在线人数统计 |

## 3. 为什么不建用户表

第一版中「一个厅里，一个人 = 一张床」，用户档案（昵称、外观、时区）与床位一一对应。单独建一张用户表会形成 1:1 冗余表，**属于过度设计**。

用户档案所需的全部字段已经落在 `bed` 行上。等出现「一个用户在多个厅都有床」或「用户资料页」时再拆表（见 `backlog.md`）。

## 4. 不落库的数据

| 数据 | 原因 |
| :--- | :--- |
| 位置与移动路径 | 高频变化；**醒着的人一定有活着的连接**，存在连接附加数据上即可 |
| 聊天内容 | 第一版不存历史（见 `backlog.md`）。客户端本地保留最近若干条用于显示 |
| 私聊内容 | 同上 |
| 情绪/表情事件 | 瞬时事件，无持久意义 |
| 投票状态 | 第一版无此功能 |
| 举报记录 | 第一版无此功能（协议预留错误码） |

## 5. 数据生命周期

| 事件 | 变化 |
| :--- | :--- |
| 首次躺下 | `state` → `lying`；写入 `owner_*`、`claimed_at`；`sleep_started_at` = 现在 |
| **修改昵称（已认领床位的用户）** | 同步更新该床的 `owner_name` 快照，否则他的睡痕会显示旧名字 |
| 自动或手动睡着 | `state` → `asleep` |
| 起身 | `state` → `empty`；`sleep_started_at` 清空；**保留归属** |
| 断线超宽限（在床上） | `state` → `trace` |
| 次日 08:00（厅时区） | `state = trace` 的行 → `state` = `empty`；**保留归属** |
| 最后出现超过 30 天 | 清空 `owner_*` 与 `sleep_started_at`；`state` → `empty`（床回到可认领池） |
| 每次连接建立/断开 | 更新 `last_seen_at`（**不随心跳更新，避免写放大**） |

## 6. 白送的副产品：睡眠记录

`sleep_started_at` + 起床时刻天然构成一条「睡眠时段」记录。第一版不做展示，但**不额外花钱**，将来做「一起睡了 N 小时」时零改表。

两个睡痕（或睡痕与在线睡着者）的时段重叠时长即为「共处时长」。

## 7. 存储量估算

| 项 | 量级 |
| :--- | :--- |
| 单厅行数 | 256 行，恒定 |
| 单行大小 | 约 200 字节量级 |
| 单厅数据量 | 数十 KB |
| 三个厅合计 | 数十 KB ~ 百 KB 级，远低于 5 GB 免费额度 |

存储从来不是约束；**行读取次数与对象活跃时长才是**（见 `../design/architecture.md` §5）。
