# 数据结构 Schema 设计

## 1. 存储划分

| 存储 | 内容 | 权威性 |
| :--- | :--- | :--- |
| **厅的私有 SQLite** | 床位归属、床位占用、睡痕、名字快照、厅级元信息（`meta`） | **唯一权威** |
| 连接上的附加数据 | 位置、移动路径、在床上时的清醒度、连接标识、上行限流窗口 | 临时量，可丢弃；**限流窗口放这里是因为它必须跨对象休眠存活** |
| 内存 | 移动者集合、宽限中的连接、当前级号 | 可重建（级号可从 `meta.bed_count` 反查） |
| cookie（客户端持有） | 用户标识 + 昵称 + 18 岁自述 | 服务端签名的凭据，不含隐私数据；**不放床位号、不放时区、不放厅** |

**只有一个厅，所以「厅的边界就是数据库的边界」这句话退化成「整个应用一份库」**：所有权威状态在同址，天然强一致。将来若真要多厅，`bed` 表加一列 `hall_id` 或每厅一个对象实例即可（见 `../design/backlog.md`）。

## 2. 表：`bed`

**惰性行**：只有「有主或有占用」的床才有一行。没有行 = 无主空床。

| 字段 | 是否必选 | 数据类型 | 取值范围 | 备注 |
| :--- | :--- | :--- | :--- | :--- |
| `bed_no` | 是 | INTEGER | 0 ~ `bed_count−1` | 主键。床号由布局函数给出（§5），**与当前床位数无关** |
| `state` | 是 | TEXT | `empty` / `lying` / `asleep` / `trace` | **床位**占用状态。`trace` 即睡痕（在床上但已离线超宽限） |
| `owner_user_id` | 否 | TEXT | 用户标识 | 归属。为空表示该床尚未被人认领（或认领已被释放）；**唯一索引，一个用户只能有一张床** |
| `owner_name` | 否 | TEXT | 1~16 字符 | **最近一次上床时使用的昵称快照**，不是「同步于会话的昵称」。唯一消费者：生成快照时给**睡痕条目**提供名字 |
| `owner_appearance` | 否 | TEXT | 枚举值 | 小人外观（第一版为固定几种） |
| `claimed_at` | 否 | INTEGER | epoch 毫秒 | 认领时刻 |
| `last_seen_at` | 否 | INTEGER | epoch 毫秒 | 最后一次出现的时刻。**连接建立与断开时各写一次**。两个用途：归属过期判定，以及**宽限 / 睡痕推导** |
| `sleep_started_at` | 否 | INTEGER | epoch 毫秒 | 本次睡眠（躺下）的起始时刻。为空表示当前未在床上 |
| `updated_at` | 是 | INTEGER | epoch 毫秒 | 最后一次状态变更时刻。**睡痕行上写的是宽限到期的时刻**（`last_seen_at + 宽限期`），睡痕过期由它加 `TRACE_TTL_MS` 推导 |

**删掉了 `owner_tz`**：时区概念整体删除（见 `../design/config.md` §2），它原本唯一服务「睡眠记录归属哪一晚」，而昼夜已取消。

### 状态取值语义

| 值 | 含义 | 归属 | 占用 |
| :--- | :--- | :--- | :--- |
| `empty` | 床空（可能是我的床，也可能是有主的空床） | 可能仍有归属 | 无 |
| `lying` | 有人睁眼躺着（在线） | 有 | 有 |
| `asleep` | 有人睡着（在线） | 有 | 有 |
| `trace` | 睡痕：床上的人已离线超过宽限期 | 有 | 有（**到期后视为无占用，但不写库**，见 §6） |

| 字段 | 角色 |
| :--- | :--- |
| `owner_user_id` | **关联键**：与会话里的用户标识比对，回答「这张床是不是我的」 |
| `owner_name` | **显示快照**：只服务于快照里的睡痕条目，不参与任何判断 |

**入场的顺序**：昵称先写入会话（建连之前），躺下时才随认领一起写入 `owner_user_id` 与 `owner_name`。所以「关联」发生在上床那一刻，而不是入场那一刻。

**注意**：`empty` 不等于「无归属」。一张床可以是「你的，但现在空着」。**归属与占用是两个正交概念**，不要合并成一个字段。

对应的协议设计也保持这两个维度分离：归属集合进快照的位图、归属变更走独立的 `bed` 下行消息，而占用完全由「人」的那一类消息派生。详见 `../api/20-api-ws.md`。

**两个词表的区别（容易搞混）**：

| 词表 | 取值 | 主体 |
| :--- | :--- | :--- |
| 本表的 `state` | `empty` / `lying` / `asleep` / `trace` | **一张床** |
| 下行 `state` 消息的取值 | `roaming` / `lying` / `asleep` / `trace` | **一个人** |

差别只在第一个值上：人可以说「不在床上但活着」（`roaming`），而对应那张床的状态是 `empty`（没有占用者）。**不要把 `roaming` 写进这张表**。

### 索引

| 索引 | 目的 |
| :--- | :--- |
| 主键 `bed_no` | 按床号直接寻址（认领、起身、单行读取） |
| 唯一索引 `owner_user_id` | 保证一个用户只能认领一张床；也是「我的床」的取行路径 |
| 索引 `state` | 睡痕查询（`state = 'trace'`）与占用者补录（`state IN ('lying','asleep')`） |
| 索引 `last_seen_at` | 归属释放扫描（30 天） |

**没有行数 = 床位数这条关系**：行数 ≈ 当前有主床数（几百行量级），远小于级容量（117 ~ 9558）。这是**惰性行**的直接收益：一次初始化不再需要写 9558 行（那会吃掉每日行写额度的一成）。

## 3. 表：`meta`

键值表（每个 key 一行）。**只在升级 / 降级 / 每日唤醒后写**，读快照时读这些行。

| key | 类型 | 含义 | 何时写 |
| :--- | :--- | :--- | :--- |
| `bed_count` | INTEGER | **当前级容量**（`../design/20-layout.md` §3.1 的 `capacity`）。决定世界里存在哪些床 | 升级、降级 |
| `daily_wake_at` | INTEGER | **最近一次已结算的每日唤醒边界**（epoch 毫秒 = 已结算的那个 UTC 20:00）。用于保证「一天最多降一级」 | 每日唤醒执行后 |

**不存「已用床数」这个计数**：判断「该不该升降级」用的是**与出生点同一套谓词**（有主或有占用：无主或归属已过期、无占用或只剩已过期睡痕，见 §6）在**同一次全表读**里数出来的**已用床数**。于是只有一个真相源，也不存在「计数器与实际行数漂移」的窗口。代价是入场时多一次线性扫行（几百行量级，已接受；**不做缓存**，见 `../design/10-hall-runtime.md` §8、§9）。

**缺失或可疑时按需推导一次**：`bed_count` 由 `MAX(bed_no)` 反推所属的档；`daily_wake_at` 缺失视为「从未结算」→ 允许补跑一次。对象被驱逐后第一次用到时走这条路径。

## 4. 为什么不建用户表

第一版中「一个人 = 一张床」，用户档案（昵称、外观）与床位一一对应。单独建一张用户表会形成 1:1 冗余表，**属于过度设计**。用户档案所需的全部字段已经落在 `bed` 行上。等出现「一个用户在多处都有床」或「用户资料页」时再拆表（见 `backlog.md`）。

## 5. 不落库的数据

| 数据 | 原因 |
| :--- | :--- |
| 位置与移动路径 | 高频变化；**醒着的人一定有活着的连接**，存在连接附加数据上即可 |
| 床位坐标 | **由布局函数现算**（`../design/20-layout.md` §4），不落库、不下发、没有场景文件 |
| 聊天内容 | 第一版不存历史（见 `backlog.md`）。客户端本地保留最近若干条用于显示 |
| 私聊内容 | 同上 |
| 情绪/表情事件 | 瞬时事件，无持久意义 |
| 睡痕的「已过期」与「归属已过期」 | 都能由时间戳推导，不写库（§6） |

## 6. 数据生命周期

| 事件 | 变化 |
| :--- | :--- |
| 首次躺下（无行） | **INSERT**：`state = 'lying'`，写 `owner_*`、`claimed_at`、`last_seen_at`、`sleep_started_at`、`updated_at`；**不写任何计数** |
| 每次上床（含从睡痕恢复） | 刷新 `owner_name` / `owner_appearance`（因为只有此时的昵称才可能被显示） |
| 自动或手动睡着 | `state → 'asleep'` |
| 起身 | `state → 'empty'`；`sleep_started_at` 清空；**保留归属** |
| 断线超宽限（在床上） | `state → 'trace'`；`updated_at` 写的是**宽限到期的时刻**（由 `last_seen_at + 宽限期` 推导），不是「发现它的时刻」——睡痕过期拿它当判据，写发现时刻会让远处的睡痕多活一整个 TTL |
| 宽限期内重连（在床上） | `state` 保持 `lying` / `asleep`（位置与路径由内存的宽限记录恢复；记录丢了就退回床边站着） |
| 宽限已过后重连（床仍是自己的且是睡痕） | `state → 'lying'`，归属与 `sleep_started_at` 不动 |
| **睡痕到期（TTL 12h）** | **不写库**。读取时按 `updated_at + TRACE_TTL_MS` 判定：该床回落为「有主空床」，别人可以躺上去 |
| 别人躺上一张「过期睡痕 / 过期归属」的床 | **直接覆盖**（UPSERT：写新的 `owner_*` 与占用）。归属过期同样只判定、不先释放 |
| **升级** | 入场前判定：**已用床数 ≥ 本档容量的 75%**（与出生点同一套谓词）且未到上限 → 取下一级容量写 `meta.bed_count`，广播 `resize`。**不写任何床位行**（新床都是无主空床） |
| **降级**（每日唤醒评估） | 最外圈那一级的床**全部无主且无占用**（「过期即视为空」）**且已用率 < 50%**、今天还没结算过（`daily_wake_at` < 最近一个 UTC 20:00）→ 取下 `meta.bed_count` + 写 `daily_wake_at`，广播 `resize` |
| **归属释放**（每日唤醒，UTC 20:00） | 一次 `UPDATE` 清空 `owner_*`、`sleep_started_at`，`state → 'empty'`（`last_seen_at` 为空或超过 30 天的行）。并对受影响的床广播 `bed`（`owned: false`） |
| 每次连接建立/断开 | 更新 `last_seen_at`（**不随心跳更新，避免写放大**） |

**为什么归属释放仍然是一次批量任务，而不是纯推导**：判定「能不能躺」时确实按过期推导（`../design/config.md` §2），但**行不会自己消失**——「最外圈是否全空」需要一个周期性结算点才能结算（睡痕过期则连结算都不需要：它只影响「画不画」与「能不能躺」）。每日唤醒本来就要为缩级评估存在，顺手一条 `UPDATE` 即可（见 `../design/10-hall-runtime.md`）。

## 7. 白送的副产品：睡眠记录

`sleep_started_at` + 起床时刻天然构成一条「睡眠时段」记录。第一版不做展示，但**不额外花钱**，将来做「一起睡了 N 小时」时零改表。

两个睡痕（或睡痕与在线睡着者）的时段重叠时长即为「共处时长」。

## 8. 存储量估算

| 项 | 量级 |
| :--- | :--- |
| 单厅行数 | ≈ 有主床数（几百），**不是级容量** |
| 单行大小 | 约 180 字节量级（去掉 `owner_tz` 后更小） |
| 单厅数据量 | 几十 ~ 几百 KB，远低于 5 GB 免费额度 |

存储从来不是约束；**行读取次数与对象活跃时长才是**（见 `../design/architecture.md` §5）。
