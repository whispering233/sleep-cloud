# 数据结构 Schema 设计

## 1. 存储划分

| 存储 | 内容 | 权威性 |
| :--- | :--- | :--- |
| **厅的私有 SQLite** | 床位归属、床位占用、睡痕、名字快照、厅级元信息（`meta`）、**风控台账（`identity` / `block` / `admin_audit`）** | **唯一权威** |
| 连接上的附加数据 | 位置、移动路径、在床上时的清醒度、连接标识、上行限流窗口 | 临时量，可丢弃；**限流窗口放这里是因为它必须跨对象休眠存活** |
| 内存 | 移动者集合、宽限中的连接、当前级号 | 可重建（级号可从 `meta.bed_count` 反查） |
| cookie（客户端持有） | 用户标识 + 昵称 + 18 岁自述 | 服务端签名的凭据，不含隐私数据；**不放床位号、不放时区、不放厅** |
| cookie（后台，`sc_admin`） | `ADMIN_TOKEN` 的指纹 + 签发时刻 | 与 `sc_session` 完全独立；见 `../api/30-api-admin.md` §2 |

**只有一个厅，所以「厅的边界就是数据库的边界」这句话退化成「整个应用一份库」**：所有权威状态在同址，天然强一致。将来若真要多厅，`bed` 表加一列 `hall_id` 或每厅一个对象实例即可（见 `../design/backlog.md`）。

## 2. 表：`bed`

**惰性行**：只有「有主或有占用」的床才有一行。没有行 = 无主空床。

| 字段 | 是否必选 | 数据类型 | 取值范围 | 备注 |
| :--- | :--- | :--- | :--- | :--- |
| `bed_no` | 是 | INTEGER | 0 ~ `bed_count−1` | 主键。床号由布局函数给出（§5），**与当前床位数无关** |
| `state` | 是 | TEXT | `empty` / `lying` / `asleep` / `trace` | **床位**占用状态。`trace` 即睡痕（在床上但已离线超宽限） |
| `owner_user_id` | 否 | TEXT | 用户标识 | 归属。为空表示该床尚未被人认领（或认领已被释放）；**唯一索引，一个用户只能有一张床** |
| `owner_name` | 否 | TEXT | 1~16 字符 | **最近一次上床时使用的昵称快照**，不是「同步于会话的昵称」。唯一消费者：生成快照时给**睡痕条目**提供名字 |
| `owner_appearance` | 否 | TEXT | 枚举值 | 小人外观（第一版为固定几种） |
| `claimed_at` | 否 | INTEGER | epoch 毫秒 | 认领时刻。**两个用途**：①换床冷却的判据（`now − claimed_at < 10_000` 且目标是另一张床 → `3008`；**读取时推导**，不挂定时器，见 `../design/config.md` §2）；②「这张床归我多久了」这类展示的口子 |
| `last_seen_at` | 否 | INTEGER | epoch 毫秒 | 最后一次出现的时刻。**连接建立与断开时各写一次**。两个用途：归属过期判定，以及**宽限 / 睡痕推导** |
| `sleep_started_at` | 否 | INTEGER | epoch 毫秒 | 本次睡眠（躺下）的起始时刻。为空表示当前未在床上 |
| `updated_at` | 是 | INTEGER | epoch 毫秒 | 最后一次状态变更时刻。**睡痕行上写的是宽限到期的时刻**（`last_seen_at + 宽限期`）。它**不是任何判据**（睡痕没有 TTL），只是「这件事本该何时发生」的记录 |

**删掉了 `owner_tz`**：时区概念整体删除（见 `../design/config.md` §2），它原本唯一服务「睡眠记录归属哪一晚」，而昼夜已取消。

### 状态取值语义

| 值 | 含义 | 归属 | 占用 |
| :--- | :--- | :--- | :--- |
| `empty` | 床空（可能是我的床，也可能是有主的空床） | 可能仍有归属 | 无 |
| `lying` | 有人睁眼躺着（在线） | 有 | 有 |
| `asleep` | 有人睡着（在线） | 有 | 有 |
| `trace` | 睡痕：床上的人已离线超过宽限期 | 有 | 有（**跟归属同寿，自身不过期**，见 §7） |

| 字段 | 角色 |
| :--- | :--- |
| `owner_user_id` | **关联键**：与会话里的用户标识比对，回答「这张床是不是我的」 |
| `owner_name` | **显示快照**：只服务于快照里的睡痕条目，不参与任何判断 |

**入场的顺序**：昵称先写入会话（建连之前），躺下时才随认领一起写入 `owner_user_id` 与 `owner_name`。所以「关联」发生在上床那一刻，而不是入场那一刻。

**注意**：`empty` 不等于「无归属」。一张床可以是「你的，但现在空着」。**归属与占用是两个正交概念**，不要合并成一个字段。

对应的协议设计也保持这两个维度分离：归属集合进快照的位图、归属变更走独立的 `bed` 下行消息，而占用完全由「人」的那一类消息派生。详见 `../api/20-api-ws.md`。

**两个词表的区别（容易搞混）**：

| 词表 | 取值 | 主体 |
| :--- | :--- | :--- |
| 本表的 `state` | `empty` / `lying` / `asleep` / `trace` | **一张床** |
| 下行 `state` 消息的取值 | `roaming` / `lying` / `asleep` / `trace` | **一个人** |

差别只在第一个值上：人可以说「不在床上但活着」（`roaming`），而对应那张床的状态是 `empty`（没有占用者）。**不要把 `roaming` 写进这张表**。

### 索引

| 索引 | 目的 |
| :--- | :--- |
| 主键 `bed_no` | 按床号直接寻址（认领、起身、单行读取） |
| 唯一索引 `owner_user_id` | 保证一个用户只能认领一张床；也是「我的床」的取行路径 |
| 索引 `state` | 睡痕查询（`state = 'trace'`）与占用者补录（`state IN ('lying','asleep')`） |
| 索引 `last_seen_at` | 归属释放扫描（30 天） |

**没有行数 = 床位数这条关系**：行数 ≈ 当前有主床数（几百行量级），远小于级容量（117 ~ 9558）。这是**惰性行**的直接收益：一次初始化不再需要写 9558 行（那会吃掉每日行写额度的一成）。

## 3. 表：`meta`

键值表（每个 key 一行）。**只在升级 / 降级 / 每日唤醒后写**，读快照时读这些行。

| key | 类型 | 含义 | 何时写 |
| :--- | :--- | :--- | :--- |
| `bed_count` | INTEGER | **当前级容量**（`../design/20-layout.md` §3.1 的 `capacity`）。决定世界里存在哪些床 | 升级、降级 |
| `daily_wake_at` | INTEGER | **最近一次已结算的每日唤醒边界**（epoch 毫秒 = 已结算的那个 UTC 20:00）。用于保证「一天最多降一级」 | 每日唤醒执行后 |

**不存「已用床数」这个计数**：判断「该不该升降级」用的是**与出生点同一套谓词**（有主或有占用：无主或归属已过期、无占用，见 §7）在**同一次全表读**里数出来的**已用床数**。于是只有一个真相源，也不存在「计数器与实际行数漂移」的窗口。代价是入场时多一次线性扫行（几百行量级，已接受；**不做缓存**，见 `../design/10-hall-runtime.md` §8、§9）。

**缺失或可疑时按需推导一次**：`bed_count` 由 `MAX(bed_no)` 反推所属的档；`daily_wake_at` 缺失视为「从未结算」→ 允许补跑一次。对象被驱逐后第一次用到时走这条路径。

## 4. 风控与台账三张表

语义、留存与告知口径见 `../design/70-privacy-risk.md`（唯一来源）。这里只描述结构与读写点。

### 4.1 表：`identity`

**一个人的入场台账**，一行一个身份。`hello` 成功时 UPSERT；**它是「来源」的载体，不是用户档案**（见 §5）。

| 字段 | 是否必选 | 数据类型 | 取值范围 | 备注 |
| :--- | :--- | :--- | :--- | :--- |
| `user_id` | 是 | TEXT | `u_` + 16 个十六进制字符 | 主键。**与服务端签发的身份逐字一致**（L1） |
| `first_seen_at` | 是 | INTEGER | epoch 毫秒 | 首次入场 |
| `last_seen_at` | 是 | INTEGER | epoch 毫秒 | 最近一次入场。台账排序键、留存判据 |
| `last_ip` | 否 | TEXT | IPv4 / IPv6 字面量 | `null` = 已过 90 天留存期被清空，或本地开发拿不到该头（L3） |
| `last_country` | 否 | TEXT | ISO-3166-1 α2；`T1` = TOR | 同上 |
| `ua_hash` | 否 | TEXT | 16 个十六进制字符 | UA 的 SHA-256 前 8 字节。**是遮挡不是匿名化** |

索引：`last_ip`（按网络反查）、`last_seen_at`（留存扫描；后台台账的 `ORDER BY last_seen_at DESC, user_id DESC` 第二键没有索引，靠排序——表上限是历史身份数、只有运维翻页会走到，暂不为它加复合索引）。

### 4.2 表：`block`

**黑名单本体**。与 `identity` 无外键关系——**台账被清理后封禁照样生效**。

| 字段 | 是否必选 | 数据类型 | 取值范围 | 备注 |
| :--- | :--- | :--- | :--- | :--- |
| `kind` | 是 | TEXT | `user` / `ip` | 联合主键之一 |
| `value` | 是 | TEXT | user_id 或 IP 字面量 | 联合主键之一。**不校验存在性** |
| `until_at` | 否 | INTEGER | epoch 毫秒 | **为空 = 永久**。非空时「是否生效」由 `until_at > now` **读取时推导** |
| `reason` | 是 | TEXT | 1~64 字符 | 运维填写，**不下发给被封者** |
| `created_at` | 是 | INTEGER | epoch 毫秒 | 写入时刻；同时是「改判」时的覆盖依据 |

索引：联合主键 `(kind, value)` 就是判定路径——入场时最多两个索引命中。

### 4.3 表：`admin_audit`

**运维动作的流水**，只写不改。首版只有 `block` / `unblock` 两种动作。

| 字段 | 是否必选 | 数据类型 | 取值范围 | 备注 |
| :--- | :--- | :--- | :--- | :--- |
| `id` | 是 | INTEGER | 自增 | 主键；前台分页的排序键 |
| `at` | 是 | INTEGER | epoch 毫秒 | 动作时刻 |
| `action` | 是 | TEXT | `block` / `unblock` | |
| `kind` / `value` | 是 | TEXT | 同 `block` | 作用对象 |
| `until_at` | 否 | INTEGER | epoch 毫秒 | 为空 = 永久 |
| `reason` | 否 | TEXT | 1~64 字符 | 解封时可能带说明 |
| `actor` | 是 | TEXT | 首版恒为 `admin` | 单令牌，没有账号表（见 `../api/30-api-admin.md` §1） |

### 4.4 三张表的读写点

| 时机 | 动作 |
| :--- | :--- |
| 每次页面加载（`/api/me`） | **读** `block`（最多两次索引命中），与厅满判定合并成一次 `entryStatus` 调用 |
| 每次成功入场（`hello`） | **写** `identity`（UPSERT）+ **读** `block`（兵底，防直接打 `/api/ws`） |
| 后台点封禁/解封 | **写** `block` + **写** `admin_audit`；随后由厅关闭命中的在线连接 |
| 每日唤醒 | **改** `identity`（90 天清空来源三列）+ **删** `block`（到期 + 30 天）+ **删** `admin_audit`（1 年） |

三条清理**并入既有的每日唤醒**，不新开唤醒（见 `../design/10-hall-runtime.md` §4）。

## 5. 为什么不建用户表

第一版中「一个人 = 一张床」，用户档案（昵称、外观）与床位一一对应。单独建一张用户表会形成 1:1 冗余表，**属于过度设计**。用户档案所需的全部字段已经落在 `bed` 行上。等出现「一个用户在多处都有床」或「用户资料页」时再拆表（见 `backlog.md`）。

**注意：§4.1 的 `identity` 不是这张被否决的用户表**。它不含昵称、外观、床位这类档案字段，也不参与任何业务判定（唯一消费者是运维台账与按网络反查）；用户档案仍然只在 `bed` 行上。两张表的区别正是「身份 ≠ 档案」。

## 6. 不落库的数据

| 数据 | 原因 |
| :--- | :--- |
| 位置与移动路径 | 高频变化；**醒着的人一定有活着的连接**，存在连接附加数据上即可 |
| 床位坐标 | **由布局函数现算**（`../design/20-layout.md` §4），不落库、不下发、没有场景文件 |
| 聊天内容 | **不存历史**（见 `backlog.md`）：服务端不存，**客户端也不再保留消息流**——聊天只在世界里以 8 秒气泡出现（见 `../ui/DESIGN.md` 的 `chat-bubble`） |
| 私聊内容 | 同上 |
| 情绪/表情事件 | 瞬时事件，无持久意义 |
| 归属的「已过期」 | 由时间戳推导，不写库（§7）。睡痕没有独立到期 |

## 7. 数据生命周期

| 事件 | 变化 |
| :--- | :--- |
| 首次躺下（无行） | **INSERT**：`state = 'lying'`，写 `owner_*`、`claimed_at`、`last_seen_at`、`sleep_started_at`、`updated_at`；**不写任何计数** |
| 每次上床（含从睡痕恢复） | 刷新 `owner_name` / `owner_appearance`（因为只有此时的昵称才可能被显示） |
| 自动或手动睡着 | `state → 'asleep'` |
| 起身 | `state → 'empty'`；`sleep_started_at` 清空；**保留归属** |
| 断线超宽限（在床上） | `state → 'trace'`；`updated_at` 写的是**宽限到期的时刻**（由 `last_seen_at + 宽限期` 推导），不是「发现它的时刻」。它不再是任何判据，只是「这件事本该何时发生」的记录 |
| 宽限期内重连（在床上） | `state` 保持 `lying` / `asleep`；位置退回床边（没有内存宽限记录，见 `../design/10-hall-runtime.md` §6） |
| 宽限已过后重连（床仍是自己的且是睡痕） | `state → 'asleep'`，归属与 `sleep_started_at` 不动。**为什么是 `asleep` 而不是 `lying`**：睡痕本身已经意味着「在床上睡过去了」（§5 「断线一律转睡痕」是同一条简化），而且「点了睡了再退出，回来还是睡下」是明确要求 |
| **睡痕没有到期这回事** | 睡痕跟归属同寿（30 天）。它只在三种情形下终结：主人回来（`lying` / `asleep`）、归属释放（`state → 'empty'`）、行被新人躺上改写。**没有任何按时间读取的推导** |
| 别人躺上一张「归属已过期」的床 | **直接覆盖**（UPSERT：写新的 `owner_*` 与占用）。归属过期同样只判定、不先释放 |
| **升级** | 入场前判定：**已用床数 ≥ 本档容量的 75%**（与出生点同一套谓词）且未到上限 → 取下一级容量写 `meta.bed_count`，广播 `resize`。**不写任何床位行**（新床都是无主空床） |
| **降级**（每日唤醒评估） | 最外圈那一级的床**全部无主且无占用**（占用清空只有一条路：归属 30 天释放）**且已用率 < 50%**、今天还没结算过（`daily_wake_at` < 最近一个 UTC 20:00）→ 取下 `meta.bed_count` + 写 `daily_wake_at`，广播 `resize` |
| **归属释放**（每日唤醒，UTC 20:00） | 一次 `UPDATE` 清空 `owner_*`、`sleep_started_at`，`state → 'empty'`（`last_seen_at` 为空或超过 30 天的行）。并对受影响的床广播 `bed`（`owned: false`） |
| 每次连接建立/断开 | 更新 `last_seen_at`（**不随心跳更新，避免写放大**） |
| **封禁生效** | 不动 `bed`。被封者的床走既有的 30 天自然释放，**不在封禁时释放**（见 `../design/70-privacy-risk.md` §5.1） |

**为什么归属释放仍然是一次批量任务，而不是纯推导**：判定「能不能躺」时确实按过期推导（`../design/config.md` §2），但**行不会自己消失**——「最外圈是否全空」需要一个周期性结算点才能结算（睡痕没有独立期限，它只跟着归属走）。每日唤醒本来就要为缩级评估存在，顺手一条 `UPDATE` 即可（见 `../design/10-hall-runtime.md`）。

## 8. 白送的副产品：睡眠记录

`sleep_started_at` + 起床时刻天然构成一条「睡眠时段」记录。第一版不做展示，但**不额外花钱**，将来做「一起睡了 N 小时」时零改表。

两个睡痕（或睡痕与在线睡着者）的时段重叠时长即为「共处时长」。

## 9. 存储量估算

| 项 | 量级 |
| :--- | :--- |
| 单厅行数 | ≈ 有主床数（几百），**不是级容量** |
| 单行大小 | 约 180 字节量级（去掉 `owner_tz` 后更小） |
| 风控三表行数 | `identity` ≈ 历史上出现过的身份数（万级是上限）；`block` / `admin_audit` 是人工动作，几十行量级 |
| 单厅数据量 | 几十 ~ 几百 KB，远低于 5 GB 免费额度 |

存储从来不是约束；**行读取次数与对象活跃时长才是**（见 `../design/architecture.md` §5）。
