# 接口设计：大厅 WebSocket 协议

## 1. 连接

| 项 | 约定 |
| :--- | :--- |
| 路径 | `/api/halls/{hallId}/ws` |
| 鉴权 | 握手时验证会话 cookie 的签名。**验签失败不升级连接** |
| 前置校验 | 未完成 18 岁自述 → 拒绝（`1002`）；未设置昵称 → 拒绝（`1003`）。理由：入厅广播必须带名字，没有名字的人不应进入大厅 |
| 归属校验 | 会话中的大区与路径中的厅必须一致，否则拒绝（`2001`） |
| 拒绝时的形态 | 前置校验不通过就**不升级**，直接返回 JSON（业务错误统一 HTTP 200）。浏览器的 WebSocket API 读不到这个响应体，所以客户端应当在建连之前就用 `/api/me` 确认自己够格进厅 |
| 心跳 | 使用平台的 WebSocket 自动响应能力处理协议层 ping/pong（不唤醒休眠、不产生计费）。**不定义应用层心跳** |
| 同一用户多连接 | **只保留最新的一条**：新连接握手成功时，旧连接被断开（关闭原因 `replaced`）。一个人 = 一张床 = 一份状态，两条连接会各带一份位置数据，不顶掉就会出现同一个 id 的两份状态 |

## 2. 握手

**首条上行消息必须是 `hello`**，携带场景标识。

| 行为 | 结果 |
| :--- | :--- |
| 首条不是 `hello` | 返回 `2004` 并断开 |
| 场景标识与服务端不一致 | 返回 `2003` 并断开 |
| 通过 | 服务端下发 `snapshot`（全量），此后只发增量 |

**在通过握手之前，服务端不向该连接转发任何房间消息。**

这个形态参考自 `WheatCloudSleep` 的场景包校验（源码中的 `CmdPackGuid` 与转发前的 `m_receivedPackGuid` 判断）。区别是：参考项目只用它做地图一致性校验，我们同时用它充当「连接必须先完成握手」的门槛。

## 3. 上行消息（客户端 → 服务端）

**上行只表达意图。** 服务端有权拒绝任何一条。

| t | 字段 | 说明 | 前置条件 |
| :--- | :--- | :--- | :--- |
| `hello` | `sceneGuid`, `tz` | 握手。`tz` 为 IANA 时区名（可选，与 HTTP 上报等价） | 必须是首条 |
| `walk` | `x`, `y` | 「我要去这一格」。**不是坐标上报，是目标声明**。会覆盖当前路径；目标为当前格时视为原地不动 | 已握手 |
| `lie` | `bedNo` | 「我要躺这张床」= **走过去 + 躺下**的复合意图（不在床边时会先寻路过去）。若该床尚未被认领，同时完成认领 | 不在床上 |
| `rise` | — | 起床 | 在床上 |
| `sleep` | — | 手动表示「我睡了」 | 在床上且清醒 |
| `chat` | `text` | 全局聊天 | 已握手。**睡着时不报错**：先自动醒，再照常发出 |
| `whisper` | `toId`, `text` | 私聊。`toId` 来自**点选**（选中某个人即成为私聊目标，见 `../ui/DESIGN.md`）。文本规则与 `chat` 完全相同（打码、长度、空消息） | 已握手（睡着时自动醒后处理）；对方不在厅 → `2005`（静默） |
| `emote` | `id` | 表情。`id` 为第一版固定的少量枚举值（定义在共享契约层） | 已握手（睡着时自动醒后处理）；**非法值静默丢弃：不回错误码** |

```json
{ "t": "walk", "x": 12, "y": 8 }
```

```json
{ "t": "lie", "bedNo": 42 }
```

**上行不含**：坐标同步、心跳、状态声明、身份声明、时间戳。这些要么由服务端计算，要么由平台处理。

### 3.1 枚举值（定义在共享契约层）

| 枚举 | 取值 | 说明 |
| :--- | :--- | :--- |
| 表情 `emote.id` | `wave` / `zzz` / `heart` / `cry` / `hug` | 非法值静默丢弃 |
| 外观 `appearance` | `a1` / `a2` / `a3` | 小人外观，第一版固定三种，**不提供用户选择入口** |
| 朝向（`pos.items` 第 4 位） | `0` 下 / `1` 左 / `2` 上 / `3` 右 | 小人朝向 |

## 4. 下行消息（服务端 → 客户端）

**下行表达服务端认定的事实，是唯一真源。**

前面六条描述**人**，`bed` 描述**床**，最后三条是消息与错误。

| t | 字段 | 何时发送 |
| :--- | :--- | :--- |
| `snapshot` | 见 §4.1 | 握手完成后（进入或重连） |
| `join` | `id`, `name`, `appearance`, `state`, `x`, `y`, `bedNo`, `online` | 有人进入厅。**只发给其他人**：自己不需要收到自己的 `join`（自己在 `snapshot.me` 里，`people` 也不含自己） |
| `leave` | `id`, `online` | 有人离开厅（**不在床上的人一断线就发**；或睡痕被清理） |
| `state` | `id`, `state`, `bedNo`, `x`, `y`, `online` | 某人显示态变化：躺下、起床、睡着、变成睡痕、睡痕恢复。**也发给本人**——自己的 `me` 要跟着变（`people` 里不含自己，收不到就永远不知道自己躺下了） |
| `pos` | `ts`, `items` | 位置节拍（每 100 ms 一条，**已合并**） |
| **`bed`** | `bedNo`, `owned` | **床位归属变化**：某张床被认领（`owned: true`）或归属被释放（`owned: false`）（见 §4.5） |
| `chat` | `id`, `text`, `ts` | 全局消息（发给厅内所有人，**含发送者本人**） |
| `whisper` | `fromId`, `toId`, `text`, `ts` | 私聊：**只发给发送者与接收者，两边各一条**，第三人零流量 |
| `emote` | `id`, `emoteId` | 表情：广播给厅内所有人（含自己），显示时长由客户端决定 |
| `error` | `code` | 见 `error-code.md` |

**`online`（在线人数）只挂在会改变它的三条消息上**：`join` / `leave` / `state`（外加 `snapshot` 里的 `hall.online`）。

它是**服务端的事实**，客户端从 `people` 推导不出来：`people` 里既有睡痕（人已离线），也有床上断线、还在宽限期里的人——两者都不是在线，但客户端分辨不出。

`state` 也必须带着它，因为**床上的人断线不广播任何东西**：人数降下来的唯一时点是宽限到期转睡痕（或睡痕醒来重连）那一条 `state`。

### 4.1 snapshot（全量，仅进入/重连时一次）

| 字段 | 是否必选 | 说明 |
| :--- | :--- | :--- |
| `sceneGuid` | 是 | 场景标识，客户端据此加载场景资源 |
| `serverTs` | 是 | 服务端当前时间（epoch 毫秒），客户端据此校准插值时钟 |
| `hall` | 是 | `{ id, name, timezone, capacity, online }` |
| `me` | 是 | `{ id, name, appearance, state, x, y, bedNo?, ownedBedNo? }` 自己的完整状态。**`bedNo` 是占用**（我在床上时才有），**`ownedBedNo` 是归属**（我的床是哪张，走路时也带着）——客户端靠它在厅里走动时也能画出「我的床」的暖灯标记 |
| `ownedBeds` | 是 | **归属表**：bedNo 数组，包含**所有有主的床**（见 §4.2）。**不带名字**：归属不需要名字，名字全部来自下面的人 |
| `people` | 是 | 厅内可见的人：`[{ id, name, appearance, state, x, y, bedNo? }]`。**含睡痕条目**——服务端在生成快照时按床位的 `state` 索引取出 `trace` 行并填入（名字取自 `owner_name`）；在线的人则来自活着的连接。**不含自己**（自己在 `me` 里），因此客户端不必去重 |

### 4.2 两个正交维度：归属 与 占用

「一张床」在客户端需要两个互不相干的信息：

| 维度 | 回答什么 | 载体 | 变化频率 |
| :--- | :--- | :--- | :--- |
| **归属** | 这张床是谁的？ | `ownedBeds`（快照）+ `bed` 消息 | 极低（认领、30 天释放） |
| **占用** | 此刻床上有人吗？是谁？什么姿势？ | `people` 列表（快照）+ `join`/`leave`/`state` | 频繁 |

**客户端不存「床的状态」，而是在渲染时把两个维度派生出来。**

这样切分的直接好处：

- **不需要为「床」维护一份状态机**，也就不存在「床的状态与人的状态不同步」这类 bug
- 睡痕天然可表达：一个已离线的人仍然留在 `people` 里、`state` 为 `trace`、带着 `bedNo`
- 睡痕被次日清理时，服务端只需发一条 `leave`——床上的占用自动消失，而床本身仍是那个人的（归属表没动）
- 归属被释放时，服务端发一条 `bed` 消息把这张床移出归属表

**`ownedBeds` 为什么发全部有主的床**（而不是只发被占用的）：

- 「有主但空的床」和「无主的空床」在视觉上必须区别对待——前者是**某个人的位置**，后者是空地（见 `../ui/DESIGN.md`）
- 快照只在进入时发一次，多几十行不构成压力
- 反过来，只发被占用的床会让「谁的位置」这个信息在主人不在时凭空消失

**归属为什么带名字（或者不带）**：

归属只是一张床的「有主/无主」，**不需要名字**。而所有需要显示的名字都来自「人」那一侧：

| 要显示的名字 | 来源 |
| :--- | :--- |
| 在场的人（含躺在床上的人） | 该人的连接（握手时从会话读出） |
| **睡痕的人** | 服务端内存里已经没有他了 → **只能从床位的 `owner_name` 快照读** |

于是数据库里的 `owner_name` 有一个、且只有一个消费者：**生成快照时给睡痕条目填名字**。名字在协议里只有这一个来源（`people`），不会出现「同一人两个名字不同步」的问题。

**`ownedBeds` 里不出现的床 = 无主空床**（客户端从场景数据得知全部床位坐标）。

**去重规则**：睡痕行若对应的人此刻在线（例如刚重连），该行**不进** `people`——在线连接是更新的真相（见 `10-hall-runtime.md` §3）。

### 4.3 睡痕条目从哪里来（服务端侧）

客户端要让「人」与「床」发生关联，靠的是 **`people` 条目里的 `bedNo` 字段**（不需要额外关联表）。所以服务端必须保证：**每一个占用者都有一条 `people` 条目**。三类占用者的来源不同：

| 占用者 | 来源 | 需要查库吗 |
| :--- | :--- | :--- |
| 站在/走在地上的人 | 活着的连接 | 否 |
| 躺在床上且在线（`lying` / `asleep`） | 活着的连接（「在床上」与「当前姿势」存在连接附加数据里） | 否 |
| **躺/睡在床上但连接已断、仍在宽限期内** | 没有连接 → 只能查库：取出 `state` 为 `lying` / `asleep` 的床位行，按 `last_seen_at + 宽限期` 判断该不该已经变成睡痕 | **是** |
| **睡痕（`trace`，已离线）** | **没有连接 → 只能查库**：按 `state` 索引取出所有 `trace` 行，用 `owner_user_id` 作 id、`owner_name` 作名字、`bed_no` 作 bedNo | **是** |

第三行是前两行的兜底：**连接附加数据是可以丢的**（对象空闲约 10 秒后即可休眠，宽限期比它长），所以「床上有人」这件事必须有一条只在数据库里的真相——`state` 为 `lying` / `asleep` 的床位行。判断这些人是否已经被断开、断开多久，只看 `last_seen_at`（连接建立与断开时各写一次）。

由此得到两条实现约束：

1. **`sleep_trace` 的查询不是全表扫描**，而是走 `state` 索引（否则每次快照都要读 256 行，撞上行读取配额）
2. **睡痕行数决定快照里的额外条目数**：约等于「昨晚在床上睡着且没有主动起身的人」。若某天这个数字变得很大（例如宽限期设置得过短导致大量误判），快照体积会跟着涨——这是一个值得监控的指标

**清除睡痕后不要忘记一致性**：睡痕被清理时服务端发 `leave`（人从列表消失），那张床仍在 `ownedBeds` 里（归属没变），于是它自然回落为「有主但空着」。

```json
{
  "t": "snapshot",
  "sceneGuid": "dorm-asia-01",
  "serverTs": 1735689600000,
  "hall": { "id": "asia-1", "name": "亚洲厅", "timezone": "Asia/Shanghai", "capacity": 256, "online": 37 },
  "me": { "id": "u_7f3a91", "name": "小明", "appearance": "a1", "state": "roaming", "x": 12, "y": 8 },
  "ownedBeds": [3, 42],
  "people": [
    { "id": "u_1a2b3c", "name": "阿雅", "appearance": "a2", "state": "asleep", "bedNo": 3 },
    { "id": "u_9d8e7f", "name": "夜猫", "appearance": "a1", "state": "roaming", "x": 20, "y": 14 }
  ]
}
```

### 4.4 state 的消息语义（人）

`state` 的取值只有四种，与设计文档里的派生显示态一一对应：

| state 值 | 含义 | 是否带 bedNo | 是否带 x/y |
| :--- | :--- | :--- | :--- |
| `roaming` | 不在床上（站着或走动） | 否 | 是 |
| `lying` | 在床上，睁眼（失眠的人的真实状态） | 是 | 否（即为床的位置） |
| `asleep` | 在床上，闭眼睡着 | 是 | 否 |
| `trace` | **睡痕**：在床上但已离线超过宽限期 | 是 | 否 |

**睡着的人不需要位置**：他的位置就是他的床。因此 `lying` / `asleep` / `trace` 都不带坐标，客户端直接按床位坐标渲染。

**睡痕是「人」的一种显示态**：宽限超时时若人在床上，服务端**不发 `leave`**，而是把他留在 `people` 里、`state` 改为 `trace`。这样任何在线观者都能立刻看到他变成了睡痕。

**地上的人不等宽限**：不在床上的人一断线就发 `leave`（小人立刻消失）。理由见 `../design/10-hall-runtime.md` §6：宽限能兑现的前提是「到期时还有个东西记得他」，而地上的人没有任何持久真相（床位行只服务于床上的人）。

**注意与数据库词表的区别**：上表描述的是**一个人**的显示态；数据库 `bed.state` 描述的是**一张床**的占用，其取值没有 `roaming`（人不在床上时那张床就是 `empty`）。两个词表不要混用，详见 `../db/schema.md`。

### 4.5 bed 消息（归属变更）

```json
{ "t": "bed", "bedNo": 42, "owned": true }
```

| 场景 | 发送内容 |
| :--- | :--- |
| 有人首次躺下完成认领 | `{ bedNo, owned: true }` |
| 某张床的归属被释放（30 天未出现） | `{ bedNo, owned: false }` |

**为什么归属要单独一条消息**：它与人无关。认领之后那个人可能就起身走开了，甚至在 30 天后永远不再出现——但「这张床是谁的」这件事仍然必须对所有人可见。放进 `state` 里会把两个正交维度绑死（也正是「有主但空的床」这种状态无处表达的原因）。

**为什么不带名字**：归属不需要名字；而睡痕的名字走的是 `people` 里的条目（服务端从 `owner_name` 快照读出）。少一个字段就少一个不一致源。

频率极低（一夜几十条），不需要合并。

### 4.6 pos 消息（批量）

```json
{ "t": "pos", "ts": 1735689600000, "items": [[17, 12, 8, 1], [23, 15, 9, 3]] }
```

| 字段 | 说明 |
| :--- | :--- |
| `ts` | 本批次的权威时刻 |
| `items` | `[用户id, x, y, 朝向]` 的数组 |
| 频率 | 目标每 100 ms 一条（仅在厅内有人走动时才有） |

**合并是关键**：无论这一周期里有 1 个人还是 50 个人移动，只发这一条。客户端按 `ts` 对每个人的位置做插值。

**不得假设固定帧间隔**：服务端的节拍只是一个**尽力而为的唤醒**，云端计时本身不精确，两次 `pos` 的真实间隔会抖动。因此：

- 服务端推进的格数是「自上次推进以来**实际经过的时间**」的函数，不是「拍数」的函数——节拍抖动只影响平滑度，不影响移动速度
- 客户端必须按 `ts` 插值，不得按「收到两条消息的间隔」推进动画。实现上建议**渲染时往后坐一个 `TICK_MS`**：收到新批次的瞬间，画面正好走完【上一批, 本批】这一格，否则小人会每 100 ms 跳一格（代价是比服务端晚 100 ms，不到半格）

### 4.7 whisper 与 emote 的投递规则

| 项 | 全局聊天 | 私聊 | 表情 |
| :--- | :--- | :--- | :--- |
| 收件人 | 厅内所有人（含发送者） | **发送者 + 接收者**（各一条、结构相同） | 厅内所有人（含发送者） |
| 文本过滤 | 打码不拦截 | **与聊天同一套规则**（打码、长度、空消息），只是投递范围不同 | 不适用 |
| 目标不存在 | — | `2005`，**静默**：发送者拿不到任何反馈，探测者也无从判断 | — |
| 参数非法 | — | — | **静默丢弃、不回错误码**（与「非法值静默丢弃」一致，避免给探测者反馈） |
| 睡着时 | 先自动醒后处理 | 同左 | 同左 |

**表情不落库、服务端不记任何状态**：它是一次瞬时事件，显示多久完全由客户端按 `EMOTE_MS` 推导（到期即不画），因此不需要定时器，也不会因为对象休眠而「卡住一个表情」。

## 5. 客户端状态机（渲染侧）

本地状态只有三块，都不需要「床的状态机」：

```
me            ：自己的身份与状态（含 bedNo）
ownedBeds     ：归属集合 Set<bedNo>
people        ：可见的人 Map<id, { name, state, x, y, bedNo? }>
```

| 收到 | 动作 |
| :--- | :--- |
| `snapshot` | 用服务端内容整体覆盖三块状态 |
| `join` | 插入/覆盖 `people` 条目；把 `hall.online` 刷新为消息里的值 |
| `leave` | 删除 `people` 条目（该床上的占用随之消失）；刷新 `hall.online` |
| `state` | 更新 `people` 条目的显示态（含 `trace`）；刷新 `hall.online` |
| `pos` | 更新 `people` 条目的位置，按 `ts` 插值 |
| `bed` | 更新 `ownedBeds` 集合：`owned` 为真则加入，`false` 则移出 |
| `chat` / `whisper` / `emote` | 追加到消息流或触发世界内表现。**追加时就把发送者当时的名字固化到该行**（否则对方离开后去 `people` 里查不到，那行的名字会变空） |
| `error` | 按错误码映射为提示（静默类不提示） |

**床位视觉的派生规则**（两个维度各自独立，不要合并成一个「床位状态」）：

```
轮廓 = 床上有人（lying/asleep） → line
       床上是睡痕（trace）      → trace
       床上无人 + 有主          → claimed
       床上无人 + 无主          → 不画

暖灯小标记 = 该床是我的（me.bedNo 匹配） → 画；否则不画
名字       = 床上有人 且 不是我自己       → 画；否则不画
小人不透明度 = 睡痕 → 降低；其余 → 正常
```

| 情形 | 轮廓 | 暖灯小标记 | 名字 |
| :--- | :--- | :--- | :--- |
| 无主空床 | 不画 | 无 | 不画 |
| 别人的床，空着 | `claimed` 淡 | 无 | 不画 |
| 我的床，空着（我在厅里走动） | `claimed` 淡 | **有** | 不画 |
| 别人的床，有人在睡 | `line` 亮 | 无 | 画 |
| 别人的床，睡痕 | `trace` | 无 | 画，更暗（小人同步降不透明度） |
| 我的床（我自己躺着） | `line` 亮 | **有** | **不画**（我知道我是谁） |

三个设计意图：

1. **「有人睡」比「谁的床」重要**，所以轮廓梯次按占用强度排（`line` > `trace` > `claimed` > 不画）
2. **「是我的」用一个独立的小标记表达**，不参与轮廓梯次——否则暖灯色会因为在冷底上更抢眼而把「谁的床」排到「有人睡」前面（完整理由与对比度数据见 `../ui/DESIGN.md`）
3. **文字只出现在有人的床上**（凌晨大约几十张），有主空床只靠轮廓表达「这里是某个人的位置」

**渲染顺序**（不要遍历 256 张床去找占用者）：

```
1. 画场景（地板、墙、床的线稿本体）
2. 遍历 ownedBeds      → 每张有主的床画淡轮廓
3. 遍历 people 中带 bedNo 的条目 → 该床改画占用轮廓（亮线 / 痕色），画躺姿小人
4. 遍历 people 中无 bedNo 的条目 → 在地上画站/走的小人（不画名字）
5. 画自己的暖灯色小标记（小人脚下、自己的床角）
6. 若存在选中对象 → 在其上方画唯一一个名字气泡
```

第 3 步就是「床上有占用者时显示谁」的全部实现：**床号与名字在同一条 `people` 记录里**；第 4 步的漫游者自然就不会有名字。

**漫游者为什么默认不显示名字**：名字是身份信息，而「看到有人和我一样醒着」靠的是看到人本身。一百个飘动的标签会把大厅变成名单，且每个标签都要跟随移动的小人重排。名字在需要时点一下就出来（见 `../ui/DESIGN.md` 的「名字什么时候出现」）。

**服务端发消息的顺序约束**：认领时归属与占用同源，必须**先发 `bed`（归属）再发 `state`（占用）**。反了的话，客户端会短暂渲染出「这张床有人、但不在归属表里」的矛盾状态。

**连接断开** → 宽限期内自动重连；重连成功后以新的 `snapshot` 为准（不做增量补偿）。

**不做增量补偿**：WebSocket 跑在 TCP 上，消息可靠且有序，正常断线不会静默丢包。重连时直接以新快照覆盖本地状态，无需增量重放。这样也避免了「断线期间漏掉的事件」这类状态的复杂度。

## 6. 客户端预测的边界

| 允许 | 不允许 |
| :--- | :--- |
| 对**自己**的小人做乐观移动（点完立刻走，不等服务端确认） | 把自己的预测结果当作事实广播给他人 |
| 服务端权威值到达后做平滑纠正 | 用本地预测覆盖服务端下发的位置 |

**自己以外的一切都以服务端消息为准。**

## 7. 限流与异常

| 情况 | 行为 |
| :--- | :--- |
| 上行超过 5 条/秒 | 丢弃 + 返回 `4002`（静默处理，不重复提示） |
| 越界/非法目标格 | 丢弃 + 返回对应错误码；不影响连接 |
| 场景不匹配 | 返回 `2003` 并断开（客户端应刷新页面） |
| 未握手就发业务消息 | 返回 `2004` 并断开 |

## 8. 消息体积预估

| 消息 | 量级 |
| :--- | :--- |
| `snapshot`（100 人在线、200 张床有主） | `ownedBeds` 是纯数字数组，约 1 KB；`people` 约 6 KB。合计 10 KB 以内，**只在进入时发一次** |
| `pos`（20 个移动者） | 数百字节，每 100 ms 一条 |
| `bed` | 约 40 字节，一夜几十条 |
| `chat` | 数百字节 |

按 100 并发用户、每人每分钟 2 条意图估算，一晚 8 小时约 10 万条上行。**出站消息不计费、入站消息按 20:1 折算**，因此这个量级对请求额度几乎没有压力（详见 `../design/architecture.md` §5）。

**唯一需要注意的是快照体积**：它在进入瞬间产生约 10 KB 下行，且不计费（出站免费）。因为 `ownedBeds` 只是数字数组，两个维度分开后比原来带名字的写法更小。若某天厅容量大幅提高再评估——现在不需要（YAGNI）。
