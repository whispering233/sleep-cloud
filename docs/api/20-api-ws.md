# 接口设计：大厅 WebSocket 协议

## 1. 连接

| 项 | 约定 |
| :--- | :--- |
| 路径 | `/api/ws`（**只有一个厅，路径里不带厅标识**） |
| 鉴权 | 握手时验证会话 cookie 的签名。**验签失败不升级连接** |
| 前置校验 | 未完成 18 岁自述 → 拒绝（`1002`）；未设置昵称 → 拒绝（`1003`）。理由：入厅广播必须带名字，没有名字的人不应进入大厅 |
| 厅满 | 入场前由 `/api/me` 判定（`2002`）：级表触顶且无空床时不让人建连再被踢 |
| 拒绝时的形态 | 前置校验不通过就**不升级**，直接返回 JSON（业务错误统一 HTTP 200）。浏览器的 WebSocket API 读不到这个响应体，所以客户端应当在建连之前就用 `/api/me` 确认自己够格进厅 |
| 心跳 | 协议层 ping/pong 由平台自动响应（不唤醒休眠、不产生计费）。**不做常驻应用层心跳**——100 人各发 20 秒一次心跳会让对象永远等不到 10 秒空闲、整夜不休眠（`../design/architecture.md` §5.4）。只保留一条**按需探活**的应用层 `ping`（见 §5） |
| 同一用户多连接 | **只保留最新的一条**：新连接握手成功时，旧连接被断开（关闭原因 `replaced`）。一个人 = 一张床 = 一份状态，两条连接会各带一份位置数据，不顶掉就会出现同一个 id 的两份状态 |

## 2. 握手

**首条上行消息必须是 `hello`**，携带**布局版本号**。

| 行为 | 结果 |
| :--- | :--- |
| 首条不是 `hello` | 返回 `2004` 并断开 |
| 布局版本与服务端不一致 | 返回 `2003` 并断开 |
| 通过 | 服务端下发 `snapshot`（全量），此后只发增量 |

**为什么是「布局版本」而不是「场景标识」**：几何由共享的纯函数生成（`../design/20-layout.md` §4），没有场景文件可校验；版本号防的是「旧 bundle 连上新几何」——那会让客户端把床画在服务端认为不是床的地方。改动布局公式或级表就必须递增此版本号。

**在通过握手之前，服务端不向该连接转发任何房间消息。**

## 3. 上行消息（客户端 → 服务端）

**上行只表达意图。** 服务端有权拒绝任何一条。

| t | 字段 | 说明 | 前置条件 |
| :--- | :--- | :--- | :--- |
| `hello` | `layoutVersion` | 握手。必须是首条 | — |
| `ping` | — | **探活**：服务端只回一条 `pong` 给这条连接。**它不是输入**——不刷新 `lastInputAt`（躺在床上的人不会因为探活而推迟自动睡着），也不写任何业务状态；但**与业务意图共用 §7 的 5 条/秒窗口**，超限时**静默丢弃**。客户端只在**怀疑连接已死**时发（见 §5） | 已握手（握手前 → `2004` 并断开） |
| `walk` | `x`, `y` | 「我要去**这个世界像素点**」。**不是坐标上报，是目标声明**。服务端把它吸附到街网；会覆盖当前路径；吸附后与当前点相同则视为原地不动 | 已握手 |
| `hop` | `bedNo`（可选） | 「**一跳**」= 直接把我放到某张床**脚前的走道中心**（**不寻路、不推进**：跨厅走路在第 1 级是 10.7s、末档 93s，靠走解决不了）。**不带 `bedNo` = 我自己那张床**（动作行那条）；带上 = 那张床的脚前——**与归属和占用无关**（跳到别人床脚站着完全合法）。在床上时先起身（同「点地面」那条）；**越界（`3001`）或「不带床号而我没有归属」时静默忽略** | 已握手。床号范围由**客户端**先按 `bedCount` 拦一道（它知道当前床位数） |
| `lie` | `bedNo` | 「我要躺这张床」= **走过去 + 躺下**的复合意图（不在床边时会先寻路过去）。若该床尚未被认领（或归属已过期、睡痕已过期），同时完成认领；**我已有另一张床 → 这是一次换床**（旧床当场释放，见 §4.5）；**在床上时先自动起身**（同「点地面」那条）。**换床的入口只在客户端**（换床模式，见 §4.5），服务端看不到模式、语义不因此改变 | **点自己正躺着的那张床 → `3004`**（静默）；在床上点别的床 = 自动起身后过去；距上次认领不足 10 秒且目标是另一张无主的床 → `3008`（可恢复） |
| `rise` | — | 起床 | 在床上 |
| `sleep` | — | 手动表示「我睡了」 | 在床上且清醒 |
| `chat` | `text` | 全局聊天 | 已握手。**睡着时不报错**：先自动醒，再照常发出 |
| `whisper` | `toId`, `text` | 私聊。`toId` 来自**点选**（选中某个人即成为私聊目标，见 `../ui/DESIGN.md`）。文本规则与 `chat` 完全相同（打码、长度、空消息） | 已握手（睡着时自动醒后处理）；对方不在厅 → `2005`（静默） |

```json
{ "t": "walk", "x": 1234.5, "y": 287.0 }
```

```json
{ "t": "lie", "bedNo": 42 }
```

**上行不含**：坐标同步、常驻心跳、状态声明、身份声明、时间戳、朝向。这些要么由服务端计算，要么由平台处理。**探活是唯一的心跳类上行**，且只在可疑时发一条。

### 3.1 枚举值（定义在共享契约层）

| 枚举 | 取值 | 说明 |
| :--- | :--- | :--- |
| 外观 `appearance` | `boy` / `girl` | **入场层自己选**（两个选项，见 `../ui/DESIGN.md` 的 `entry-overlay`）；**没选的按 `user_id` 派生**——回落到同一个确定性哈希，同一个用户永远同一个外观。厅内不可改选（与改名一致） |

**没有朝向**：小人素材是「大头 + 简化四肢」的单张图，走动靠轻微的缩放/摆动表现（与参考实现一致），因此协议不携带朝向。

## 4. 下行消息（服务端 → 客户端）

**下行表达服务端认定的事实，是唯一真源。**

前面六条描述**人**，`bed` 与 `resize` 描述**厅与床**，最后三条是消息与错误。

| t | 字段 | 何时发送 |
| :--- | :--- | :--- |
| `snapshot` | 见 §4.1 | 握手完成后（进入或重连） |
| `join` | `id`, `name`, `appearance`, `state`, `x`, `y`, `bedNo`, `online` | 有人进入厅。**只发给其他人**：自己不需要收到自己的 `join`（自己在 `snapshot.me` 里，`people` 也不含自己） |
| `leave` | `id`, `online` | 有人离开厅（**不在床上的人一断线就发**；睡痕到期时也发） |
| `state` | `id`, `state`, `bedNo`, `x`, `y`, `online` | 某人显示态变化：躺下、起床、睡着、变成睡痕、睡痕恢复。**也发给本人**——自己的 `me` 要跟着变（`people` 里不含自己，收不到就永远不知道自己躺下了） |
| `pos` | `ts`, `items` | 位置节拍（每 100 ms 一条，**已合并**）：`[用户id, x, y]`，世界像素 |
| `bed` | `bedNo`, `owned` | **床位归属变化**：某张床被认领（`owned: true`）或归属被释放（`owned: false`）（见 §4.5） |
| **`resize`** | `bedCount` | **厅的床位数变化**：升级（外圈加床）或降级（砍掉最外圈）。见 §4.6 |
| `chat` | `id`, `text`, `ts` | 全局消息（发给厅内所有人，**含发送者本人**）。客户端以**气泡 8 秒**呈现（同人后来的消息覆盖前一条） |
| `whisper` | `fromId`, `toId`, `text`, `ts` | 私聊：**只发给发送者与接收者，两边各一条**，第三人零流量。同样以气泡呈现（只在这两人头上，加「悄悄话」前缀） |
| `error` | `code` | 见 `error-code.md` |
| `pong` | `ts` | **探活回执**：只回给发出 `ping` 的那一条连接，不广播。`ts` 是服务端回执时刻（客户端不用它校准时钟——时钟锚点只有 `snapshot.serverTs`） |

**`online`（在线人数）只挂在会改变它的三条消息上**：`join` / `leave` / `state`（外加 `snapshot` 里的 `hall.online`）。

它是**服务端的事实**，客户端从 `people` 推导不出来：`people` 里既有睡痕（人已离线），也有床上断线、还在宽限期里的人——两者都不是在线，但客户端分辨不出。

`state` 也必须带着它，因为**床上的人断线不广播任何东西**：人数降下来的唯一时点是宽限到期转睡痕（或睡痕醒来重连）那一条 `state`。

### 4.1 snapshot（全量，仅进入/重连时一次）

| 字段 | 是否必选 | 说明 |
| :--- | :--- | :--- |
| `layoutVersion` | 是 | 布局版本号，客户端据此自检几何是否与本机一致 |
| `serverTs` | 是 | 服务端当前时间（epoch 毫秒），客户端据此校准插值时钟 |
| `hall` | 是 | `{ bedCount, online }`。**没有厅名**（单厅之后它只是产品名，HUD 不显示，见 `../ui/DESIGN.md`） |
| `me` | 是 | `{ id, name, appearance, state, x, y, bedNo?, ownedBedNo? }` 自己的完整状态。**`bedNo` 是占用**（我在床上时才有），**`ownedBedNo` 是归属**（我的床是哪张，走路时也带着）——客户端靠它在厅里走动时也能画出「我的床」的暖灯标记 |
| `ownedBeds` | 是 | **归属位图**（§4.2）：第 `bedNo` 位为 1 表示该床有主。base64 编码 |
| `people` | 是 | 厅内可见的人：`[{ id, name, appearance, state, x, y, bedNo?, traceUntil? }]`。**含睡痕条目**——服务端按床位 `state` 索引取出未过期的 `trace` 行并带上 `traceUntil`；在线的人则来自活着的连接。**不含自己**（自己在 `me` 里），因此客户端不必去重 |

```json
{
  "t": "snapshot",
  "layoutVersion": "room-1",
  "serverTs": 1735689600000,
  "hall": { "bedCount": 114, "online": 37 },
  "me": { "id": "u_7f3a91", "name": "小明", "appearance": "boy", "state": "roaming", "x": 812.5, "y": 430 },
  "ownedBeds": "SAAAAA==",
  "people": [
    { "id": "u_1a2b3c", "name": "阿雅", "appearance": "girl", "state": "asleep", "bedNo": 3 },
    { "id": "u_9d8e7f", "name": "夜猫", "appearance": "boy", "state": "trace", "bedNo": 8, "traceUntil": 1735728000000 },
    { "id": "u_5c4d3e", "name": "数羊", "appearance": "boy", "state": "roaming", "x": 1200, "y": 640 }
  ]
}
```

### 4.2 两个正交维度：归属 与 占用

「一张床」在客户端需要两个互不相干的信息：

| 维度 | 回答什么 | 载体 | 变化频率 |
| :--- | :--- | :--- | :--- |
| **归属** | 这张床是谁的？ | `ownedBeds` 位图（快照）+ `bed` 消息 | 极低（认领、30 天释放） |
| **占用** | 此刻床上有人吗？是谁？什么姿势？ | `people` 列表（快照）+ `join`/`leave`/`state` | 频繁 |

**客户端不存「床的状态」，而是在渲染时把两个维度派生出来。** 这样切分的好处：不需要为「床」维护一份状态机，也就不存在「床的状态与人的状态不同步」这类 bug；睡痕天然可表达（一个已离线的人仍在 `people` 里、`state` 为 `trace`、带着 `bedNo`）。

**归属为什么用位图编码**：床位数会涨到 9558。`bedNo` 数组在 9558 张床全有主时是 9558 个数字（约 50 KB JSON），而位图只有 `ceil(9558/8) = 1195` 字节（base64 后约 1.6 KB）。快照只在进入时发一次，但没必要为此付 50 KB。

**睡痕为什么带 `traceUntil`**：睡痕到期（TTL 12 小时）**不改库、不广播**（见 `../design/config.md` §2）。服务端在生成快照时按 `updated_at + TRACE_TTL_MS` 过滤掉已过期的睡痕，并给未过期的带上**绝对到期时刻**；客户端拿自己的 `clockOffsetMs` 与之比较，到点让睡痕自行淡出。于是「睡痕消失」这件事在整个系统里没有任何定时器。

**归属为什么带名字**：不带。所有需要显示的名字都来自「人」那一侧：在场的人来自连接；**睡痕的人服务端内存里已经没有他**，只能从床位的 `owner_name` 快照读。于是 `owner_name` 只有一个消费者：生成快照时给睡痕条目填名字。

**`ownedBeds` 里为 0 的位 = 无主空床；`bedNo ≥ bedCount` 的位无意义**（位图只编码到 `bedCount−1`）。

### 4.3 三类占用者的来源（服务端侧）

| 占用者 | 来源 | 需要查库吗 |
| :--- | :--- | :--- |
| 站在/走在地上的人 | 活着的连接 | 否 |
| 躺在床上且在线（`lying` / `asleep`） | 活着的连接（「在床上」与「当前姿势」存在连接附加数据里） | 否 |
| **躺/睡在床上但连接已断、仍在宽限期内** | 没有连接 → 只能查库：取出 `state` 为 `lying` / `asleep` 的床位行，按 `last_seen_at + 宽限期` 判断该不该已经变成睡痕 | **是** |
| **睡痕（`trace`）** | 没有连接 → 只能查库：按 `state` 索引取出 `trace` 行（**并过滤掉 `updated_at + TRACE_TTL_MS` 已过的**），用 `owner_user_id` 作 id、`owner_name` 作名字、`bed_no` 作 bedNo、`updated_at + TRACE_TTL_MS` 作 `traceUntil` | **是** |

第三行是前两行的兜底：**连接附加数据是可以丢的**（对象空闲约 10 秒后即可休眠，宽限期比它长），所以「床上有人」必须有一条只在数据库里的真相——`state` 为 `lying` / `asleep` 的床位行。

**睡痕行数决定快照里的额外条目数**：约等于「昨晚在床上睡着且没有主动起身、且断线不到 12 小时的人」。这是一个值得监控的指标（行数暴增说明宽限期或 TTL 设置不合理）。

**去重规则**：睡痕行若对应的人此刻在线（例如刚重连），该行**不进** `people`——在线连接是更新的真相。

### 4.4 state 的消息语义（人）

| state 值 | 含义 | 是否带 bedNo | 是否带 x/y |
| :--- | :--- | :--- | :--- |
| `roaming` | 不在床上（站着或走动） | 否 | 是 |
| `lying` | 在床上，睁眼（失眠的人的真实状态） | 是 | 否（即为床的位置） |
| `asleep` | 在床上，闭眼睡着 | 是 | 否 |
| `trace` | **睡痕**：在床上但已离线超过宽限期（未过 TTL） | 是 | 否 |

**睡着的人不需要位置**：他的位置就是他的床。因此 `lying` / `asleep` / `trace` 都不带坐标，客户端直接按床位坐标渲染。

**睡痕是「人」的一种显示态**：宽限超时时若人在床上，服务端**不发 `leave`**，而是把他留在 `people` 里、`state` 改为 `trace`。这样任何在线观者都能立刻看到他变成了睡痕。

**地上的人不等宽限**：不在床上的人一断线就发 `leave`（小人立刻消失）。理由见 `../design/10-hall-runtime.md`：宽限能兑现的前提是「到期时还有个东西记得他」，而地上的人没有任何持久真相。

**注意与数据库词表的区别**：上表描述的是**一个人**的显示态；数据库 `bed.state` 描述的是**一张床**的占用，其取值没有 `roaming`。两个词表不要混用，详见 `../db/schema.md`。

### 4.5 bed 消息（归属变更）

```json
{ "t": "bed", "bedNo": 42, "owned": true }
```

| 场景 | 发送内容 |
| :--- | :--- |
| 有人首次躺下完成认领 | `{ bedNo, owned: true }` |
| **换床**（我已有别的床，在一张无主的床上躺下） | **两条，顺序固定**：先 `{ bedNo: 旧床, owned: false }`，再 `{ bedNo: 新床, owned: true }` |
| 某张床的归属被释放（30 天未出现，每日唤醒批量释放） | `{ bedNo, owned: false }` |

**换床为什么是两条、而且顺序固定**：释放必须走在认领之前——否则客户端会瞬时持有两张有主床（一人一床的唯一索引在服务端守得住，但客户端的暖标记会短暂指两张床）。

**换床的入口是一个客户端闸门，不是协议的一部分**：服务端看不到「换床模式」，它对 `lie` 的判定与从前逐字相同（躺到另一张可认领的床就是换床）。客户端只在换床模式内为另一张无主空床发出 `lie`；模式外的那一下轻点被本地拦下并给一句提示——因为它要付的代价是**旧床归属当场释放**（别人可以立刻捡走），不该由一次误点承担。代价是**缓存里的老 bundle 仍会点空床即换床**：这是可接受的过渡态（换床不是越权动作，不需要服务端再设一道闸）。

**为什么归属要单独一条消息**：它与人无关。认领之后那个人可能就起身走开了，甚至在 30 天后永远不再出现——但「这张床是谁的」仍然必须对所有人可见。放进 `state` 里会把两个正交维度绑死（也正是「有主但空的床」这种状态无处表达的原因）。

**为什么不带名字**：归属不需要名字；睡痕的名字走 `people` 条目。少一个字段就少一个不一致源。

**注意**：归属被*判定为过期*（30 天）时**不发** `bed` 消息——判定是读取时推导，只有每日唤醒真正把行清掉时才广播（一次一条批量消息里的若干条 `bed`）。

### 4.6 resize 消息（床位伸缩）

```json
{ "t": "resize", "bedCount": 161 }
```

| 场景 | 触发 | 内容 |
| :--- | :--- | :--- |
| **升级** | 入场前判定：**已用床数 ≥ 本档容量的 75%**（与出生点同一套谓词）且未到上限 → 取下一级容量 | 新的 `bedCount` |
| **降级** | 每日唤醒评估：最外圈那一级的床全部无主且无占用（「过期即视为空」）**且已用率 < 50%**，该次 20:00 尚未结算过 → 取下 `bedCount` | 新的 `bedCount` |

**为什么只需要一个数字**：升级新增的那一圈床**全是无主空床**，所以归属位图与占用都不需要变化——客户端拿到新 `bedCount` 后，按布局函数把新床画成虚线空床即可。降级只会砍掉无主无占用的床，同理。

**升级不移动任何既有床**：床号与位置的关系与 `bedCount` 无关，编号按「建成顺序」（先内后外）分配（`../design/20-layout.md` §3.1、§4），所以老用户的床永远在原地。

### 4.7 pos 消息（批量）

```json
{ "t": "pos", "ts": 1735689600000, "items": [[17, 812.5, 430], [23, 1043.25, 672]] }
```

| 字段 | 说明 |
| :--- | :--- |
| `ts` | 本批次的权威时刻 |
| `items` | `[用户id, x, y]` 的数组（世界像素，可能是小数） |
| 频率 | **每 100 ms 一条，而且只要有人在走动就必发**（不按「格号有没有变」筛）|
| 何时必有 | **走路开始**与**走路结束**时各立即补发一条当前位置（让客户端永远有新鲜的插值端点）|

**合并是关键**：无论这一周期里有 1 个人还是 50 个人移动，只发这一条。客户端按 `ts` 对每个人的位置做插值。

**不得假设固定帧间隔**：服务端的节拍只是一个**尽力而为的唤醒**，云端计时本身不精确，两次 `pos` 的真实间隔会抖动。因此：

- 服务端推进的距离是「自上次推进以来**实际经过的时间**」× `WALK_SPEED_PX_PER_S`，不是「拍数」的函数——节拍抖动只影响平滑度，不影响移动速度
- 客户端必须按 `ts` 插值，不得按「收到两条消息的间隔」推进动画。实现上建议**渲染时往后坐一个 `TICK_MS`**：收到新批次的瞬间，画面正好走完【上一批, 本批】这一段，否则小人会每 100 ms 跳一下

**为什么「每拍必发」而不是「变了才发」（这条是实测逼出来的）**：位置是连续的像素量。若只在格号变化时才发，批次间隔会随速度与节拍抖动（实测 202 / 305 / 203 ms），客户端算出的插值窗口跨度跟着变——跨度一缩短，渲染时间线就往前跳一截，表现为**单帧瞬移 10~13px**；而人停下后再起步时，窗口起点还停在几十秒前的旧样本上，起步那一帧直接跳满一整格（32px）。

这与业界结论一致：**快照按固定频率生成 + 客户端在「过去」插值 + 插值缓冲至少覆盖一个发送间隔**（Gabriel Gambetta《Entity Interpolation》、Gaffer On Games《Snapshot Interpolation》、SnapNet《Netcode Architectures Part 3》）。SnapNet 特别点出：**服务端按固定频率生成快照；若玩家速度可变而快照频率不匹配，远端玩家的插值会出现不均匀的运动**——正是我们踩到的这个坑。

**客户端滞后**：`滞后 = clamp(1 × 本窗口跨度, 100 ms, 400 ms)`。等长跨度下它就是那个固定间隔（≈一个节拍）；跨度超出上限时**不跨该窗口插值**（那就是“快进一格”），取窗口那一侧的端点。口径、误差预算与验收见 `../design/30-movement-sync.md` §4。

**跳变类位置（`hop` 瞬移）不插值**：服务端把位置一步改到位时发的是普通 `pos`，但**客户端对单次位移 > 400px 的更新直接落位**（否则跨厅瞬移会在 100 ms 内拉出一道横贯大厅的模糊线）。阈值只写在客户端，服务端不需要知道；相机**同时对准那张床**（客户端 `focusBed`），不依赖跟随。

**为什么不加抖动预算（不取 1.5×）**：快照走 TCP，没有丢包，客户端时钟又被 `serverNow` 锚定（恒定传输延迟被时钟偏移吸收），剩下要缓的只是「相对快照时刻的偏差 Δ」。逐帧模拟显示：跨度等长时 1× 在 Δ≈0 下**零台阶**，而 1.5× 每拍固定制造 0.5×跨度（≈6.4px）台阶与半程 2 倍速（即“跳一下→走一段”）；在 Δ 抖动、节拍拖到 260ms 这两组场景里 1× 也不劣于 1.5×。

**已知未解项**：服务端节拍偶尔晚点（例如 100ms 的拍拖到 260ms）时，1× 仍会出现一次 ~20px 台阶（迟到期间的位移一次补上）。要不要加「渲染时钟平滑」（把补上来的位移均摊到后续几帧）**先看实际的 tick 间隔分布**：本地已实测（`tickSpan` p50/p95 = 101/102ms、`>150ms` 只有 2 次，且都发生在「停后重新起步」那一拍——那时窗口跨度远超上限、客户端本来就取端点），**结论是现在不做**；生产上的 RTT 与平台定时器精度仍未量，配方与判据在 `../design/backlog.md` 的「节拍实际抖动」与「渲染时钟平滑」两行。

**位置必须带小数**：若位置量化到格（旧实现就是如此），即使固定每 100 ms 发一次，客户端也只能每 250 ms 拿到一个整格位移——“跳一下→走一段”照旧。

### 4.8 whisper 的投递规则

| 项 | 全局聊天 | 私聊 |
| :--- | :--- | :--- |
| 收件人 | 厅内所有人（含发送者） | **发送者 + 接收者**（各一条、结构相同） |
| 文本过滤 | 打码不拦截 | **与聊天同一套规则**（打码、长度、空消息），只是投递范围不同 |
| 目标不存在 | — | `2005`，**静默**：发送者拿不到任何反馈，探测者也无从判断 |
| 睡着时 | 先自动醒后处理 | 同左 |

**表情没有自己的通道**：它就是一条聊天文本（`chat` 或 `whisper`），客户端表情按钮发出去的内容就是一个 emoji 字符。因此它跟着聊天的全部规则走——打码、长度、5 条/秒限流、8 秒气泡（`CHAT_BUBBLE_MS`），不落库、服务端不记任何状态。

## 5. 客户端状态机（渲染侧）

本地状态只有三块，都不需要「床的状态机」：

```text
me        ：自己的身份与状态（含 bedNo / ownedBedNo）
bedCount  ：当前床位数（未过期的床号区间是 0 … bedCount−1）
ownedBeds ：归属集合（快照位图解开后是 Set<bedNo>；bed 消息增量维护）
people    ：可见的人 Map<id, { name, appearance, state, x, y, bedNo?, traceUntil? }>
```

| 收到 | 动作 |
| :--- | :--- |
| `snapshot` | 用服务端内容整体覆盖全部状态（位图 → `Set<bedNo>`） |
| `join` | 插入/覆盖 `people` 条目；把 `online` 刷新为消息里的值 |
| `leave` | 删除 `people` 条目（该床上的占用随之消失）；刷新 `online` |
| `state` | 更新 `people` 条目的显示态（含 `trace`）；刷新 `online` |
| `pos` | 更新 `people` 条目的位置，按 `ts` 插值 |
| `bed` | 更新 `ownedBeds`：`owned` 为真则加入，`false` 则移出 |
| `resize` | 更新 `bedCount`；床号 ≥ 新值 的条目从 `ownedBeds` 与 `people` 里丢弃 |
| `chat` / `whisper` | 挂到**那个人**身上成为气泡（与选中名字共用头顶唯一一个槽位，见 `../ui/DESIGN.md`）。**没有本地消息流、没有历史**；同人后来的消息覆盖前一条；人离开大厅则气泡随之消失（气泡挂在人身上，不留“空气里的名字”） |
| `error` | 按错误码映射为提示（静默类不提示） |

**三处纯客户端推导**（都不需要服务端参与）：

| 推导 | 依据 | 为什么放客户端 |
| :--- | :--- | :--- |
| 睡痕过期 | 条目的 `traceUntil` 与自己的 `clockOffsetMs` | 让「睡痕消失」不需要任何定时器与广播 |
| 色调档位 | 自己的显示态（`roaming` / `lying` / `asleep`） | 只是画面氛围，不需要协议字段（见 `../ui/DESIGN.md`「三档色调」） |
| 位置插值 | `pos.ts` | 位置不进前端框架的渲染循环（见下） |

**床位视觉的派生规则**（两个维度各自独立，不要合并成一个「床位状态」）：

```text
轮廓颜色 = 床上有人（lying/asleep） → line
           床上是睡痕（trace）      → trace
           空床（有主无主都一样）   → claimed
轮廓线型 = 空床 + 无主 → 虚线（另加淡填充）；其余 → 实线
床号文字 = 每张床常显（1× 下床号是主要导航线索；拉远后文字退役）
暖灯小标记 = 该床是我的（ownedBedNo 匹配） → 画；否则不画
名字       = 床上有人 且 不是我自己       → 画；否则不画
小人不透明度 = 睡痕 → 降低；其余 → 正常
```

| 情形 | 轮廓 | 床号 | 暖灯小标记 | 名字 |
| :--- | :--- | :--- | :--- | :--- |
| 无主空床 | `claimed` + **虚线** | 画 | 无 | 不画 |
| 别人的床，空着 | `claimed` 实线 | 画 | 无 | 不画 |
| 我的床，空着（我在厅里走动） | `claimed` 实线 | 画 | **有** | 不画 |
| 别人的床，有人在睡 | `line` 亮 + 实线 | 画 | 无 | 画 |
| 别人的床，睡痕 | `trace` 实线 | 画 | 无 | 画，更暗（小人同步降不透明度） |
| 我的床（我自己躺着） | `line` 亮 + 实线 | 画 | **有** | **不画**（我知道我是谁） |

三个设计意图：

1. **「有人睡」比「谁的床」重要**，所以轮廓**颜色**档位只按占用强度排（`line` > `trace` > `claimed`）；**归属（有主 / 无主）走线型**，不占颜色档位——深底上做不出既单调又都 ≥3:1 的四档颜色。
2. **「是我的」用一个独立的小标记表达**，不参与轮廓梯次——否则暖灯色会因为在冷底上更抢眼而把「谁的床」排到「有人睡」前面（理由与对比度数据见 `../ui/DESIGN.md`）。
3. **名字只出现在有人的床上**（凌晨大约几十张）；大厅里每张床都常显**床号**（1× 下的主要导航线索）。

**渲染顺序**（不要遍历所有床去找占用者；渲染层只画相机视野内的那几十张）：

```text
1. 画地板与墙
2. 画视野内的床（按归属：无主 → claimed 虚线 + 淡填充；有主 → claimed 实线）+ 每张床的床号
3. 遍历 people 中带 bedNo 的条目 → 该床改成占用轮廓（line 亮线 / trace 痕色），画躺姿
4. 遍历 people 中无 bedNo 的条目 → 在地上画站/走的小人（不画名字）
5. 画自己的暖灯色小标记（小人脚下、自己的床角）
6. 若存在选中对象 → 在其上方画唯一一个名字气泡
```

**漫游者为什么默认不显示名字**：名字是身份信息，而「看到有人和我一样醒着」靠的是看到人本身。几十个飘动的标签会把大厅变成名单。名字在需要时点一下就出来（见 `../ui/DESIGN.md`）。

**服务端发消息的顺序约束**：认领时归属与占用同源，必须**先发 `bed`（归属）再发 `state`（占用）**；升级时**先发 `resize`**，之后才可能有人躺到新床上。反了的话，客户端会短暂渲染出「这张床有人、但不在归属表里」或「床号越界」的矛盾状态。

### 5.1 连接与重连（客户端侧）

**这一块只是渲染层的显示态**，与「人在不在场」无关（服务端看到的仍是 `ONLINE` / `GRACE` / `OFFLINE`，见 `../design/00-master-design.md` §7）。手机上切屏会把连接切成僵尸——`readyState` 仍是 `OPEN`，但发出去的消息没有下文——所以「能不能点」不能靠 `readyState` 判断。

| 客户端连接态 | 含义 | 界面 |
| :--- | :--- | :--- |
| `connecting` | 建连 / 重连中 | 首次 3 秒内**不显示**（否则每次进厅闪一下）；之后显示「正在连接…」+ 按钮 |
| `online` | 已收到 `snapshot` | 不显示 |
| `offline` | 探活超时，或收到 `close` / `error` | 显示「连接已断开，正在重连…」+「尝试连接」按钮，**不自动消失** |

**探活按需，不常驻**（常驻心跳会把对象整夜唤醒）。三条触发点，收敛到同一个动作：

| 触发 | 条件 |
| :--- | :--- |
| 页面从后台回到前台 | `visibilitychange` → 可见 |
| 浏览器恢复联网 | `online` 事件 |
| 发了意图却没有下文 | 发出上行后 `INTENT_ECHO_TIMEOUT_MS` 内没收到任何「关于自己的下行」 |

动作：socket 不是 `OPEN` → 立即重连；是 `OPEN` → 发 `ping`，`PROBE_TIMEOUT_MS` 内没有 `pong` → 关掉它并重连。

**探活的往返也算一次延迟样本**：`ping` 发出到 `pong` 到达就是一次真实往返（HUD 的「延迟」只收真实往返，见 `../design/config.md`），所以回到前台、浏览器恢复联网后延迟会自己刷新一次；**超时那条路不记样本**（TCP 黑洞下没有往返可言）。这仍然不是心跳：探活只在上面三条触发点发。

**重连**按 `1s → 2s → 4s → 8s → 15s` 退避（成功后归零）；**页面 hidden 期间不重试**（省电，且回到前台由探活接手）。提示条**只有一个消失条件**：重连成功。「尝试连接」按钮只做一件事——打断退避等待、立即试一次，不改变退避序列。

**上行在 `offline` 期间一律丢弃，不排队补发**：重连后的位置可能是宽限恢复的原位、也可能是出生点，1 秒前点的那块地已经不代表用户现在想去的地方。丢弃 + 一条常驻提示条（用户看得见、知道要重做）比补发更诚实。

**重连成功后一律以新的 `snapshot` 为准**（不做增量补偿：WebSocket 跑在 TCP 上，消息可靠且有序，正常断线不会静默丢包）：清插值窗口、清气泡与选中，相机对准**我的小人**（不是我的床——宽限恢复会把我放回原位，可能在厅的另一头）。

## 6. 客户端预测的边界

> 完整规格（时间轴、重锚公式、领先量、已知代价、验收口径）见 `../design/30-movement-sync.md`。本节只留协议层边界。

| 允许 | 不允许 |
| :--- | :--- |
| 只对**自己**的小人做外推：发出 `walk` 后，用**共享的同一份寻路**（`src/shared/pathfinding.ts`）算出路径，按 `WALK_SPEED_PX_PER_S` 与时间推进 | 把自己的外推结果当事实发给服务端，或广播给他人 |
| 每收到一条关于自己的 `pos` 就**重锚**（锚点换成权威点在折线上的投影与该批时刻，路径不重算） | 不重锚就一路外推下去（会与服务端分叉，而且再也回不来） |
| 自己**不等**插值滞后（外推的是「现在」，别人的插值滞后一拍） | 也用外推画别人：别人的路径我不知道，外推等于造第二个事实源 |
| `2` 秒收不到关于自己的 `pos` → **冻结在最后一个外推点**；上床 / 离开 / 重连 → 清掉外推 | 冻结时**回退**到旧权威点（倒退比停住更难受）；任何一次重锚让画面**往回走** |

**为什么可以这样外推**：服务端寻路是闭式解（`../design/architecture.md` §2.6），路径与速度都在共享层，所以客户端算出来的轨迹**与服务端一致**，不是猜。这也解释了为什么别人的插值滞后不能照搬到自已身上：那条滞后买的是「别人路径未知时的平滑」，自己不需要。

**被拒的意图必须当场丢掉外推**：服务端拒绝一条 `walk` / `lie` 时**不会**再为那个目标发任何 `pos`（我不是移动者），所以「先走一小段」之后不会有人来纠正——那会变成永久错位。客户端的做法：收到「这条意图一步也没走」的错误码（`3001`/`3002`/`3003`/`3004`/`3005`/`3006`/`3008`/`4002`）就**立刻丢弃外推**、回到权威位置；聊天类错误（`4001`/`4003`）与走动无关，不清。另外 **`hop` 发出去就作废本地外推**（它一步到位，而相邻床脚只差一格，重锚的跳变阈值盖不住）。

**已知代价**：服务端**接受了**意图但轨迹与我算的不一样时（例如它换了目标、或路径被重算），仍是我先按旧折线走、由下一条关于自己的 `pos` 重锚纠正；若那期间一直没有 `pos`，2 秒后冻结在最后一个外推点（**不回退**）。**不给 `walk` 加 ack**：拒绝路径本来就有 `error`（§7），ack 只是同一信息的第二条通道（理由见 `../design/30-movement-sync.md` §3.6、§7）。

**自己以外的一切都以服务端消息为准。**

## 7. 限流与异常

| 情况 | 行为 |
| :--- | :--- |
| 上行超过 5 条/秒 | 丢弃 + 返回 `4002`（静默处理，不重复提示） |
| `ping` 探活 | 与业务意图**共用** 5 条/秒窗口，但**超限时静默丢弃**（不回 `4002`——探活失败不该变成用户可见的错误）。理由：探活不能变成绕过「第一版唯一治理措施」的口子（它会唤醒对象，无限探活 = 无限唤醒） |
| 目标点不在街网上 | 丢弃 + `3006`（静默）；**不吸附到最近的合法点**——静默吸附会让「点床躺下」与「点地面走动」的判定出现意外 |
| 床号越界（≥ `bedCount`） | 丢弃 + `3001`（静默） |
| 布局版本不匹配 | 返回 `2003` 并断开（客户端应刷新页面） |
| 未握手就发业务消息 | 返回 `2004` 并断开 |

## 8. 消息体积预估

| 消息 | 量级 |
| :--- | :--- |
| `snapshot`（100 人在线、200 张床有主、级容量 9558） | `ownedBeds` 位图约 1.6 KB；`people` 约 6 KB。合计 8 KB 以内，**只在进入时发一次** |
| `pos`（20 个移动者） | 数百字节，每 100 ms 一条 |
