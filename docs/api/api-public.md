# 公共约定

## 1. 传输

| 项 | 约定 |
| :--- | :--- |
| 协议 | HTTPS（含 WSS）。平台默认提供，无需自建证书 |
| 同源 | 前端与接口同源。**因此会话 cookie 自动随 WebSocket 握手发送，不需要令牌交换、不需要跨域头** |
| 编码 | 请求与响应体均为 JSON（`Content-Type: application/json`）；WebSocket 消息体为 JSON 文本帧 |

## 2. 会话

| 项 | 约定 |
| :--- | :--- |
| 形式 | 服务端签发的**签名 cookie**（HMAC SHA-256），HttpOnly |
| Cookie 名 | `sc_session` |
| 属性 | `HttpOnly`、`SameSite=Lax`、`Path=/`；`Secure` 只在 HTTPS 下加（本地 http 开发也要能跑） |
| 签发时机 | 首次访问时自动签发，不需要注册流程 |
| 内容 | 用户标识 + **昵称** + **形象** + 18 岁自述位 |
| 有效期 | 长期有效（会话持续刷新）。签名密钥是**对称密钥**（HMAC）：换密钥时走**密钥环**——签名恒用当前密钥，验签再试上一把（`SESSION_SECRET_PREV`），所以轮换不再让所有人变成新身份。详见 `../design/config.md` §4 |
| 客户端职责 | 不需要读取或解析 cookie；不需要在请求里带任何身份信息 |

**服务端不接受任何客户端自报的身份。** 用户标识与床位归属全部来自签名 cookie 或服务端状态。

**从会话里删掉的两样**：`hallId`（只有一个厅，路由用常量）与本地时区（厅时区概念已删除，没有任何消费者）。

### 2.1 为什么昵称必须放在会话里

入场的顺序是「先入场、后认领床位」（见 `../design/00-master-design.md`）。这意味着：

- 一个刚进厅、还没躺下的人，**数据库里没有任何属于他的行**
- 但其他人必须能立即看到他的名字（入口处站着一个小人）

**昵称没有别的来源，就是用户自己在入场层输入的那个**（没有登录、没有第三方资料、没有默认名）。而它不能只存在前端内存里——「上一个人是谁」必须由服务端在**每次 WebSocket 握手时自己读出来**。于是有两个可选存放处：建一张用户表（被否：与床位 1:1，是冗余表），或者放进会话凭据。选了后者。

所以「昵称进 cookie」的准确含义是：**服务端把昵称作为会话状态的一部分，编码进自己签发的那份签名凭据**。不是「前端把昵称塞进 cookie」——cookie 的内容、签名与重签时机完全由服务端决定（见 `10-api-http.md` §2.1 的逐步时序）。

这么做可行的三个前提：

| 前提 | 说明 |
| :--- | :--- |
| 不保密 | 昵称、形象与自述位都是别人本来就看得见（或明知是自述）的信息 |
| 不可篡改 | 靠 HMAC 签名保证。**签名解决的是篡改，不是保密** |
| 体积小 | 三个字段加起来不到 100 字节；会话 cookie **只放这几个字段**，不得往里加聊天历史、设置项等 |

同一个昵称会存在两处，职责不同：

| 位置 | 服务于 | 生命周期 |
| :--- | :--- | :--- |
| 会话 cookie | 在场者的入厅广播（包括还没躺下的人） | 随会话 |
| `bed.owner_name` | 离线者（睡痕）的名字显示 | 随床位归属 |

### 2.2 会话里放什么、不放什么

一条判据：**只有「服务端不查库就无法得知、且必须跨请求存在」的字段才进会话。**

| 字段 | 进会话？ | 理由 |
| :--- | :--- | :--- |
| 用户标识 | 是 | 没有它就认不出人 |
| 昵称 | 是 | 还没认领床位的人在任何数据库里都没有行 |
| 18 岁自述位 | 是 | 客户端上报，服务端无从得知 |
| 形象 | 是 | 入场层选的，别人在厅里直接看得见；**没选过时 cookie 里为空**，厅按 `user_id` 派生 |
| **床位号** | **否** | 纯冗余：床位归属的权威在厅的数据库，用户进厅后由快照下发。放在会话里等于制造第二个真相源 |
| **所属厅** | **否** | 只有一个厅，路由用常量即可 |
| **本地时区** | **否** | 时区概念已删除（没有昼夜、没有按人区分的时间语义） |

## 3. 公共请求头

| 头 | 是否必选 | 说明 |
| :--- | :--- | :--- |
| `Content-Type` | 是（有请求体时） | `application/json` |
| `Cookie` | 自动 | 由浏览器同源策略自动携带，前端无需手工设置 |
| `Accept-Language` | 否 | 仅用于文案语言，不影响业务 |

第一版不做接口版本号（没有外部调用方）。

## 4. 公共响应体结构

| 字段 | 是否必选 | 数据类型 | 取值范围 | 备注 |
| :--- | :--- | :--- | :--- | :--- |
| code | 是 | string | 见 `error-code.md` | 错误码，默认: `"0"` |
| msg | 是 | string | 见 `error-code.md` | 错误码对应说明信息，默认: `"success"` |
| data | 否 | object | — | 响应数据。成功时按各接口定义；失败时通常为空 |

```json
{
    "code": "0",
    "msg": "success",
    "data": {}
}
```

**HTTP 状态码约定**：业务错误统一返回 HTTP 200，错误语义由 `code` 承载。仅当请求本身不合法（格式错误、方法不允许、路由不存在）时使用非 200 状态码。

## 5. WebSocket 消息公共结构

所有 WebSocket 消息都是 JSON 对象，**必须带 `t` 字段表示消息类型**。

| 方向 | 形态 |
| :--- | :--- |
| 上行（客户端 → 服务端） | `{ "t": "...", ... }` —— **只允许表达意图** |
| 下行（服务端 → 客户端） | `{ "t": "...", ... }` —— 表达服务端认定的事实 |

**上行消息中的任何坐标、床位号、身份都只是「意图声明」，服务端有权校验并拒绝。** 下行消息中的状态是唯一事实。

## 6. 时间

| 项 | 约定 |
| :--- | :--- |
| 服务端内部 | 一律使用 UTC 时间戳 |
| 下发给客户端的时间 | epoch 毫秒（`serverTs`、`pos.ts`、`traceUntil`、`chat.ts`） |
| 客户端上报时间 | 一律不信任 |
| 时区 | **服务端不存、不接收、不使用任何时区信息**。每日唤醒固定在 UTC 20:00 |

## 7. 限制

| 项 | 值 | 说明 |
| :--- | :--- | :--- |
| 上行消息频率 | 5 条/秒/连接 | 超出丢弃并返回限流错误 |
| 昵称长度 | 1~16 字符 | 超长拒绝 |
| 聊天消息长度 | 1~200 字符 | 超长拒绝，见接口文档 |
